# kube-resource-fcst 汇报与演示

面向：向领导汇报、现场演示。每一条“已验证”都写了依据，“未验证”和边界单独列出，汇报时可以直接照着讲。

## 一、一句话

按工作负载（模块）自动预测它未来的 CPU/内存/副本需求，由平台给出建议值，再由 operator 调副本、Kyverno 在发布时按建议设置资源；每一步都有安全边界、可以人工压过算法，并且每个决定都能说明依据。

## 二、解决什么问题

- 资源长期按峰值预留：浪费；按平均值给：高峰扛不住。
- 靠人盯着调副本：慢、容易漏；HPA 只看当前值，不看趋势，总是慢半拍。
- 自动化之后最怕“说不清为什么”：所以这个系统把依据、来源、规则都留下来。

## 三、原理（四步，一张图讲完）

```
Prometheus 指标 ──► 采集历史 ──► 多种算法各自预测 ──► 回测打分、选最优 ──► 推荐值（带依据）
                                                                     │
                       ┌─────────────────────────────────────────────┤
                       ▼                                             ▼
            operator 按推荐调副本（auto）                Kyverno 发布时设置资源（admission）
            受 步长/冷却/上下限 约束                      没有对应模块的工作负载不允许部署
```

1. **采集**：按模块绑定的“指标模板”（PromQL 写一次，变量换成该模块自己的命名空间和工作负载）从 Prometheus 取历史数据，同一个模板可以被不同模块使用。
2. **预测**：14 种内置算法（持续值、季节、指数平滑、Holt-Winters、MACD 趋势、随机森林、GBDT、LSTM/GRU 等）加自定义公式，各自对未来一段时间给出预测。
3. **回测与选择**：每种算法都用“滚动回测”（只用当时能看到的历史，不偷看未来）打分，误差用 WAPE 等指标；分数低于门槛的算法不参与，最高分的决定推荐值，不够格就走兜底。
4. **决策与执行**：推荐副本 ≈ 预测峰值 × 余量 ÷ 单 Pod 承载能力（测试环境：请求 100m × 目标 60% = 60m）。operator 再按每个模块配置的最大步长和冷却时间一步一步调，不会一下跳到位，所以副本变化是“台阶”，不是“瞬时”。

**优先级规则（每个字段单独判断）**：旁路 > 固定周期 > 算法推荐 > 模块兜底值 > 保持原值。固定周期里写死的副本/CPU/内存，在生效时间内算法改不了；固定值仍受模块上下限和 OOM 内存下限约束。

### 一次真实压测记录（`deploy/testbed/stress-223214.log`，2026-10-27 22:32，load-web）

| 时间 | 事件 | 副本 |
|---|---|---|
| 22:32 | 压测前 | 2 |
| 22:33 | 需求 120m → 700m | 2 |
| 22:35 | 平台出新决策 | 3 |
| 22:44 | 决策继续跟上 | 6 |
| 22:45 | 需求 700m → 120m（此时副本还在追上一轮的决策） | 6 |
| 22:47 | 追上到最高点（模块上限 10） | 8 |
| 22:51 / 22:55 | 逐个回落（缩容步长 1，冷却 2 分钟） | 7 → 6 |

要讲清楚的一点：副本**滞后于需求**，是因为“决策刷新约 5 分钟一次 + 每次最多加 3 个 + 冷却”，这是有意为之的稳健设计，不是反应慢。

## 五、演示脚本

总原则：**提前一小时开始预演并保留日志**，现场放日志和页面，不要空等 10 分钟。

### 0. 演示前检查（5 分钟）

- 平台在运行（`127.0.0.1:20001`），能登录；模块列表里有 `load-web` 等 4 个模块，模式为 auto。
- 系统参数里 `forecast.allow_auto_mode` 为开启；Prometheus 能查到数据。
- operator 在运行：`kubectl -n kube-resource-fcst-system get pods` 为 Running。
- 凭据有效：看平台日志里没有 `/api/v1/operator/decisions` 的 401。

### 1. 先看页面（3 分钟，讲“看得见、说得清”）

1. 「模块管理 → 模块列表」：一个模块 = 一个被预测和扩缩容的工作负载，行内编辑、删除、克隆、旁路。
2. 「预测结果 → 历史数据」：图上预测线和实际线对比，图例里每个算法带最新预测值和 WAPE，可以点击显示/隐藏。
3. 「预测管理 → 当前排名 / 算法评分」：每种算法的得分和谁在起作用。
4. 「推荐与执行 → 资源推荐」点开详情：这个副本数为什么是这个值（指标来源、哪个算法、依据、固定周期是否生效）。

### 2. 瞬时压测（可调时长，讲“自动扩缩”）

```sh
cd deploy/testbed
# 8 分钟版：需求一下子拉到 700m，看 5 分钟，再降回去看 3 分钟
./stress.sh --mode spike --high 700 --low 120 --hold 300 --recover 180 --sample 15 --name load-web
# 阶梯版：4 次升到顶，每 30 秒一次
./stress.sh --mode ramp --steps 4 --step-every 30 --hold 240 --recover 0
# 只演示流程，不改集群
./stress.sh --dry-run --hold 20 --recover 20
```

- 看什么：脚本每行是 `时间 就绪/期望副本 平台决策副本 决策版本`；结束有汇总：压测前副本、峰值、首次扩容和缩容用了多少秒。
- 要点：`--hold` 少于 5 分钟可能还没出新决策，汇总会写“未观察到”，不是故障。
- 本脚本的 `--dry-run` 已验证；真实压测的参数组合以上面那份历史记录为准，现场第一次跑建议先预演。

### 3. 固定周期压过算法（3 分钟，讲“人可以兜底”）

模块编辑 → “固定周期” → 添加：设起止时间、固定副本、优先级 → 保存。窗口内看“资源推荐”详情：来源显示固定周期；改成禁用或到期后自动回到算法推荐。

### 4. 旁路与安全（2 分钟）

模块行内“旁路”：填写原因后，该模块保持原值，operator 和 Kyverno 都不再改；“解除旁路”恢复。全局还有 admission、auto 两个总开关，关闭后立即停止应用。

### 5. 准入：没有模块就不允许部署（可选，3 分钟）

```sh
kubectl apply -f deploy/testbed/admission-demo.yaml     # 没有模块：被 Kyverno 拒绝，终端直接提示
# 在平台里为它创建同名模块后再 apply：放行；「准入决策记录」页能看到每次询问和结论
```

- 前置：两条 Kyverno 策略和凭据 Secret 已按 `deploy/testbed/README.md`“Admission demo”一节应用，并且 `forecast.allow_admission_mode` 为开启。
- 我这里**没有保留上一次拒绝提示的原文**，请务必在汇报前预演一次。

## 六、边界与风险（要主动说）

- 目前在本地 Docker Desktop 集群 + 合成/测试负载上验证，**没有在生产集群验证**。
- 算法准确率只在测试数据上看过，不能把测试分数当成生产预期；上线前要在真实业务数据上做回测对比。
- 准入部分是 Kyverno 参考策略（未做大规模验证），默认失败放行，不会因为平台故障阻塞发布。
- 副本变化有意比需求“慢一拍”（决策周期、步长、冷却），要快可以缩短决策周期、放大步长，但会增加抖动风险。
- 集群接入凭据（AK/SK）需要用 Kubernetes Secret 自行保管；SK 只在创建/重置时显示一次。

## 七、下一步建议

1. 选 1 到 2 个真实业务工作负载，先用 observe/recommend 模式跑 1 到 2 周，只看建议不执行，对比实际。
2. 确认准确率达标后，对低风险服务开启 auto，保持较小的步长和较长的冷却。
3. 接入生产 Prometheus 与真实告警，补齐运维手册（凭据轮换、旁路流程、故障回退）。

## 八、可能被问到的问题

- **预测不准怎么办？** 模块有最低评分门槛，低于门槛自动走兜底值并在“降级与回退记录”里记录原因；也可以随时旁路。
- **会不会把服务缩没了？** 副本有下限，每次缩容有步长和冷却，OOM 后内存有下限保护，固定周期可以人工压住。
- **平台挂了会怎样？** operator 在决策过期或缺失时冻结，不继续缩容（兜底只会加副本）；Kyverno 策略平台不可达时放行。
- **和 HPA 是什么关系？** 副本由本系统的 operator 唯一控制，不能和 HPA/KEDA 同时控制同一个工作负载。
- **为什么用这么多算法？** 不同负载形态不同；用回测分数选最合适的，而不是押注某一种。
