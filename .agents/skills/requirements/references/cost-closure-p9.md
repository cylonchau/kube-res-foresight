## 目标与 KPI

**目标**：在不损害业务稳定和性能的前提下，用更少的基础设施成本承载负载，并能证明省了多少。KPI 的顺序：

1. 业务稳定：OOM、CPU 节流、容量 SLO 不退化。
2. 可兑现的成本节省：有价格或账单依据的下降。
3. 资源浪费可见：哪些工作负载的 requests 高于它需要的。
4. 预测准确率是支撑指标，不是目标。

**两个闭环，各自独立验证**：资源闭环（负载 → 预测 → requests/limits/副本 → 性能验证，P1～P8 已有主体）；成本闭环（配置 → 节点装箱 → 节点释放 → 账单核对 → 实际节省，P9 新增）。第一条保证稳定，第二条保证真的少花钱。

**必须守住的一点**：requests 降了 40%，节点数不变，固定按节点计费时直接节省是 0。所以每个页面同时给“资源释放量”和“可兑现成本”，不能只报前者。

## 四个财务口径（不得混用）

| 口径 | 定义 | 数据依据 | 能不能标“已实现” |
|---|---|---|---|
| 资源释放量 | 前后 requests（vCPU、GiB）× 持续时间之差 | 平台的推荐快照、准入记录、实测 requests 指标 | 是，但它是资源量，不是钱 |
| 预计节省（情景） | 释放量按价格表折算，或装箱模拟可释放节点数 × 节点单价 | 价格表 + C4 模拟 | 否，页面标“预计” |
| 成本避免量 | 未来扩容需求可能减少的支出 | 需要增长假设 | 否，单独列出，不进总 KPI |
| 实际节省 | 与基线比，经节点小时或账单核实的成本下降 | 实际节点小时 × 单价，或手工录入的账单金额 | 只在节点数确实下降且价格已知时 |

- **机会不能直接相加**：同一节点上的多个工作负载的收益会在装箱里互相吞掉，总额由 C4 对合并后的结果重新模拟，列表上写明“不能直接相加”。
- **基线必须声明**：默认取优化生效前的一段窗口（D3），同时记下那段窗口的负载量；负载变了就写“负载变化 x%”，不假装可比。没有基线依据就不给“实际节省”。
- 已有的“Pod·小时多占”**不是**节省（P8 已写明没有基线）；P9 的台账才引入基线。

## 与现有规则的关系（冲突与处理）

| 方案的说法 | 与现有规则 | 处理 |
|---|---|---|
| “Operator 管运行期，HPA 控制副本” | 副本只由 operator 写，HPA/KEDA 不能双写 | **不采用 HPA 当执行后端**。外部 HPA/KEDA 只报冲突；成本模拟里对它们的目标标“不可优化：外部 HPA”。方案担心的“HPA 利用率分母随 requests 变”，在本平台体现为副本按“新规格 × 目标利用率”重算，候选方案必须一起算，不能单独降 requests |
| Karpenter / Cluster Autoscaler 整合节点 | 平台和 operator 不创建任何集群资源 | 它们自己整合；平台只模拟、验证、记录，**不 cordon、不 drain、不删节点** |
| 跨集群优化、规格选择 | 项目是单集群，已有多集群缺口（C1–C3）待决策 | 不在 P9 内 |
| 准入记录必须来自真实准入事件 | R20 已落实 | 台账用推荐 ID、规格版本、准入记录的 `record_id` **关联**这些记录，从不生成准入记录 |
| “Limits 不按 Requests 百分比统一缩减” | AGENTS 第 9 条：未经回测和授权不得自动调低内存 limit | 一致；内存 limit 仍按模块 `limit_memory_ratio`，成本方案不自动调低它 |
| “成本最优资源” | 一个值只叠一层余量（R23 的教训） | 成本最优值**不得低于安全值**；安全值就是现有推荐（含 OOM 地板、规格保持、目标利用率口径），不在其上再叠第二层余量或再下调 |
| Operator 与数据库 | operator 不连数据库，只经平台 API | 节点快照要采集的话由 operator 只读上报到平台 API（D2） |
| 金额 | 页面固定中文、UTC+8 显示 | 价格存“每小时单价 + 币种代码”，不假设美元，不同币种不相加 |

## C1 价格与成本数据层

**回答的问题**：集群和每个工作负载现在花多少钱，闲置多少。

- **内容**：纯函数包（暂定 `pkg/cost`）：节点小时单价 × 节点小时 → 节点成本；工作负载成本按 requests（及使用）分摊到所在节点的成本，CPU 与内存的权重是可配置的（默认值需有依据，核实前不写“业界标准”）；闲置成本 = 节点成本 − 已分摊。价格表按节点标签或实例类型匹配；可选的 OpenCost 预设（标“未验证”，指标名按目标版本核实）。
- **验收**：守恒——Σ工作负载成本 + 闲置 = 节点总成本（单测）；没有价格的节点显示“未定价”，**不当 0 算**；币种不同不相加；迁移在三种数据库上都建得起来；价格与币种变更有操作日志。
- **不做**：不接云厂商账单 API；不做多集群。

## C2 浪费诊断

**回答的问题**：哪些工作负载的 requests 超过了它需要的，浪费多少 vCPU 和 GiB，折合多少钱，调低有什么风险。

- **内容**：每个工作负载 × 资源：当前 requests、使用的 P50/P95/P99、窗口（7/14/30 天，取已有历史）、OOM 与节流次数；闲置工作负载（使用长期低于 requests 的某个比例，阈值是系统参数）。浪费 = max(0, requests − 安全值)，金额 = 浪费 × 单价（C1）。不只看平均，窗口短于一个业务周期的标“窗口不足”。
- **验收**：每个数字能追到已有的样本表和指标；样本不足写“样本不足（n）”而不是 0；单测覆盖口径（闲置、浪费、窗口不足）。
- **不做**：不改任何配置，只读。

## C3 候选方案与风险等级

**回答的问题**：这个工作负载的 requests 调成多少，成本和风险各是什么。

- **内容**：每个工作负载三个值并列——当前、**安全**（现有推荐）、**成本最优**（不低于安全值）。候选分激进（安全值）、平衡（P99 用量 + 余量）、保守（最高用量 + 余量），三档都夹在安全值和现在的请求之间，余量是系统参数 `cost.candidate_margin_percent`；规格保持时间不进候选（保持是应用时现有逻辑的事），不新增预测模型。每个候选写：requests 变化、预计金额（标“预计”）、依据的证据（低估 P90、OOM 次数、节流）；不满足条件时不给候选并写原因。副本和单 Pod 规格一起算（目标利用率口径，见 R23）。
- **验收**：候选值不低于安全值（属性测试）；有外部 HPA/KEDA 的目标不出候选；纯函数加单测。
- **不做**：不给“概率”式的风险数字（没有校准依据，只给证据）；不新增算法。

## C4 节点装箱模拟器（只读 what-if）

**回答的问题**：按候选方案调完，能少几台节点，哪些节点放不掉、为什么。

- **内容**：输入节点与 Pod 快照（D2）和候选的新 requests；按 CPU/内存二维做 first-fit-decreasing；首版约束见 D5；输出：可释放节点数（**估计**，不是上界也不是下界）、每个放不掉的节点及原因、未模拟的约束清单。这是 what-if，不等价于 Karpenter 的 consolidation，页面和文档都要写。
- **验收**：确定性（同输入同输出）；所有 Pod 都放得下才算可行；合成集群单测（放不下、污点、DaemonSet 开销、空节点）。
- **不做**：不执行 cordon/drain/删节点，不调用云 API。

## C5 节省台账与效果验证

**回答的问题**：每次调整到底省了多少、有没有伤到业务、没达到目标的是哪些。

- **内容**：一张台账，每次被应用的资源变更一条：关联的推荐 ID、规格版本、准入记录的 `record_id`、应用时间；前后 requests；基线窗口与对照窗口的负载量；资源释放量；预计节省；实际节省（只有节点数确实下降且价格已知才有）；状态：预计 / 生效中 / 已实现 / 未达标 / 已回滚。**未达标也记录原因**（如“requests 降了但节点数没变”）。
- **验收**：重复写同一变更幂等；“已实现”必须有节点小时或账单依据，否则最多是“预计”；列表合计不直接相加机会，写明去重口径；页面是一个标准列表页。
- **不做**：不生成准入记录；不把 Pod·小时多占当节省。

## C6 SLO 保护与自动回滚

**回答的问题**：调完之后变差了，能不能自己退回去。

- **内容**：应用后的观察窗口内，容量 SLO 低于 `forecast.slo_capacity_target_percent`、OOM 增加或节流升高（阈值是系统参数）→ 退回上一个规格版本，写回退记录，通过 B3 通知。回滚也是一条台账记录。准入只改新建的 Pod，运行中的 Pod 要等工作负载滚动，回滚同样如此，页面要写明。
- **验收**：合成数据单测；回滚幂等；回滚不会被规格保持拦住（增加立即生效，是现有规则）。
- **依赖**：B3 没做之前只提示，不自动回滚。

## C1～C4 实际实现（2026-11-19）

- **后端**
  - `pkg/cost`（纯函数，不读库、不写集群）：`price.go`（价格规则：匹配、校验、优先级）、`allocate.go`（`Allocate`：把节点价格按 requests 分摊，CPU 部分占 `cost.cpu_share_percent`，默认 50）、`diagnose.go`（`UsageOf`、`Diagnose`、`Candidates`）、`simulate.go`（`Simulate`）、`snapshot.go`（`Collect`：从 kube-state-metrics 读节点、污点、标签、Pod、requests、属主）。`promclient.QueryVector` 是多序列即时查询。
  - 价格规则表 `cost_price_rule`（AutoMigrate）；四个系统参数 `cost.datasource_id`、`cost.cpu_share_percent`、`cost.candidate_margin_percent`、`cost.idle_percent`（`pkg/timing/cost.go`，随 `timing.All()` 播种）。
  - 接口：`GET/POST/PUT/DELETE /api/v1/cost/prices`、`GET /cost/overview`、`GET /cost/modules`、`POST /cost/simulate`；菜单 `forecast-results_cost`（预测结果下，`BeApis` 随种子）。
- **前端**：一个页面 `forecast-results/cost`，单视图，价格规则、工作负载详情、模拟都是弹窗，没有页签。
- **口径**
  - 成本：Σ工作负载 + 闲置 = 节点价格（测试守恒）；没有价格规则匹配的节点列为“未定价”，不当免费；币种分块，不相加；一个月按 730 小时。
  - 浪费：只对模块（平台管理的工作负载）。每个 Pod 的使用量 = 工作负载总量序列 ÷ 同一时刻的就绪副本数（要有 replicas 序列），pod/container 级序列直接用；P50/P95/P99 用最近排名法；**安全值** = 最新推荐里来自算法或 OOM 保护的 CPU/内存（固定周期、旁路、fallback、原值不算）；可回收 = max(0, 请求 − 安全值)；闲置 = P99 低于请求的 `cost.idle_percent`；样本少于 100 个不判断。
  - 候选：激进 = 安全值，平衡 = P99 × (1 + 余量)，保守 = 最高用量 × (1 + 余量)，都夹在 [安全值, 现在的请求]，并按 `RoundCPUMilli`/`RoundMemoryBytes` 取整成可执行的规格；现在的请求不高于安全值时不给候选（低于它写“这是风险，不是节省”）；最近 24 小时有“冲突”执行记录（外部 HPA/KEDA）的目标不给候选。
  - 金额：可回收量 × 副本数（最新就绪副本数，没有取推荐的副本数）× 集群平均的核·小时、GiB·小时价格 × 730，**是预计**。
  - 模拟：最少用的节点先试；Pod 从大到小放到放得下且放完最紧的节点；DaemonSet Pod 跟节点走；没有控制器的 Pod 挡住节点；一个 Pod 只能去污点是它原节点污点子集的节点；节点的 Pod 数上限也算。输出“按现在的 requests”和“用某档候选后”两份，差值才是候选带来的；候选只会降低一个 Pod 的请求，不会抬高。
- **与原计划的差别**
  1. 候选档位按上面的定义，不含规格保持时间。
  2. 候选的证据里没有 OOM 次数和节流次数（要读 OOM、节流指标，没做）：证据是用量分位、样本数和“有没有外部控制器”。
  3. 模拟结果标“估计”，不是“乐观上界”。
  4. 候选只给值，不改任何 requests；没有“风险概率”，只有三个档位。
  5. D2 的 operator 只读上报没做：没有亲和性、拓扑分布、PDB、Pod 的真实 tolerations；节点标签只在 kube-state-metrics 放行后才有（没有就写在快照说明里）。
  6. OpenCost 可选来源没做，只有手填价格规则。
