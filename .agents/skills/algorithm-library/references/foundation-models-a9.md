# A9 小型时序基础模型离线评估（2026-10-29）

结论先说：**Chronos-2 在这份数据上和平台自带的最好统计算法大致打平，没有拉开差距；现成镜像里的 TimesFM 2.5 输出异常，不可用。现在不值得为它引入外部服务。** 数据只有约 5 小时（322 点）、4 个合成负载 × CPU/内存，不是生产结论。

## 做法

- **不自己封装**：用 Docker Hub 上现成的第三方镜像 [`kingfs/unitshub`](https://hub.docker.com/r/kingfs/unitshub)（每个镜像一个模型，REST：`POST /models/current/invoke`，Bearer 密钥）。镜像：`chronos-0.4.0`（Chronos-2，2.85 GB 解压后）、`timesfm-0.4.0`（TimesFM 2.5，3.71 GB）。模型权重已打在镜像里，启动约 25 秒就绪，仅用 CPU（本机 12 核）。
- **只有预测，没有训练接口**：两个模型都是零样本，“周期提交数据训练”在这里等于每次预测都带上截止点之前的全部历史。需要训练/微调（如 Granite TTM 的少样本微调、AutoGluon 微调 Chronos-Bolt）得自己封装服务，本轮没有做。
- **评估工具**：`scripts/tsfm-eval`（Go）。读平台库的**副本**（只读打开），用平台自己的 `backtest.Run` 在**同一批起点**上给所有模型打分，与 `scripts/baseline` 同口径；基础模型每个起点只看到起点之前的数据。
  ```
  docker run -d --name ut-chronos -p 18000:8000 -e MODEL_TYPE=chronos -e API_KEY=local kingfs/unitshub:chronos-0.4.0
  docker run -d --name ut-timesfm -p 18001:8000 -e MODEL_TYPE=timesfm -e API_KEY=local kingfs/unitshub:timesfm-0.4.0
  go run ./scripts/tsfm-eval -db <平台库副本> -horizon 10 -cutoffs 10
  ```
- 对照算法用默认参数：naive、ewma、holt_winters、theta、hist_percentile、peak_envelope、combination。**ridge_ar、gbdt 因必填参数 `lags` 没有跑；knn 在 `load-web` 上历史不足被跳过**，所以它们不在对比里。
- 数据：平台库副本里 `load-web/api/batch/cache` 的 CPU 与内存各一条，步长 60 秒；缺口处只取最近一段连续数据，共 322 点，每条序列 7 个起点、70 个评分点。

## 结果（8 条序列平均，按低估加权误差排序）

视野 10 步（10 分钟）：

| 模型 | WAPE | 低估加权误差 | 峰值低估 | 覆盖率 | 每次预测耗时 |
|---|---|---|---|---|---|
| theta | 0.163 | **0.298** | 0.191 | 0.620 | <1 ms |
| combination | 0.164 | 0.308 | 0.192 | 0.600 | <1 ms |
| ewma | 0.163 | 0.313 | 0.201 | 0.621 | <1 ms |
| **chronos（P50）** | **0.145** | 0.324 | 0.216 | 0.539 | 0.11 s |
| chronos@P90 | 0.298 | 0.338 | 0.059 | 0.902 | 0.14 s |
| holt_winters | 0.182 | 0.353 | 0.195 | 0.593 | <1 ms |
| naive | 0.196 | 0.388 | 0.217 | 0.530 | <1 ms |
| hist_percentile | 0.414 | 0.435 | 0.037 | 0.964 | <1 ms |
| peak_envelope | 0.614 | 0.622 | 0.015 | 0.979 | 2 ms |
| timesfm（该镜像） | 0.426 | 1.013 | 0.079 | 0.334 | 0.96 s |

视野 30 步：theta 0.319、combination 0.322、ewma 0.330、**chronos 0.331**、holt_winters 0.333、naive 0.356，chronos@P90 0.417，timesfm 1.356（低估加权误差）。

## 读数

1. **Chronos-2 的 WAPE 最低**（10 步 0.145，其余最好 0.163），但按“低估更贵”的低估加权误差排只排第 4，与 theta/combination/ewma 的差距在这 70 点样本下不足以排先后。它没有在这份平滑的合成负载上显示出统计算法做不到的东西。
2. **Chronos-2 的 P90 线覆盖率 0.90，达到名义水平**，峰值低估 0.059，比平台默认的 P90 保形包装（A3，覆盖率约 0.83–0.89）略好，但 WAPE 约翻倍（故意偏高），与 hist_percentile 同类取舍。这是它最有用的一点：不用自己标定就给出校准较好的上界。
3. **TimesFM 2.5（该镜像）不可用**：在一条光滑正弦上单独调用时第 2 步就跳到 72（真值约 58），回测里覆盖率仅 0.33、低估加权误差 1.0。这是**该镜像服务的输出**有问题（可能是它的封装或输入处理），**不能当作 TimesFM 模型本身的结论**；没有查原因。
4. **成本**：CPU 上每次预测 0.1 秒（Chronos）和约 1 秒（TimesFM）；平台统计算法不到 1 毫秒。每个模块每次运行的预测次数不多，延迟不是障碍；真正的成本是 2.85 GB 镜像、单独部署、多一个故障点，以及 Operator 的“预测不依赖外部服务”要变成“外部服务不可用时降级”。
5. 数据太短：5 小时、合成负载，没有日周期，基础模型擅长的“识别周期形状”在这里用不上。

## 建议

- **现在不接入**：收益在这份数据上看不出来，代价是新的外部依赖。
- 想继续评估的话，先用**更长的真实历史**（至少几天，含日周期）重跑同一个命令；这一步不需要改代码。
- 如果之后要接入，只考虑 Chronos 的 P90 作为“上界”算法候选，接入方式是一个新的远程算法（走 forecast 注册表，超时/失败时回退到统计算法），而不是替换现有算法；要先决定能否接受外部服务和 2.85 GB 镜像。
- “周期提交数据训练”需要支持微调的模型（Granite TTM、AutoGluon 微调 Chronos-Bolt），不在现成镜像里，得自己封装；上一次尝试的自建镜像因 CUDA 依赖下载过慢（1.2 MB/s）中止，没有评估结果。

## 限制

第三方镜像 `kingfs/unitshub` 未做安全审查，评估只往里发数字，不含凭据；镜像版本 0.4.0（2026-10-22 发布）。结果为 5 小时合成负载上的 7 个起点，不能推广。

## 微调：服务已搭好，效果待数据（2026-10-29 补充）

- **用 Chronos-2 而不是 Chronos-Bolt**：现成镜像里的 chronos 包（2.3.2）自带 Chronos-2 的 `fit`，Bolt 没有（它的微调走 AutoGluon，没装）。镜像里没有 peft，所以是**全参数微调**，不是 LoRA。
- **服务**：`scripts/tsfm-eval/finetune/app.py`，挂载进已拉取的 unitshub chronos 镜像运行，不用新构建（自建镜像那条路因 CUDA 依赖下载太慢作废）。`POST /v1/fit` 提交序列并微调一个模型副本，`POST /v1/predict` 用该序列的微调副本预测（没有就用预训练模型）。
  ```
  docker run -d --name ut-ft -p 18010:8000 -v <scripts/tsfm-eval/finetune>:/srv/ft --entrypoint uvicorn kingfs/unitshub:chronos-0.4.0 --app-dir /srv/ft app:app --host 0.0.0.0 --port 8000
  go run ./scripts/tsfm-eval -db <库副本> -models "ft=http://127.0.0.1:18010,ft:30=http://127.0.0.1:18010" -horizon 10
  ```
  `ft` 是预训练模型，`ft:N` 是每个起点用截止点之前的数据先微调 N 步再预测（序列 id 带起点，微调副本不会用于别的起点，无泄漏）。微调组至少需要 200 点历史。
- **机制验证结果**（`load-web` 的 CPU 与内存，410 点，各 4 个起点共 80 个评分点，视野 10 步，微调 30 步）：

  | 模型 | WAPE | 低估加权误差 | 每次预测耗时 |
  |---|---|---|---|
  | chronos2 预训练 | 0.173 | 0.408 | 0.16 s |
  | ewma | 0.192 | 0.413 | <1 ms |
  | chronos2 微调 30 步 | 0.171 | 0.424 | **约 40 s**（几乎全是微调） |
  | theta | 0.206 | 0.432 | <1 ms |
  | naive | 0.214 | 0.516 | <1 ms |

  微调 30 步没有带来可见的改善（WAPE 0.171 对 0.173，低估加权误差反而 0.424 对 0.408），样本只有 2 条序列 × 4 个起点，**不能据此说微调有用或没用**。这次只证明流程跑得通。
- **还缺**：几天以上的真实历史（现在每条序列约 16 小时、有缺口，集群曾中断）。攒够后用同一条命令重跑；微调步数、学习率（现为 1e-5）、是否 LoRA 都还没调。
- **成本**：微调约 40 秒/次（CPU），每个模块每次运行都微调不现实；若有收益，也只能是“定期微调、预测时复用”，那需要保存微调后的模型副本（约 120M 参数），这套服务还没有这部分。

## 已接入平台：`model_service`（2026-10-30）

- 平台里新增算法 `model_service`（类别“模型服务”），把基础模型当作一个**外部服务**用 HTTP 调用，不是平台内的算法。**默认不启用**；要用先在算法管理页填 `endpoint` 并启用。
- **微调参数由平台定义**：在算法管理页的参数里设置（见 algorithm-library 技能），保存后平台在后台把序列和这些参数一起提交给服务微调，不需要在服务端另配。服务只按收到的参数训练。
- 平台侧流程、接口约定与限制（回测不用微调副本、LoRA 需要 peft、密钥走环境变量）见 [algorithm-library 技能](../SKILL.md) 的“模型服务”一条。
- **验证**：单测覆盖三种协议的请求格式、微调参数原样发给服务、副本新鲜时不重复微调、旧了重新提交、微调失败不影响预测并留下记录、关闭微调时不带序列名、回测不带序列名。真实环境：本机的 Chronos-2 微调容器上，临时平台实例保存参数后自动为 5 个指标各提交了微调，服务收到的参数（10 步、学习率 2e-5、批大小 8、上下文 128、全参数）与平台保存的一致，每次微调有训练记录；算法管理页能按类别筛选并编辑全部参数，浏览器无报错。
- **没验证**：微调后的预测**是否更准**（需要几天以上的真实历史，见上一节）；服务重启后微调副本丢失（只在内存里，平台下一次预测会重新提交，没有持久化）；多个模块同时微调时服务按顺序排队（一次一个，CPU 上每次几十秒）；生产部署（容器放哪、怎么限流）。
