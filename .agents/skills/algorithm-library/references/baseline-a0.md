# A0 实测基线：现有算法在测试平台数据上的滚动回测（2026-10-28）

这是 P7 的第一份实测，**只描述测试环境的这份数据**，不是生产准确率结论，也不能当算法优劣的定论。

## 数据与方法

- 数据：本机 Docker Desktop 集群里的测试负载（ConfigMap 控制需求的 `load-*` 服务），平台 SQLite 库的**副本**（工具只读副本，不碰原库，回测记录写进副本后随副本删除）。
- 有效样本：`load-api`、`load-batch` 两个模块，各 CPU 与内存两个来源，历史约 2.9 小时、步长 60 秒、预测视野 10 步（10 分钟）。`load-web` 当时只有约 6 分钟历史，多数算法因历史不足被跳过；`load-cache` 在取快照时数据已过期（9 分钟）而报错，未计入。
- 历史不足一天，所以“昨天同一时刻”的基线（`seasonal_naive` 日周期）在这份数据上**没有参与任何比较**，所有候选只和 `naive` 比。
- 复现：`go run ./scripts/baseline -db <平台库文件> [-cutoffs N] [-module 名称]`，输出一张 markdown 表（模块、来源、步长、历史、视野、算法、状态、起点数、点数、WAPE、低估加权误差、峰值低估、覆盖率、基线与原因）。

## 读数时要注意

1. **判定有变**：66 个来源×算法结果里 12 个的晋升状态变了（晋升 20 → 22）。这是 A1 的效果（起点更多、铺开、同窗口比较）；A2 的低估规则在这份数据上**没有成为任何一次拒绝的原因**（没有出现“低估加权误差更差”的理由）。
2. **CPU 上没有任何非基线算法被晋升**（新版）：`naive` 的 WAPE 最低（约 0.035），其余都略差。这符合“需求是一个常数加平滑变化，最后一个值就是好预测”的合成负载，不能推广到真实业务。
3. **内存上多数算法比 `naive` 好**（WAPE 约 0.23–0.29 对 0.345），`random_forest` 的低估加权误差最低（0.426）。
4. `hist_percentile` 与 `peak_margin` 是有意保守的（取高分位或加余量）：WAPE 高，但低估加权误差几乎等于 WAPE，说明几乎不会预测偏低；它们适合保底，不适合比准确度。
5. 点数：每个结果 100 点，样本很少，排名对窗口敏感；后续（A3 起）要用更长历史再测。

## 工具的局限

- 只读副本，所以不包含取快照之后新采集的数据；两次运行要比较时必须用同一份副本（本文就是这样做的）。
- 工具走平台自己的回测代码路径，不绕过任何规则；它不评估“实测回填”（`prediction_evaluation`）和模块评分，只是滚动回测。

## A3/A4 补充：Theta 与 P90 线（2026-10-28，同一份快照）

同一份 2.9 小时数据快照（这次把时钟固定在快照里最新样本之后，所以 `load-cache` 也计入，共 6 个模块×来源；`scripts/baseline` 新增 `-enable`、`-set 算法={参数JSON}` 在副本上开关算法、改参数）。

**Theta（点预测）**，6 个来源平均（WAPE / 低估加权误差 / 覆盖率）：

| 算法 | WAPE | 低估加权 | 覆盖率 | 被晋升 |
|---|---|---|---|---|
| theta | 0.143 | **0.260** | 0.55 | 3 |
| random_forest | 0.136 | 0.269 | 0.59 | 4 |
| ridge_ar / knn | 0.146 | 0.272 | 0.62 / 0.58 | 3 / 2 |
| holt_winters | 0.154 | 0.271 | 0.67 | 3 |
| ewma | 0.149 | 0.282 | 0.52 | 2 |
| macd_trend | 0.141 | 0.304 | 0.55 | 2 |
| naive（基线） | 0.174 | 0.326 | 0.47 | 6 |

Theta 的低估加权误差在这份数据上最低，但差距很小（0.260 对 0.269）。CPU 上它和 `naive` 持平（0.035 对 0.035、0.036 对 0.035，load-cache 上略差 0.028 对 0.023），内存上稳定好于 `naive`（0.277/0.289/0.192 对 0.340/0.349/0.264）。**一份 2.9 小时的合成负载不足以排出 Theta 与其他算法的先后。**

**P90 线（`quantile_level`=0.9，ewma / holt_winters / theta / ridge_ar，校准窗口 8）**：

| 算法 | 点预测 WAPE / 覆盖率 | P90 WAPE / 覆盖率 | P90 被晋升（共 6） |
|---|---|---|---|
| ewma | 0.149 / 0.52 | 0.320 / 0.83 | 5 |
| holt_winters | 0.154 / 0.67 | 0.331 / 0.85 | 6 |
| theta | 0.143 / 0.55 | 0.320 / 0.86 | 6 |
| ridge_ar | 0.146 / 0.62 | 0.357 / 0.89 | 5 |

- 覆盖率从约 0.5–0.65 升到 0.83–0.89，接近名义的 0.9，但**略低于 0.9**（校准只用了 8 个窗口，且负载有跳变）。这条线更安全，不是更准：WAPE 变成两倍多，因为它故意偏高，内存的阶跃越大偏得越多。
- P90 线不按 WAPE 晋升（它必输），按“覆盖率不低于 level−0.1 且 pinball 胜过同分位下的基线”晋升（`evaluateQuantile`）。基线是点预测，在 0.9 分位下 pinball 很差，所以这个门槛不高，真正起作用的是覆盖率。6 个来源里只有两次被拒：`load-api` CPU 上 ewma 覆盖率 78% 低于 80%；`load-cache` CPU 上 ridge_ar 的 pinball（0.0034）没有胜过基线（0.0034）。历史只有 6 分钟的 `load-web` 不在表里（覆盖率 60%–67%，大多被拒）。
- 要不要把某个算法设成 P90，取决于业务怎样权衡“扛不住”和“浪费”，这里没有替你决定；默认仍是点预测。

## A5 补充：直接多步与递归（2026-10-28，同一份快照）

岭回归（lags=10）与 GBDT（lags=10，60 棵树），6 个来源平均，视野 10 步（10 分钟）：

| 算法 | 递归 WAPE / 低估加权 / 覆盖率 / 被晋升 | 直接 WAPE / 低估加权 / 覆盖率 / 被晋升 |
|---|---|---|
| gbdt | 0.143 / 0.288 / 0.53 / 4 | 0.144 / **0.257** / 0.64 / 4 |
| ridge_ar | 0.146 / 0.282 / 0.57 / 4 | 0.154 / 0.286 / 0.61 / 2 |

- **在这份数据上没有明显胜负**：10 步的视野太短，递归的误差累积还很小。CPU 上直接略好（如 0.050→0.046、0.048→0.045），内存上略差（如 0.267→0.295）。GBDT 的低估加权误差降了（0.288→0.257），岭回归持平。
- **长视野下差别才显出来**：单测里用噪声正弦、视野 40 步，直接多步对真实信号的平均误差比递归低约 22%（岭回归 27.95→21.83）和 37%（GBDT 29.51→18.60，一次性试验的数字）。所以直接多步是**选项**，默认仍是递归；预测视野长（例如超过 30 步）时再试。
- 成本：这份快照上整次回测 2.66 秒（递归）对 2.84 秒（直接），历史更长或锚点更多时按锚点数倍增加。
