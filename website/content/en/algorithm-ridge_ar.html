Purpose and workload fit

Fits linear relationships from lags, optional UTC calendar features, and covariates. A relatively inexpensive machine-learning candidate for stable linear dependencies.

History and runtime requirements

At least lags + 2×feature width + 1 observations. Calendar features add four dimensions; covariates also increase width. Direct mode adds horizon−1 observations.

Inputs must be regularly sampled, gap-free, and finite. Outputs retain the metric unit, such as CPU cores, memory bytes, or requests per second. The sample interval determines the duration of a step. Minimum history permits execution; it does not establish forecast quality.

Supports covariates on the same sample grid, using only observations before the forecast origin. Future covariates carry the last observed value; future business demand is not assumed known.

How it works and the formula

Ridge autoregression (ridge_ar) predicts the next value linearly from the previous few, with the coefficients fitted by ridge regression. Ridge adds a penalty to ordinary least squares so the coefficients do not swing wildly when the features are correlated (neighbouring lags almost always are).

features:     x(t) = [ y(t−1), y(t−2), …, y(t−L) ]            L = lags
              optional: 4 calendar features, the sin/cos of the day and the week; optional: the latest covariate_lags values of each covariate
standardise:  z(j) = (x(j) − mean(j)) / std(j)                 the target first has its mean ȳ subtracted
ridge:        β = argmin Σ ( y − ȳ − zᵀβ )² + λ · n · ‖β‖²     λ = l2_lambda, n = number of training rows
              (solved as (ZᵀZ + λ·n·I) β = Zᵀ(y − ȳ) with a Cholesky decomposition)
forecast:     ŷ(t) = ȳ + Σ β(j) · z(j)

several steps: recursive (default): the forecast of each step is used as the lag of the next
               direct: one model per step ahead, fed with observed values only, no compounding; with many steps only direct_anchors anchor steps are trained and the steps between are interpolated

How the parameters enter the formula:

  • lags (L): how many previous steps are features. Required; with 5-minute steps 12 looks one hour back.
  • calendar_features: add the sin/cos of the day and the week, so the linear model can express a daily cycle (these features depend on the timestamp alone and are known for every future step).
  • l2_lambda: the strength of the penalty. Features and target are standardised, so it does not depend on the scale of the data; larger gives smaller, steadier coefficients and more underfitting.
  • training_window_steps: use only the latest this-many steps as training rows, 0 = all history.
  • covariate_lags: how many latest values of each covariate are features, only values before the target step, never the future.
  • multi_step, direct_anchors: recursive or direct forecasting, and the number of anchor steps of a direct forecast.
  • The least history = lags + 2 × the number of features + 1, plus the steps ahead − 1 for a direct forecast.

Why it is done this way: a linear autoregression is the cheapest "learned" forecast: it expresses trend and short-term inertia, with calendar features also a cycle, and a linear model can extrapolate (a forecast may leave the training range), which a tree model cannot. The ridge penalty and the standardisation keep it steady with few samples and strongly correlated features.

The price of the recursive forecast: the error of each step is fed to every step after it and a long range drifts towards the mean; the direct strategy trains separately for every anchor step and has no such compounding, at the cost of more trainings.

Configuration example

Edit parameters in Algorithm management. This is a parameter object, not a complete config.yaml. Seasonal examples assume five-minute sampling; adjust for your actual interval. Omitted optional values use the defaults above.

{
  "lags": 24,
  "l2_lambda": 0.01,
  "calendar_features": true,
  "training_window_steps": 2000,
  "multi_step": "direct",
  "direct_anchors": 8
}

Worked example: data, parameters and substitution

Two lags, no calendar features and a history of only 10 points (one every 5 minutes), so the fit can be followed.

{
  "lags": 2,
  "calendar_features": false,
  "l2_lambda": 0.1,
  "multi_step": "recursive"
}
y = [10, 12, 13, 15, 14, 16, 18, 17, 19, 21]

Step 1, build the training rows. Every target y(t) is paired with the two values before it, 8 rows:

feature y(t−1)feature y(t−2)target y(t)
121013
131215
151314
141516
161418
181617
171819
191721

Step 2, standardise and fit. The two features have means 15.5 and 14.375 and standard deviations 2.2913 and 2.4969; the target mean is ȳ = 16.625. Ridge with λ = 0.1 gives the standardised coefficients:

β(y(t−1)) = 1.0902        β(y(t−2)) = 1.1073

Step 3, forecast step 1. The next point has the last two values as features: y(t−1) = 21, y(t−2) = 19:

z1 = (21 − 15.5)   / 2.2913 = 2.4004
z2 = (19 − 14.375) / 2.4969 = 1.8523
ŷ(T+1) = 16.625 + 1.0902 × 2.4004 + 1.1073 × 1.8523 = 21.2931

Step 4, forecast step 2 recursively. 21.2931 becomes the new "latest value": the features are y(t−1) = 21.2931, y(t−2) = 21, and the same formula gives 22.3195.

The result is [21.2931, 22.3195]. The last value of the history is 21 and the forecast goes on up to 22.3, outside the range of the training targets (10 to 21). A linear model extrapolates, which sets it apart from the tree models (random forest, GBDT). Mind it too: extrapolation is a strength on a rise and overshoots at a turning point, so it has to beat the baseline in the backtest before it is adopted.

These numbers are computed by the real code in pkg/forecast/docs_examples_test.go and checked on every test run.

Tuning and tradeoffs

Start with moderate lags. Larger l2_lambda regularizes more strongly but can flatten changes. Direct mode avoids recursive feedback at greater history and training cost. The training window must still meet model requirements.

Use in a module

  1. Save parameters and check history, sample interval, and horizon.
  2. Enable module prediction. Fixed mode runs the selected method; dynamic mode uses centrally enabled methods.
  3. Run rolling backtests and earn version promotion before adoption. Re-run backtests after changes affecting model identity.
  4. Review error, peak underestimation, runtime, and adoption reasons in Observe or Recommend before separately authorizing admission and replica actions.

For insufficient history, invalid settings, timeouts, or invalid output, inspect run reasons. Without eligible forecasts, the module follows its schedules, fallback, and protection rules.
