What the four strategies are for

They are set under "Module strategies" in the module form. They answer one question: how many replicas should there be now.

StrategyHow it decides the replicasFits
Prediction modeNo prediction, one fixed algorithm or the dynamic choice; the replicas and resources come from the forecast.A load with a pattern, capacity prepared ahead.
PeriodsA fixed value, an at-least or an at-most for a time of the day or week.A known business window, such as an evening peak.
Metric triggersWhen a metric crosses a threshold over some minutes: scale out, scale in or set the replicas.Reacting to a metric directly, without a forecast.
Fixed replicasThe replica count written as one constant.Stateful services and others whose replicas must not be changed automatically.

The prediction mode and the run mode are two things: the first answers "how the advice is worked out", the second "what is allowed". A new module has prediction off; with it off or unavailable, the fallback defaults are used.

What fixed replicas is

With fixed replicas set, the module keeps that many replicas; no algorithm, forecast or trigger decides them, and the prediction mode governs only the CPU and the memory. It is not a duplicate of the forecast, the periods or the triggers: it is the step of the merge that comes first and that later strategies do not change; only the bypass and a period that fixes the replicas are above it. 0 lets the algorithm decide.

Periods

Set the replicas for a time: weekly repeating (for example 20:00-03:00 every day; an end before the start crosses midnight) or one-off with a start and an end, in the module's time zone. The replicas of a period can be set in three ways:

  • Fixed: that number for the period; the algorithm takes no part.
  • At least: the algorithm works as usual but not below the number.
  • At most: the algorithm works as usual but not above the number.

CPU and memory are fixed when filled in. When periods overlap: of the fixed ones, the higher priority wins; the largest at-least and the smallest at-most apply, and an at-least above an at-most wins. The result is still held to the module's bounds, and a bypass switches periods off.

Metric triggers

A trigger has the parts below, and a module can have several:

FieldMeaning
Name, priorityThe name is unique in the module; when triggers ask for different counts the larger number wins.
MetricA metric of the module's sources, or the JVM heap share (heap used / heap maximum). The threshold is in the unit of the metric.
Statistic, windowThe latest, mean, maximum or minimum over the last N minutes (15 by default).
Comparison, thresholdGreater than, at least, less than, at most.
Action, amountScale out or in (by N replicas or by N% of the running replicas), or set to N replicas.
In forceWeekdays and the start and end of the day, in the module's zone; empty is all day.

Example: "when the mean CPU over the last 15 minutes is above 2.4 cores, add 2 replicas, on weekdays 09:00-18:00."

When several triggers fire: a set takes the highest priority (the larger on a tie); a scale-out takes the largest increase and is not lowered by a set, the forecast or a scale-in; a scale-in acts only with no scale-out or set, no OOM or JVM pressure and no forecast asking for more, and of several scale-ins the one that removes the least wins.

When strategies give different counts

  1. What the administrator fixed comes first: the bypass, a fixed count in a period, the fixed replicas. Later strategies do not change them.
  2. The rest start from the forecast; with the prediction mode "none" or no forecast, the fallback defaults.
  3. Metric triggers act on that base as described above.
  4. A period's "at least" raises and "at most" caps; several periods go by priority.
  5. The bounds (least and most replicas) apply to the final result and are always last.
  6. The pace limits once more how many replicas an action moves and how often.

"This action reaches" on the recommendation pages and the dashboard is the number after the last step. The pace and the bounds are not strategies, so every strategy is held to them.

Suggestions

  • Start with the prediction mode and the bounds, and add metric triggers once the effect is seen, so it stays clear which source of scale-out is acting; when a trigger fires, the decision records the count each one asked for, whether it was used and why.
  • The at-least of a period can follow the busy hours and the busiest count of "The normal and the busy hours" on the resource dashboard.
  • One controller only for the replicas of a target: do not run it together with HPA or KEDA; see One controller for one target.
