Where to configure, and how to read what is in force

Create or edit a module under "Module management > Module list". The form has four groups: Base settings, Calculation, Safety bounds and Module strategies; the mode is chosen in the basic information. The operate column of the module list has a "Parameters" button: without opening the form it shows, by group, the value in force of every parameter with its unit, its source (this module, a system setting or not set) and its meaning.

The pictures on this page come from a demonstration environment built with simulated data (three modules, a simulated Prometheus and Operator report); the figures only explain the screens and are not any real load.

The "Parameters" window: the value in force of every parameter by group, with its source (this module, a system setting or not set) and its meaning; read only.

Most calculation coefficients take 0 to mean "follow the system setting" (System management > System settings > Resource analysis and recommendation). Change the system setting to move everything; set a coefficient in a module only when that module needs different treatment.

The order of one configuration

  1. Workload and metrics. Fill in the namespace, kind and name; pick CPU, memory and other metric templates under "Algorithm metrics" and Requests, Limits and other display-only metrics under "Monitoring display metrics". Templates come from the data sources and metric templates of Metrics and data quality.
  2. Mode. Start with Observe or Recommend, check that the resource dashboard can be trusted, and only then consider Admission or Auto.
  3. Calculation. Most modules keep the defaults; change a coefficient when there is a definite margin to keep.
  4. Safety bounds. At least the least and most replicas; the pace when the speed of actions must be limited.
  5. Strategies. Add periods, metric triggers or fixed replicas when needed.
  6. Back on the resource dashboard, confirm in the basis that every figure uses the coefficient you set.

"Algorithm metrics" in the base settings: CPU, memory and replicas picked from the metric templates, which come from the mappings of the data source.

Binding metrics: what the dashboard reads

The resource dashboard reads every metric source of the module from Prometheus on the spot. When binding:

  • A use metric returns either one Pod or the sum of all replicas; say which in the source ("the query returns one Pod / all replicas"). When a query returns a series for each Pod, the platform says how to join them: sum(...) for all replicas, avg(...) or max(...) for one Pod.
  • Requests and Limits are display metrics and do not take part in algorithms. With an Operator report the dashboard uses the Pod template and the metric is only a cross-check.
  • OOM, throttling and JVM need their own metrics (OOM count, working set before the kill, CPU throttling, JVM heap); a rule with no metric does not act and the page says what is missing.

Calculation: the recommendation coefficients of the dashboard

These are all the coefficients the dashboard recommends Requests, Limits and replicas with. A module takes 0 to follow the system setting; the system default is in brackets.

SettingMeaningHow to set it
P90, P95, P99 target share (80%, 85%, 110%)The share of the Requests the use at that percentile takes after the recommendation; recommended Requests = use / it.The smaller the share the larger the recommendation. The P99 may be above 100%: a short excess over the Requests is carried by the Limits.
Sustain window (30 minutes)The percentiles of the recommendation are taken of the sustained use; the longer the window the less a short peak counts for a long-term setting.0 takes raw points; widen it for a load with regular short peaks.
CPU and memory Requests margin (none)The share added over the largest need of the three percentiles; 0.1 is 10% more.Set apart for CPU and memory.
CPU and memory Limits coefficient (120%)Recommended Limits = max(recommended Requests, P99 x coefficient).1.2 is P99 x 1.2; not below 1. Do not squeeze the memory coefficient: a Limits below the peak is OOM-killed.
Peak share of the Limits (90%)At the recommended replicas the P99 use of all Pods stays under this share of their Limits.Keeps the replicas from being cut so low that the peak reaches the Limits.
Recommendation floorAbove 0, the recommendation is not below the Pod Requests the module states x it.0 is off.

The reasonable ranges of the three percentiles, the over-provision grades, the CPU throttle limit and the analysis period are changed in the system settings only; the Parameters window of the module list shows them marked "System setting".

"Coefficients" under Calculation: the P90, P95 and P99 target shares of the resource dashboard, the sustain window, the Requests margins, the Limits coefficients and the peak share of the Limits; 0 follows the system setting. The formulas below follow what is filled in, and "System" marks where the system setting is still used.
The two "Limits coefficients" are not the same thing

"CPU and memory Limits coefficient" affects only the recommended Limits of the resource dashboard. The "CPU limit ratio and memory limit ratio" in the basic information are what admission sets as the Limits of a new Pod = recommended Requests x ratio; see Request and Limit ratios and the OOM floor.

Safety bounds

SettingMeaningHow to set it
Least and most replicasWhatever the strategies give ends inside this range; it is always the last step.Set at least one; an unset side has no limit.
Hard ceiling, ceiling expansionWith a dynamic most-replicas mode: when the forecast needs more, the ceiling rises by at most this share of the ceiling now per cycle, up to the hard ceiling.Used only with a dynamic ceiling.
Least and most CPU and memoryThe recommended Requests does not cross them.From the node sizes and the floor of the business.
Most added and removed per action, scale-out and scale-in cooldownHow many replicas one action moves and the gap between actions in the same direction. They limit the speed, not the range.0 is no limit. Removing 1 at a time is a steady start.
Recommendation TTL (900 s), least algorithm scoreHow long a recommendation is valid; an algorithm scoring below the least is not used.A TTL that is too short lets a recommendation expire before the next run.
Fallback CPU, memory, replicasThe defaults when the forecast is not available; they pass through the bounds above.Optional; unset keeps the value.
Recovery cycles (2)After a degraded run, this many healthy cycles in a row end it.Avoids flapping at the edge of a fault.
BypassWhen on, the module takes no part in automatic decisions and nothing is changed.Switch it on, with a reason, for a manual takeover.
"Replica bounds" under Safety bounds: the least and most replicas and the mode of the most; the line below says what the setting comes to.
"Replica pace": the most replicas one action adds or removes in each direction, and the cooldowns.

Strategies

The prediction mode, periods, metric triggers and fixed replicas, and how they combine when they give different replica counts, are in Strategies and how they combine.

Example: a Deployment of 12 replicas

Pod Requests of 4 cores and 6 GiB, Limits of 8 cores and 16 GiB. Goal: observe first, then tighten step by step.

StepSettingWhat the resource dashboard shows
1Mode Recommend; the other coefficients follow the system.Ways 1 and 2 give advice; the coefficients in the basis are the system ones.
2Least replicas 4, most 20, scale-in at most 1 per action.With 9 recommended and 12 now, "recommended replicas" is 9 and "this action reaches" is 11.
