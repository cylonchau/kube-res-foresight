How a login is told apart

The sign-in page has no source option. The platform decides from the user name and the local database:

CaseResult
The name exists locally and is a local accountOnly the local password is checked; the directory is not contacted. admin keeps working when the directory is down.
The name exists locally and is an LDAP accountThe password is checked against the directory only.
The name is unknown and LDAP is enabledThe directory authenticates. On success the roles come from the role mappings and the LDAP user is created.
The name is unknown and LDAP is disabledThe login fails.

A directory user with the same name as a local account never takes it over. An LDAP user's local password is random and unusable, and the password cannot be changed in the user center; change it in the directory. The user list and the user center show the account source.

Parameters

Set them one by one under System → System parameters, in the LDAP category. Each is saved on its own.

ParameterMeaning
ldap.urlDirectory address, such as ldaps://ldap.example.com:636. ldap:// requires StartTLS.
ldap.start_tls / ldap.skip_verifyStartTLS; whether to skip certificate verification. Do not skip it when you can provide the CA.
ldap.ca_certCA (PEM) for a self-signed certificate. Shown masked after saving.
ldap.bind_dn / ldap.bind_passwordService account used to look users up. The password is stored encrypted; set the bind DN first.
ldap.user_base_dnWhere the user search starts, such as dc=example,dc=com.
ldap.user_filterFilter that finds the user. It must contain exactly one %s (the login name), for example (cn=%s) or (&(objectClass=person)(uid=%s)).
ldap.display_name_attr / email_attr / phone_attrAttributes for display name, email and phone, refreshed at each login.
ldap.member_of_attrAttribute of the user entry that lists the DNs of its groups, usually memberOf. When set, the groups are read from it.
ldap.group_base_dn / ldap.group_filterWithout memberOf, look the user up in the group entries: in the filter %s is the user DN and %u the login name, such as (member=%s). Both are set or both are empty: setting one while the other is empty fills in a usual value, and clearing one clears both.
ldap.group_name_attrAttribute of a group entry used as its name, cn by default.
ldap.group_role_mappingsGroup-to-role mappings, below.
ldap.default_role_codeRole of users in no mapped group. Empty means those users cannot sign in.
ldap.timeout_secondsConnection and query timeout, 1 to 120 seconds.
ldap.enabledWhether directory login is on.

Enabling validates the whole configuration and connects to the directory once. If that fails, LDAP is not enabled and the reason is shown, so set ldap.enabled last.

Two ways to get the groups

Use either, or both: the results are merged.

  • Read memberOf of the user: set ldap.member_of_attr; no group base DN or filter is needed. Each value (a group DN) matches either as the full DN or as the value of its first RDN (cn=ops,ou=groups,… matches ops).
  • Search the group entries: set ldap.group_base_dn and ldap.group_filter, and take the name from ldap.group_name_attr. Usual filters: (member=%s) for OpenLDAP groupOfNames, (memberUid=%u) for posixGroup, and (member:1.2.840.113556.1.4.1941:=%s) for AD when nested groups count.

Role mapping

ldap.group_role_mappings takes one group=role code per line:

ops=ADMIN
dev=VIEWER
ou=sre,ou=platform,dc=example,dc=com=ADMIN
  • The left side is a group name (cn) or a full DN, case-insensitive; spaces inside a full DN must match what the directory returns.
  • The right side is the role code, listed under Authorization → Roles. The role must exist and be enabled.
  • The line is split at the last =, so full DNs work as they are. A group may appear on several lines to grant several roles; a user in several groups gets the union.
  • Lines starting with # are comments and blank lines are ignored. A malformed or repeated line is rejected on save.

A user in no mapped group gets ldap.default_role_code; with neither, the login is refused. An existing LDAP user who loses every role is disabled and their sessions end.

Reusing an existing LDAP configuration

Other systems in your company (a wiki, a code host, monitoring, CI) usually use the same directory, and their LDAP settings already hold what is needed here. Copy each value to its parameter:

What you already haveWhere it goes
Server address, port, SSL on or offldap.url; with SSL write ldaps://address:port
StartTLS, skipping certificate verificationldap.start_tls, ldap.skip_verify
The lookup account (bind DN) and its passwordldap.bind_dn, ldap.bind_password
Where users are searched (base DN)ldap.user_base_dn
The user search filter and its placeholder for the login nameldap.user_filter, with the placeholder written as %s. (cn=${username}), (uid={0}) and (sAMAccountName=%(user)s) all become a form like (cn=%s)
Attribute names for the name and the emailldap.display_name_attr, ldap.email_attr
The attribute of the user entry that lists its groups (often memberOf)ldap.member_of_attr
Where groups are searched and the membership filter (without memberOf)ldap.group_base_dn, ldap.group_filter
The table of group DN to role or permissionldap.group_role_mappings, one group DN=role code of this platform per line

Roles in the other system (administrator, editor, read-only) have no fixed counterpart here: use the role codes you created under Authorization → Roles. The built-in administrator role is ADMIN and has every permission, so check before granting it to a whole group.

Complete configuration examples and what happens in one sign-in

Two common directories follow, with what each parameter holds and what the platform does in one sign-in, side by side. Addresses, DNs and group names are examples; replace them with the values of your directory.

Example 1: OpenLDAP, groups from the membership in group entries

The directory holds:

dn: uid=alice,ou=people,dc=example,dc=com
uid: alice
cn: Alice Zhang
mail: alice@example.com

dn: cn=sre,ou=groups,dc=example,dc=com
objectClass: groupOfNames
cn: sre
member: uid=alice,ou=people,dc=example,dc=com

Set the system parameters like this (System → System parameters → LDAP; each item is saved on its own, enable last):

ParameterValueNote
ldap.urlldaps://ldap.example.com:636LDAPS; with ldap:// StartTLS must be on.
ldap.bind_dncn=readonly,dc=example,dc=comA read-only service account used to search for users.
ldap.bind_passwordthe password of the service accountStored encrypted.
ldap.user_base_dnou=people,dc=example,dc=comUsers are searched below it.
ldap.user_filter(uid=%s)%s becomes the login name.
ldap.display_name_attrcnThe display name.
ldap.email_attrmailThe email.
ldap.group_base_dnou=groups,dc=example,dc=comGroup entries are searched here.
ldap.group_filter(member=%s)Here %s is the DN of the user, not the login name.
ldap.group_name_attrcn (default)The attribute of a group entry that is the group name.
ldap.group_role_mappings
sre=ADMIN
dev=VIEWER
One group=role code per line.
ldap.default_role_codeemptySomeone in no mapped group cannot sign in. To let them in read-only, give the code of a read-only role.
ldap.enabledtrueSet last: enabling checks the whole configuration and connects to the directory once.

What happens when alice signs in:

  1. The platform connects to the directory over LDAPS and signs in with the service account cn=readonly,….
  2. It searches below ou=people,… with (uid=alice). It finds one entry uid=alice,ou=people,dc=example,dc=com; none is "user not found", more than one is refused (the filter must match exactly one person). Special characters in the typed login name are escaped and cannot rewrite the filter.
  3. It signs in once more with that DN and the password alice typed. The password is checked only by the directory; the platform neither stores nor compares it.
  4. It reads cn and mail: the display name Alice Zhang and the email.
  5. Groups: it searches below ou=groups,… with (member=uid=alice,ou=people,dc=example,dc=com) and finds the group cn=sre, group name sre.
  6. By the mapping sre=ADMIN alice gets the ADMIN role; the local database has no alice, so a user whose source is LDAP is created and signed in.

The memberOf of an AD user entry holds the full DN of each group, for example CN=Platform-Admins,OU=Groups,DC=example,DC=com. The left side of a mapping may be the full DN or just the value of its first segment (Platform-Admins); the platform matches both. The second line shows the full-DN form: the line is split at the last =, so the whole DN in front is untouched. To count nested groups too, do not use memberOf but the group filter (member:1.2.840.113556.1.4.1941:=%s).

Check before enabling

  • The service account finds the user: sign in with it in any LDAP client and search user_base_dn for a known user with the same filter; it should return exactly one entry.
  • The role code exists and is enabled: the code on the right of a mapping must match the one under Authorization → Roles.
  • Try an ordinary user, then an administrator: make sure a mapped role does not give a whole group more than it should.

Synchronization and disabling

Users who were deleted or disabled in the directory, or who no longer belong to a mapped group, are disabled by the synchronization and lose their sessions; users the directory enabled again are restored, except those an administrator disabled. When the directory cannot be reached no account is changed, so an outage does not lock everyone out.
