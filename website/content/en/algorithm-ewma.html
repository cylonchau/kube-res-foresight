Purpose and workload fit

Smooths recent observations and projects the resulting level. A low-cost candidate for recent demand, without explicit daily seasonality.

History and runtime requirements

At least two observations.

Inputs must be regularly sampled, gap-free, and finite. Outputs retain the metric unit, such as CPU cores, memory bytes, or requests per second. The sample interval determines the duration of a step. Minimum history permits execution; it does not establish forecast quality.

This method does not use covariates; target metrics are forecast separately.

How it works and the formula

EWMA (exponentially weighted moving average, also called simple exponential smoothing) gives every historical value a weight: the newer the value the larger the weight, decaying by a fixed ratio. The forecast is the smoothed "current level", carried into the future.

level recursion:  ℓ(1) = y(1)
                  ℓ(t) = α·y(t) + (1 − α)·ℓ(t−1)        t = 2 … T
forecast:         ŷ(T+h) = ℓ(T)                          h = 1 … H (a flat line)

equivalently: ℓ(T) = α·Σ (1−α)^k · y(T−k): the newest value weighs α, each step back multiplies by (1−α)

How the parameters enter the formula:

  • alpha (α, 0 to 1): the larger, the more the newest value counts. The effective "memory" is about 1/α steps: α=0.3 is roughly the last 3 steps and a bit more.
  • span: another way to write it, α = 2 / (span + 1). span=5 equals α=1/3. Give one of the two, not both.
  • bias_correction: weight the history directly by (1−α)^age and divide by the sum of the weights, instead of starting the recursion at the first value. On a short history the first value does not pull the result.

Why it is done this way: a measured load is noisy: taking the last value lets one spike mislead you, taking the mean of the whole history reacts too slowly. EWMA trades "keeping up" against "resisting noise" with one parameter, costs a single loop, and so is a cheap candidate, especially where the recent load matters most.

What it cannot do: the forecast is a flat line, it neither extrapolates a trend nor knows a cycle. On a steadily rising load it is always a little low (it lags the trend).

Worked example: data, parameters and substitution

The last 6 samples (one every 5 minutes) of a CPU usage in cores. Parameters:

{
  "alpha": 0.3,
  "bias_correction": false
}
y = [10, 12, 11, 15, 14, 16]

Recursing from the first value with ℓ(t) = 0.3·y(t) + 0.7·ℓ(t−1):

ty(t)substitutionℓ(t)
110ℓ(1) = y(1)10.0000
2120.3×12 + 0.7×10.000010.6000
3110.3×11 + 0.7×10.600010.7200
4150.3×15 + 0.7×10.720012.0040
5140.3×14 + 0.7×12.004012.6028
6160.3×16 + 0.7×12.602813.6220

So the forecast is [13.622, 13.622] (2 steps): a flat line. Note the last actual value is 16 while the forecast is 13.6: the smaller earlier values still pull it down. That is the price of smoothing, and why it comes out low on a rising load.

See how the result changes with other parameters (same data):

  • bias_correction: true: weigh directly with 1, 0.7, 0.49, 0.343, 0.2401, 0.16807 (the newest value weighs most) and average: 14.1049. It is no longer tied to the first value 10, so it is higher.
  • span: 5 (α = 2/6 ≈ 0.3333): 13.8601, a little closer to the newest value than α=0.3.

These numbers are computed by the real code in pkg/forecast/docs_examples_test.go and checked on every test run.

Tuning and tradeoffs

A larger alpha reacts faster but follows more noise. span is an alternative way to specify smoothing; do not supply explicit alpha together with a positive span.

Use in a module

  1. Save parameters and check history, sample interval, and horizon.
  2. Enable module prediction. Fixed mode runs the selected method; dynamic mode uses centrally enabled methods.
  3. Run rolling backtests and earn version promotion before adoption. Re-run backtests after changes affecting model identity.
  4. Review error, peak underestimation, runtime, and adoption reasons in Observe or Recommend before separately authorizing admission and replica actions.

For insufficient history, invalid settings, timeouts, or invalid output, inspect run reasons. Without eligible forecasts, the module follows its schedules, fallback, and protection rules.
