Purpose and workload fit

Groups observations by time of day and optionally weekday, then uses a decayed percentile per bucket. Useful for weekday/weekend demand patterns.

History and runtime requirements

A minimum of four observations. Weekday profiles need sufficient weeks and bucket samples; sparse buckets fall back to time of day, then the overall percentile.

Inputs must be regularly sampled, gap-free, and finite. Outputs retain the metric unit, such as CPU cores, memory bytes, or requests per second. The sample interval determines the duration of a step. Minimum history permits execution; it does not establish forecast quality.

This method does not use covariates; target metrics are forecast separately.

How it works and the formula

The seasonal profile puts the history into buckets of "which day of the week + which part of the day", each bucket holding all the earlier samples of that moment. To forecast a future moment it reads the decayed percentile of the bucket that moment falls in. It is the percentile recommender of the VPA/Autopilot with a clock added.

bucket:  local time = UTC + utc_offset_minutes
         bucket no. = ⌊(minutes of the local day) / bucket_minutes⌋
         with by_weekday the bucket = (weekday, bucket no.), 7 × (1440/bucket_minutes) buckets; otherwise only the bucket no., 1440/bucket_minutes buckets

weight:  w(i) = 0.5 ^ (age(i) / H), H = half_life_days in steps (0 = no decay)

reading (in order, the first that has enough):
  1) by_weekday on and the "weekday + part of day" bucket holds at least min_samples_per_bucket samples → the weighted percentile of that bucket
  2) else the "part of day" bucket (all weekdays together) has enough → the weighted percentile of that bucket
  3) else → the weighted percentile of the whole history (then it is the same as hist_percentile)

weighted percentile: sort by value, add up the weights, take the first value whose cumulative weight ≥ (percentile/100) × total weight
forecast:  ŷ = the percentile value × (1 + safety_margin)

How the parameters enter the formula:

  • percentile: which percentile of a bucket, the higher the more conservative (default 90).
  • bucket_minutes: the width of a bucket in minutes, must divide 1440. 60 means one bucket per hour.
  • by_weekday: whether the day of the week is told apart (default yes). When not, all weekdays merge into one day's shape.
  • half_life_days: the half-life of the sample weight in days (default 14). It lets the recent past count more than the distant one.
  • min_samples_per_bucket: how many samples a bucket needs before it is trusted (default 6); with fewer the next level above is used. Note it counts samples, not cycles: with a fine step one bucket of one day already holds several samples.
  • utc_offset_minutes: the time zone, Beijing time = 480 (default). It decides which bucket "9 a.m." is.
  • safety_margin: extra room added on the percentile value.

Why it is done this way: for a load that "always peaks at 9 a.m." a time-blind flat line (hist_percentile) either wastes capacity most of the day or falls short at the peak. With buckets every part of the day has its own level: 9 a.m. reads the 9 a.m. bucket, the small hours read theirs. A percentile and not a mean covers the usual peak of that part of the day, which is what a resource recommendation wants; compared with seasonal naive, every day is a vote, so one odd day is one vote among many.

Note: a percentile is a deliberately high forecast, not the expected load, and the need breakdown says so. With few samples (say 3 days) the 90th percentile is nearly the maximum. The platform has a rule of its own: the history must hold enough full cycles (system parameter forecast.min_seasons, default 3) before it may decide, because the shape of a day learned from one day takes that day's incident for a pattern.

Configuration example

Edit parameters in Algorithm management. This is a parameter object, not a complete config.yaml. Seasonal examples assume five-minute sampling; adjust for your actual interval. Omitted optional values use the defaults above.

{
  "percentile": 90,
  "bucket_minutes": 60,
  "by_weekday": true,
  "half_life_days": 14,
  "utc_offset_minutes": 480
}

Worked example: data, parameters and substitution

To keep it readable we use a coarse setting: one point every 6 hours, buckets of 360 minutes (4 buckets a day), no weekday split, no decay, at least 2 samples per bucket, time zone UTC. The history is 3 days of a CPU usage in cores.

{
  "percentile": 90,
  "bucket_minutes": 360,
  "by_weekday": false,
  "half_life_days": 0,
  "min_samples_per_bucket": 2,
  "utc_offset_minutes": 0
}

day 1 (Wed)      20      35      60      30
day 2 (Thu)      22      38      55      32
day 3 (Fri)      21      36      70      29        the last point is Friday 18:00

Step 1, put them into "part of the day" buckets. Every bucket holds 3 samples:

Step 2, read the 90th percentile of each bucket. No decay, so the 3 samples weigh the same and the target cumulative weight = 0.9 × 3 = 2.7. Sorted, the cumulative weights are 1, 2, 3 and the first ≥ 2.7 is the 3rd, the maximum:

Step 3, forecast the next 4 steps (Saturday 00:00, 06:00, 12:00, 18:00), each reading its own bucket, safety_margin 0:

The example shows two things: with very few samples the 90th percentile is the maximum (the 70 at 12:00 comes from the one peak of day 3), and every part of the day reads its own bucket, so the forecast has the same shape within the day as the history. With more samples a high percentile becomes steadier.

These numbers are computed by the real code in pkg/forecast/docs_examples_test.go and checked on every test run.

Tuning and tradeoffs

bucket_minutes must divide 1440; smaller buckets need more history. utc_offset_minutes=480 groups by UTC+8. It is a fixed offset, not automatic daylight-saving handling.

Sources and references

  • The recommender of the Kubernetes Vertical Pod Autoscaler (VPA): a decayed histogram and a target percentile. The vertical-pod-autoscaler directory of kubernetes/autoscaler.
  • Rzadca, K. et al. "Autopilot: Workload Autoscaling at Google", EuroSys 2020: Google's Autopilot, also decayed percentile recommendations, comparing several recommenders.
  • "Adding a clock" (buckets by weekday and part of the day) is this platform's extension of those recommenders, not what the VPA or the Autopilot paper does; its relation to hist_percentile is that it falls back to it when the buckets do not have enough.

Use in a module

  1. Save parameters and check history, sample interval, and horizon.
  2. Enable module prediction. Fixed mode runs the selected method; dynamic mode uses centrally enabled methods.
  3. Run rolling backtests and earn version promotion before adoption. Re-run backtests after changes affecting model identity.
  4. Review error, peak underestimation, runtime, and adoption reasons in Observe or Recommend before separately authorizing admission and replica actions.

For insufficient history, invalid settings, timeouts, or invalid output, inspect run reasons. Without eligible forecasts, the module follows its schedules, fallback, and protection rules.
