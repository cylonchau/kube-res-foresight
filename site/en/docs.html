01Overview

kube-resource-fcst is a resource forecasting and scaling platform for a single Kubernetes cluster. It reads historical and current metrics from Prometheus, compares multiple forecasting methods through rolling backtests and actual results, and produces CPU, memory, and replica recommendations.

Use the platform to understand recurring demand, compare models, review recommendations, and gradually authorize changes. Its capabilities cover data sources, workload modules, models, forecasts, recommendations, execution history, monitoring, access control, and scheduled tasks.

One module describes one workload

A module connects a workload to its metric sources, thresholds, history window, forecast interval, replica bounds, schedules, and fallback values. Model settings are managed centrally and enabled models automatically participate across modules.

Metrics→Forecasts / backtests→Recommendations→Admission / scaling→Actual results
Read observations, estimates, forecasts, and outcomes separately

Metrics are observations. Historical capacity is an estimate. Future demand is a forecast. Applied changes and Ready replicas are execution outcomes. Review each when deciding whether capacity is sufficient.

02Get started

Start with the demo to learn how data becomes forecasts, recommendations, and evaluations. Then connect a workload in Observe mode.

1. Explore a demo module

Create the demo from the data-source pages. The platform prepares example metrics and a module. Explore history, forecasts, backtests, and advice to understand how the pages connect. Demo values are illustrative.

2. Connect your metrics

Add a Prometheus data source and check the connection. Map CPU, memory, request volume, and other metrics. Confirm workload scope, units, history, and gaps.

3. Create a workload module

Select a namespace and workload. Connect metric sources and thresholds, then set the forecast interval, resource bounds, replica limits, schedules, and fallback values. Enabled models are configured centrally.

4. Compare predictions and review advice

Run collection, forecasting, and rolling backtests. Review errors, peak underestimation, scores, and rankings. In Recommend mode, inspect resource advice, decisive constraints, sources, and fallback reasons. Evaluate against actuals as target times arrive.

5. Gradually enable actions

Review admission and scaling policies, permissions, bounds, and fallback behavior before authorizing each mode. Continue monitoring actual replicas, Ready capacity, and resource use.

Before enabling changes

Confirm the connection, metric meanings, sufficient history, comparable backtests, understandable recommendations, and appropriate fallback values. Admission and Auto are disabled by global settings by default.

Need to install the platform? View build and startup instructions

Prepare the tools

Use the Go toolchain declared by go.mod (currently 1.27.0) and the Node.js / pnpm versions specified by the admin frontend. The web/ frontend is a separate Git repository; prepare it before building the embedded UI.

BASH / REPOSITORY ROOT
cd web
pnpm install --frozen-lockfile
cd ..
make package-web
mkdir -p target/bin
go build -o target/bin/kube-resource-fcst ./cmd

Configure and start

Set the database, server address, and logging in config.yaml. The example uses SQLite and port 20001. Keep JWT and credential-encryption keys secure and stable, including KUBE_RESOURCE_FCST_SECRET_KEY.

BASH / FIRST INSTALLATION
# First installation: migrate and start the server
target/bin/kube-resource-fcst server --config config.yaml --migration

# Stop the server above, then run the API and job engine together
target/bin/kube-resource-fcst all --config config.yaml

Open http://localhost:20001. The server and job commands can also run separately. For an existing installation, back up the database before using --upgrade, which removes retired module tables. Normal startup does not perform that cleanup. Use Git Bash on Windows and an .exe executable name.

How do modules, metrics, and models relate?

A module defines the workload and its limits. Metrics define the inputs and their meaning. Models define the prediction methods, configured centrally and applied to modules. Together they determine the inputs, candidates, and resulting recommendations.

A typical operating cycle

  1. Configure: choose a workload and set inputs, bounds, schedules, fallback, and mode.
  2. Observe: inspect trends, gaps, and freshness.
  3. Compare: review predictions, backtests, and actual scores against adoption criteria.
  4. Recommend: inspect CPU, memory, and replica advice and its decisive constraints.
  5. Act and review: authorize changes and feed actual behavior into the next evaluation.

Common scenarios

  • Capacity observation: use Observe or Recommend to compare recurring demand with current resources.
  • Scheduled resource guarantees: configure fixed values for a business window, including timezone, fields, and limits.
  • Gradual scaling: start with a noncritical workload, review cooldowns and Ready capacity, then expand use.

04Data and quality

Metric mappings define queries and workload scope. Datasets define sampling, aggregation, precision, conversion, and missing-data handling. A module can use CPU, memory, requests, OOM, JVM, and other metrics with their own thresholds.

Five things to check

  • Scope: namespace, workload, and container labels must select the intended series.
  • Meaning: distinguish workload-wide request rate from per-Pod throughput, and configured requests / limits from actual use.
  • Units: align CPU cores, millicores, bytes, and MiB before comparing values.
  • Time: history length, sampling interval, forecast horizon, and freshness must fit model requirements.
  • Quality: review coverage, gaps, invalid values, and degradation thresholds. Insufficient inputs should lead to skipping or fallback.

Built-in PromQL presets are a starting point. Cluster labels differ; when a query returns no data, inspect its labels and filters against the available series.

Times are stored in UTC. Schedules use an explicit IANA timezone, and displayed times follow the configured setting.

05Models and forecasts

The platform includes 14 built-in algorithms. Manage activation, parameters, weights, and adoption thresholds centrally. Enabled candidates participate automatically; a model name alone does not determine whether it suits your workload.

Central settings and custom models

Administrators can create derived models from built-in methods or formula models with numeric and boolean parameters. Formulas are evaluated before saving. Parameter and implementation changes affect version identity and promotion eligibility.

What should you review?

  • Check sample requirements and reasons for skipped or degraded runs.
  • Align history, forecast intervals, and horizon with resource preparation time.
  • Compare backtests, actual errors, and peak underestimation against adoption thresholds.
  • Recheck eligibility after changing parameters.

Models that support additional metrics can use their past values as covariates. Backtests must respect each prediction origin and never use real future values.

06Evaluation and model selection

Rolling backtests move through history in time order. Training data stays before each forecast origin; actual observations are linked to predictions as their target times arrive. Use windows and horizons that match your operating decisions.

MeasureMeaningHow to read it
WAPETotal absolute error relative to total absolute actual valuesCompare the same inputs and window; zero denominators follow the platform rule
Peak underestimationRisk of forecasting less than peak demandLower average error can still hide peak risk
Scores and rankingsResource accuracy, OOM penalties, completeness, and configured weightsReview component scores and model eligibility together
Actual evaluationComparison with observations at forecast target timesFuture targets without actuals do not have zero error

Adoption also depends on promotion, minimum score, freshness, and switching hysteresis. A leading rank does not cause an immediate switch. Current and historical rankings, score details, and training records explain the selection.

Performance varies with workload patterns, data quality, and horizon. Use your own data to review error, peaks, and resource outcomes before adjusting policy.

07Recommendations and actions

Resource and replica advice answer different questions

Fixed replica calculation combines peak demand, headroom, and per-Pod capacity. Dynamic calculation considers throughput, CPU, memory, and JVM heap pressure. Recommendations incorporate bounds, smoothing, and peak underestimation. Historical capacity estimates need to be compared with workload load tests.

Apply replica advice through controlled scaling

Configure minimum and maximum replicas, per-direction step limits, and cooldowns in the module. After Auto mode is authorized, the Operator applies valid advice. Review desired, current, and Ready replicas together with pause or failure reasons.

Use platform module settings for day-to-day management, or PredictiveScaler for declarative configuration. One workload must have only one replica controller; do not use competing HPA, KEDA, or duplicate scalers.

Apply resources to new Pods

Admission reads the latest valid recommendation to adjust CPU / memory requests and configured limits ratios. Inspect admission records for results and reasons. Missing modules, unavailable advice, or an unreachable platform should preserve original resources and allow deployment.

Admission affects new Pods. Running Pods receive new resource settings through creation or rolling updates. Lowering memory limits needs separate risk assessment and authorization.

08Safety and fallback

Recommendations must be fresh and valid, within configured limits, and authorized for the selected mode. Data or model failures lead to recorded degradation. Enable module bypass when manual intervention is needed.

SafeguardBehavior
Gradual modesObserve → Recommend → Admission → Auto, gated by module mode and global authorization
Global settingsAdmission and automatic scaling are off by default. Disabling them stops subsequent application after a short settings cache delay
Module bypassPreserves original values and records the reason
Per-field fallbackBypass → schedule → eligible model → module fallback → unchanged, with safety checks on each value
OOM protectionThe OOM floor applies outside bypass, remains within module bounds, and includes an explanation
Recovery hysteresisRequires consecutive healthy cycles before leaving degradation
Scaling limitsHard bounds, steps, and cooldowns constrain changes; missing or stale decisions stop dangerous actions

When you need to stop automatic changes

  1. Enable Bypass for the module and record a reason.
  2. Disable the corresponding global setting and return to Recommend or Observe.
  3. Review snapshots, admission decisions, scaling reports, and actual state.
  4. Fix the inputs or policy, rerun backtests, then restore authorization gradually.

Bypass and global settings stop future actions. They do not undo earlier resource or replica changes; restoration should consider current service conditions.

09Monitoring and administration

Monitoring shows whether the workflow is running. Tasks, access control, and audit explain why advice changed and who changed the configuration.

Monitoring: locate where the workflow is waiting

Compare history, forecasts, and actuals. Inspect data-source status, recommendation age, model performance, and fallback. Desired, current, and Ready replicas distinguish a submitted change from available capacity. Use curves and exported data to review outcomes.

Task center: inspect recurring work

Review task definitions, schedules, and execution records for collection, prediction, backtesting, and evaluation. Check errors and inputs before retrying. A completed task does not guarantee fresh data or suitable recommendations.

Permissions and settings: control who changes policies

Users, roles, menu permissions, and API permissions define access. Global settings control platform defaults and safety gates; model and module pages hold their respective policies. LDAP connection, user/group lookup, and role mapping are available under System → System parameters → LDAP. Local accounts remain an emergency access path.

Audit: explain each change

QuestionWhere to look
Why was this model selected?Backtests, actual scores, rankings, and training records
Why is this the recommended value?Snapshot sources, decisive constraints, and fallback reasons
Was it applied, and what happened?Scaling reports, admission decisions, and actual / Ready replicas

Retention and exports

Set retention according to review needs for metric history, forecasts, evaluations, recommendations, actions, and logs. Audit exports support offline review and are logged. Protect credentials and grant API access by purpose with minimal permissions.

Deployment references and external monitoring

Deploy the platform separately with the required database, certificates, keys, and cluster permissions. Back up the database and stable credential-encryption key.

Configure metric listening to expose /metrics, /healthz, and /readyz for external monitoring.

10Scope and usage boundaries

Choose data sources and operating modes with the management scope and effects of each action in mind.

ScopeUsage guidance
Single clusterManage forecasting and resource policies for workloads in one Kubernetes cluster. Cross-cluster migration and multicloud scheduling are outside this scope.
Capacity estimatesHistorical per-Pod capacity is an estimate, not a measured maximum. Set bounds using workload load tests and SLOs.
Resource changesAdmission affects new Pods; the Operator adjusts replica counts. Authorize each separately.
Replica ownershipKeep one replica controller per workload. Stop the previous controller before switching.
Memory safetyReview OOM behavior, peaks, and resource bounds. Separately assess and authorize memory-limit reductions.
Forecasts and readinessSeparate future demand, desired replicas, and actual Ready capacity. Allow for metric collection and Pod startup time.

11Common questions

Can I use this website as the management console?

This website explains capabilities and usage. Deploy the management console separately to connect data sources, manage models and modules, inspect results, and authorize actions.

Can HPA or KEDA control the same workload?

No. A workload must have one replica controller. Stop the previous controller and release ownership before switching.

How should I choose a forecasting model?

Start with a baseline. Compare error, peak underestimation, and runtime over the same history and forecast horizon. Set adoption thresholds for your workload and resource budget, then continue evaluating against actual results.

Why are forecasts or rankings missing?

Check the source connection, PromQL labels, units, module activation, history window, and minimum samples. Then inspect tasks, freshness, target times, and eligibility. Actual comparisons require observations at the forecast target time.
