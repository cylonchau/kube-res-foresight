USER GUIDE

Naive

Repeats the latest observation across the horizon. Use it as a basic comparison and to check the data workflow; it cannot anticipate cycles or sudden changes.

← Models and prediction modes

Purpose and workload fit

Repeats the latest observation across the horizon. Use it as a basic comparison and to check the data workflow; it cannot anticipate cycles or sudden changes.

History and runtime requirements

At least one valid observation.

Inputs must be regularly sampled, gap-free, and finite. Outputs retain the metric unit, such as CPU cores, memory bytes, or requests per second. The sample interval determines the duration of a step. Minimum history permits execution; it does not establish forecast quality.

This method does not use covariates; target metrics are forecast separately.

How it works and the formula

The naive forecast (also called the random-walk forecast) does one thing: it takes the last observed value as the forecast for every future step.

Formula
ŷ(T+h) = y(T)        h = 1, 2, …, H

y(T) is the newest value of the history, H the number of steps to forecast and h the step ahead. There are no parameters and nothing is trained.

Why it is done this way: over minutes to tens of minutes a resource load is usually sticky: the likeliest next value is the current one, so this simplest forecast is often hard to beat over a short range. The platform uses it as the baseline: any more complex algorithm has to beat it in the backtest before it may be adopted. It also checks the collection and forecast chain (its curve should hug the actual values, one step late).

What it cannot do: it sees no cycle and no coming rise or fall. When the load changes, it follows one forecast cycle late.

Parameter reference

No method-specific parameters; the parameter object is {}.

Worked example: data, parameters and substitution

Suppose the last 4 samples (one every 5 minutes) of the CPU usage of a service are as follows, in cores. We forecast the next 3 steps (15 minutes).

Data
y = [0.8, 1.0, 1.2, 1.1]      (the newest is the last one, 1.1)

Substituting into the formula:

Calculation
ŷ(T+1) = y(T) = 1.1
ŷ(T+2) = y(T) = 1.1
ŷ(T+3) = y(T) = 1.1

The result is [1.1, 1.1, 1.1]: a horizontal line at the last observed value. The earlier 0.8, 1.0 and 1.2 play no part.

These numbers are computed by the real code in pkg/forecast/docs_examples_test.go and checked on every test run: if the algorithm changes and no longer matches this page, the test fails.

Tuning and tradeoffs

There are no algorithm parameters. Compare EWMA, Theta, or Seasonal Naive when trend or seasonality matters.

Sources and references

  • Hyndman, R.J. & Athanasopoulos, G. Forecasting: Principles and Practice (3rd ed., OTexts, 2021), section 5.2 "Some simple forecasting methods", the Naïve method: https://otexts.com/fpp3/simple-methods.html.
  • Using it as the baseline of every candidate is the general practice in forecast evaluation: a new method means something only when it beats the naïve forecast (same book, section 5.8 on evaluating forecast accuracy).

Use in a module

  1. Save parameters and check history, sample interval, and horizon.
  2. Enable module prediction. Fixed mode runs the selected method; dynamic mode uses centrally enabled methods.
  3. This baseline does not need backtest promotion, but actual performance still needs review.
  4. Review error, peak underestimation, runtime, and adoption reasons in Observe or Recommend before separately authorizing admission and replica actions.

For insufficient history, invalid settings, timeouts, or invalid output, inspect run reasons. Without eligible forecasts, the module follows its schedules, fallback, and protection rules.
