USER GUIDE

Random Forest

Fits and averages regression trees on sampled historical features, supporting nonlinear relationships and covariates. More costly than simple statistical methods.

← Models and prediction modes

Purpose and workload fit

Fits and averages regression trees on sampled historical features, supporting nonlinear relationships and covariates. More costly than simple statistical methods.

History and runtime requirements

At least lags + 4×min_samples_leaf + 1 observations; the training window must retain enough samples.

Inputs must be regularly sampled, gap-free, and finite. Outputs retain the metric unit, such as CPU cores, memory bytes, or requests per second. The sample interval determines the duration of a step. Minimum history permits execution; it does not establish forecast quality.

Supports covariates on the same sample grid, using only observations before the forecast origin. Future covariates carry the last observed value; future business demand is not assumed known.

How it works and the formula

A random forest is the average of many regression trees. Each tree sees a random sample of the training rows and a random subset of the features, so no tree is perfect, but they make different mistakes and their average is steadier than one tree. The features are the previous values, optional calendar features and covariates; the forecast rolls forward recursively.

Formula
features:  x(t) = [ y(t−1), …, y(t−L) ] (+ calendar sin/cos, + covariate lags)            L = lags
for each tree b = 1 … B (B = n_estimators):
  1) draw sample_ratio × the number of rows from the training rows, with replacement (bootstrap)
  2) draw feature_ratio × the number of features at random; this tree may split only on them
  3) split recursively on the drawn rows: bin each feature into 32 bins and pick the (feature, bin edge) with the largest "variance reduction",
       gain = (ΣL)²/nL + (ΣR)²/nR − (Σ)²/n          Σ is the sum of the targets on that side, n the number of rows
     until the depth reaches max_depth or a side has fewer than min_samples_leaf rows; a leaf's value = the mean of the targets in it
forecast:  ŷ(t) = (1/B) · Σ tree_b( x(t) )
several steps: the forecast is used as the lag of the next step, rolling forward recursively

How the parameters enter the formula:

  • lags (L): how many previous steps are features; required.
  • n_estimators (B): the number of trees. More is steadier and slower (default 50).
  • max_depth: the maximum depth of a tree (default 6). Deeper fits more complex relations and memorises noise more easily.
  • min_samples_leaf: the fewest rows in a leaf (default 5). Larger is smoother. The least history = lags + 4×min_samples_leaf + 1.
  • feature_ratio, sample_ratio: the share of the features and the share of the rows (with replacement) each tree uses. Smaller shares make the trees more different.
  • seed: the random seed. With a fixed seed the same history and parameters always give the same forecast (reproducible).
  • calendar_features, covariate_lags, training_window_steps: as in ridge autoregression.

Why it is done this way: trees can fit non-linear relations (for example "when the previous step is below some value the next one recovers") with no linearity assumption, and do not mind features of different scales. Averaging many trees offsets the overfitting of a single one.

The key limit: a tree model cannot extrapolate. A leaf's value is the mean of training targets, so a forecast always lies inside the range of the training targets. When the load keeps rising to a height the history has never shown, it does not forecast higher. That is why the platform requires it to beat the baseline in the backtest before it is adopted, and why it suits a load that swings within a range better than one that is growing.

Configuration example

Edit parameters in Algorithm management. This is a parameter object, not a complete config.yaml. Seasonal examples assume five-minute sampling; adjust for your actual interval. Omitted optional values use the defaults above.

JSON
{
  "lags": 24,
  "n_estimators": 50,
  "max_depth": 6,
  "min_samples_leaf": 5,
  "training_window_steps": 2000,
  "seed": 42
}

Worked example: data, parameters and substitution

To see "cannot extrapolate", take the simplest "always rising" series: one point every 5 minutes, from 10 up to 29 (adding 1 per step), 20 points.

JSON
{
  "lags": 2,
  "n_estimators": 20,
  "max_depth": 3,
  "min_samples_leaf": 2,
  "feature_ratio": 1,
  "sample_ratio": 1,
  "seed": 42
}
Data
y = [10, 11, 12, …, 28, 29]        n = 20; training rows: features [y(t−1), y(t−2)], target y(t), 18 rows, the targets range over 12 … 29

"Adding 1 per step", everyone knows the next values should be 30, 31, 32. The random forest gives:

Result
ŷ = [27.9125, 27.9125, 27.9125]

All three forecasts are below the largest value of the history, 29, and they form a flat line. Why:

  • For step 1 the features [29, 28] fall into the leaf on the "largest feature value" side of each tree; the value of that leaf is the mean of its training targets, and the largest training target is 29, so the forecast cannot be above 29.
  • That forecast of 27.9 is then used as the lag of the next step, falls into the same leaf, and the later steps stay at 27.9.

For comparison, a linear model (ridge autoregression) on the same data (with its default parameters) forecasts about 29.95, 30.92 and 31.88, going on up. So on a growing load, mind that a tree model comes out low; it wins when the load swings around a range and the relation is non-linear.

How one split inside the forest is chosen is shown step by step (base value, residuals, the gain of the split, the leaf values) in the example of the GBDT page; the trees of a random forest use the same splitting rule, fitted to the targets themselves instead of residuals, and every tree splits only on its sampled rows and features.

These numbers are computed by the real code in pkg/forecast/docs_examples_test.go and checked on every test run (the random seed is fixed at 42, so the result is reproducible).

Tuning and tradeoffs

Start with bounded tree count, depth, and training window. More trees cost more; deeper trees can fit noise. Keep the seed fixed for reproducible comparisons against Ridge AR and baselines.

Sources and references

  • Breiman, L. "Random Forests", Machine Learning 45(1), 2001, 5–32: the original paper.
  • Breiman, L. "Bagging predictors", Machine Learning 24(2), 1996, 123–140: bootstrap sampling and averaging (bagging).
  • Breiman, L., Friedman, J.H., Olshen, R.A., Stone, C.J. Classification and Regression Trees (Wadsworth, 1984): regression trees and the variance-reduction split criterion.
  • Using lags as features and forecasting recursively is the common way to forecast a time series with a regression model; the limit that a tree model cannot extrapolate is shown with real numbers in the example above.

quantile_level uses a 0–1 scale; percentile uses 1–100. Calibration runs extra historical forecasts. Check history and runtime budgets before increasing windows; coverage is an evaluation target, not a guarantee.

Use in a module

  1. Save parameters and check history, sample interval, and horizon.
  2. Enable module prediction. Fixed mode runs the selected method; dynamic mode uses centrally enabled methods.
  3. Run rolling backtests and earn version promotion before adoption. Re-run backtests after changes affecting model identity.
  4. Review error, peak underestimation, runtime, and adoption reasons in Observe or Recommend before separately authorizing admission and replica actions.

For insufficient history, invalid settings, timeouts, or invalid output, inspect run reasons. Without eligible forecasts, the module follows its schedules, fallback, and protection rules.
