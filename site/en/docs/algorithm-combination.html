USER GUIDE

Combination

Combines member forecasts using a stepwise median or recent-error weights. The combination must earn backtest promotion like other candidates.

← Models and prediction modes

Purpose and workload fit

Combines member forecasts using a stepwise median or recent-error weights. The combination must earn backtest promotion like other candidates.

History and runtime requirements

At least one member must have enough history; unavailable members are omitted. Error weighting adds historical forecast windows, so requirements grow with members and horizon.

Inputs must be regularly sampled, gap-free, and finite. Outputs retain the metric unit, such as CPU cores, memory bytes, or requests per second. The sample interval determines the duration of a step. Minimum history permits execution; it does not establish forecast quality.

This method does not use covariates; target metrics are forecast separately.

How it works and the formula

A combination puts several different algorithms together: for each step it takes the median of their forecasts, or an average weighted by how well each did lately. A member that is wrong in one way is outvoted by the others; it needs no training.

Formula
members:   f(k)(h) = the forecast of member k for step h (every member runs with its own default parameters on the same history)

mode = median:         ŷ(h) = the median of the member forecasts f(k)(h)

mode = inverse_error:  ŷ(h) = Σ w(k) · f(k)(h) / Σ w(k)
  member error e(k):  cut the history at the last error_windows "forecast ranges", let the member forecast again and compare with the actual,
                      add the newest recent_steps steps; take the mean absolute error, a shortfall (a forecast below the actual) counted under_weight times
  eps  = 0.001 × the mean absolute value of the history + 10⁻¹²            (so a member that was exactly right does not take all the weight)
  trim:   a member with e(k) > trim_ratio × min(e) + eps gets weight 0
  weight: w(k) = ( 1 / (e(k) + eps) ) ^ sharpness

How the parameters enter the formula:

  • members: the algorithm ids of the members, 2 to 6, comma separated (default ewma,holt_winters,theta). Members run with default parameters, so only an algorithm that needs no required parameter can be a member (ewma, holt_winters, theta, hist_percentile, naive, knn and the like); a combination cannot be a member of itself, nor repeat one. A member that needs more history than there is is left out of that forecast.
  • mode: inverse_error (weighted by error, default) or median.
  • error_windows (default 4): how many forecast ranges the member errors are measured over.
  • under_weight (default 2): how many times a member's error counts when it forecast below the actual. It follows the way the platform grades an algorithm: a shortfall of a resource is worse than a surplus.
  • sharpness (default 2): the power of the inverse error that is the weight. Larger leans more on the member that was lately most accurate.
  • trim_ratio (default 3): members whose error exceeds 3 times the best one's are left out; 0 leaves none out.
  • recent_steps (default 3): also weigh in the newest steps, so a member that has just followed a change counts for more than one that was right an hour ago.

Why it is done this way: the conclusion of the forecasting competition M4 is that a combination of unlike models is hard to beat for any single model. A member wrong in one pattern is pulled back by the others, and it costs almost no training. Weighting by recent error makes the combination lean on the member that has lately been right instead of averaging in one that has lately been wrong.

Mind: a combination is an algorithm like any other: it is backtested, scored and promoted, and is not adopted by default because it is "several algorithms put together". Members do not read the values set on their own algorithm pages; they use default parameters only.

Configuration example

Edit parameters in Algorithm management. This is a parameter object, not a complete config.yaml. Seasonal examples assume five-minute sampling; adjust for your actual interval. Omitted optional values use the defaults above.

JSON
{
  "members": "ewma,holt_winters,theta",
  "mode": "inverse_error",
  "error_windows": 4,
  "under_weight": 2,
  "sharpness": 2,
  "recent_steps": 3,
  "trim_ratio": 3
}

Worked example: data, parameters and substitution

The three default members ewma, holt_winters and theta, weighted by error (every parameter at its default). The data is a slowly rising load with a little wiggle, one point every 5 minutes, 30 points; forecast 3 steps.

JSON
{
  "members": "ewma,holt_winters,theta",
  "mode": "inverse_error",
  "error_windows": 4,
  "under_weight": 2,
  "sharpness": 2,
  "recent_steps": 3,
  "trim_ratio": 3
}
Data
y(i) = 50 + 0.8·i + 3·sin(i)        i = 0 … 29        (mean absolute value 61.7268)

Step 1, the forecast of each member:

memberh=1h=2h=3
ewma71.367871.367871.3678
holt_winters72.316673.120473.9242
theta71.603271.997272.3913

ewma is a flat line, the other two carry a trend.

Step 2, the recent error of each member (backtested by the rules above, a shortfall counted twice):

membererror e
ewma6.5656
holt_winters3.4951
theta3.8190

On a rising load ewma, with no trend, lags and has the largest error.

Step 3, the weights. eps = 0.001 × 61.7268 = 0.0617. The trim line = 3 × 3.4951 + 0.0617 = 10.55; all three errors are below it, so all stay. w = (1/(e + eps))²:

memberweight wshare
ewma(1/6.6273)² = 0.0227713.5%
holt_winters(1/3.5568)² = 0.0790547.0%
theta(1/3.8807)² = 0.0664039.5%

Step 4, the weighted average (step 1 as the example):

Calculation
ŷ(T+1) = (0.02277×71.3678 + 0.07905×72.3166 + 0.06640×71.6032) / (0.02277 + 0.07905 + 0.06640)
       = 71.9065

The three steps give [71.9065, 72.4398, 72.9731], between the lowest (ewma) and the highest (holt_winters), but nearer to holt_winters and theta, which were lately the most accurate.

With mode set to median each step takes the median of the three members: [71.6032, 71.9972, 72.3913] (all theta's values, because theta happens to be in the middle).

These numbers are computed by the real code in pkg/forecast/docs_examples_test.go and checked on every test run.

Tuning and tradeoffs

members contains 2–6 comma-separated IDs that can be built with defaults, excluding combination. Members do not inherit saved settings from model management. Higher under_weight penalizes underestimation; higher sharpness concentrates weight on stronger members.

Sources and references

  • Bates, J.M. & Granger, C.W.J. "The combination of forecasts", Operational Research Quarterly 20(4), 1969, 451–468: the pioneering paper on forecast combination; the idea of weights from the inverse of the forecast errors comes from here.
  • Makridakis, S., Spiliotis, E., Assimakopoulos, V. "The M4 Competition: 100,000 time series and 61 forecast methods", International Journal of Forecasting 36(1), 2020, 54–74: combination methods did best in the M4 competition.
  • Timmermann, A. "Forecast combinations", Handbook of Economic Forecasting vol. 1, 2006, 135–196: a survey of forecast combination.
  • "A shortfall counted under_weight times", "members with more than 3 times the best error left out" and "the newest steps weighed in" are this platform's additions, to agree with the way algorithms are graded and to follow a change faster; they are not in the papers above.

quantile_level uses a 0–1 scale; percentile uses 1–100. Calibration runs extra historical forecasts. Check history and runtime budgets before increasing windows; coverage is an evaluation target, not a guarantee.

Use in a module

  1. Save parameters and check history, sample interval, and horizon.
  2. Enable module prediction. Fixed mode runs the selected method; dynamic mode uses centrally enabled methods.
  3. Run rolling backtests and earn version promotion before adoption. Re-run backtests after changes affecting model identity.
  4. Review error, peak underestimation, runtime, and adoption reasons in Observe or Recommend before separately authorizing admission and replica actions.

For insufficient history, invalid settings, timeouts, or invalid output, inspect run reasons. Without eligible forecasts, the module follows its schedules, fallback, and protection rules.
