USER GUIDE

MSTL

Separates daily and weekly seasonal shapes and applies Theta to the remainder. This implementation iterates fixed seasonal shapes rather than time-varying LOESS components.

← Models and prediction modes

Purpose and workload fit

Separates daily and weekly seasonal shapes and applies Theta to the remainder. This implementation iterates fixed seasonal shapes rather than time-varying LOESS components.

History and runtime requirements

At least twice the longest cycle. Five-minute daily seasonality needs 576 observations; adding weekly seasonality needs 4032, or two weeks.

Inputs must be regularly sampled, gap-free, and finite. Outputs retain the metric unit, such as CPU cores, memory bytes, or requests per second. The sample interval determines the duration of a step. Minimum history permits execution; it does not establish forecast quality.

This method does not use covariates; target metrics are forecast separately.

How it works and the formula

MSTL (multiple seasonal-trend decomposition) is for a load that has a "daily cycle" and a "weekly cycle" at once. It splits the series into a trend and one seasonal shape per cycle, sets the seasonal shapes aside, forecasts what is left (trend plus noise) with Theta, and adds the seasonal shapes back.

Formula
decomposition:  y(t) = trend(t) + S_day(t mod day) + S_week(t mod week) + remainder(t)
forecast:       ŷ(T+h) = Theta( y − S_day − S_week )(h) + S_day((T+h) mod day) + S_week((T+h) mod week)
                a forecast below 0 is cut to 0

each seasonal shape S is estimated (repeated 3 times so the shapes agree with each other):
  r(t)  = y(t) − trend(t) − the shapes of the other cycles
  S(pos) = the mean of r over all cycles at position pos, then the overall mean is subtracted (the shape averages 0)
  trend  = the centred moving average, over a window of the longest cycle, of what is left after the seasonal parts

How the parameters enter the formula:

  • daily_season_steps: steps in a day (the shorter cycle). 5-minute samples = 288.
  • weekly_season_steps: steps in a week, must be longer than the daily one; 5-minute samples = 2016. 0 means a daily cycle only.
  • The least history = 2 × the longest cycle (two full cycles at least, otherwise a position has been seen once and cannot be told from noise).

Why it is done this way: a real business load is often "high on weekday daytimes, low at night, and lower as a whole at the weekend"; a one-cycle seasonal algorithm catches only one of these. Estimating the two cycles apart and adding them back expresses "which hours of the day are high" and "which days of the week are high" together.

Difference from the paper: the STL of the paper smooths every seasonal shape with LOESS so a shape may change slowly; here every shape is fixed: the mean of that position over all cycles of the history (after the trend and the other cycles are removed). It is cheap and needs no tuning, but a shape that changes within the history is averaged, not followed.

Configuration example

Edit parameters in Algorithm management. This is a parameter object, not a complete config.yaml. Seasonal examples assume five-minute sampling; adjust for your actual interval. Omitted optional values use the defaults above.

JSON
{
  "daily_season_steps": 288,
  "weekly_season_steps": 2016
}

Worked example: data, parameters and substitution

To keep it readable we use a "mini day" of 4 steps, no weekly cycle and 3 cycles (12 points). The data is constructed: a base of 10, rising by 0.5 per step, plus the seasonal shape [−2, 0, +3, −1].

JSON
{
  "daily_season_steps": 4,
  "weekly_season_steps": 0
}
Data
y = [8, 10.5, 14, 10.5,   10, 12.5, 16, 12.5,   12, 14.5, 18, 14.5]
    └─ 1st cycle ─┘        └─ 2nd cycle ─┘        └─ 3rd cycle ─┘

Step 1, estimate the seasonal shape. After removing the trend the algorithm averages the 3 values of each position and makes the overall mean 0, repeated 3 times. The shape it gets is

Result
S_day = [−2.1913, −0.0491, +3.0693, −0.8289]        (averages 0)

It is close to the [−2, 0, +3, −1] used to build the data; the difference comes from the rising trend and the edge effect of the centred moving average at the two ends of the series.

Step 2, forecast the seasonally adjusted series with Theta (it is roughly a line rising 0.5 per step). For step 1 the base forecast is 13.3812 − (−2.1913) = 15.5725.

Step 3, add the shape back. The next position is 12 mod 4 = 0, so:

Calculation
ŷ(T+1) = base forecast + S_day[0] = 15.5725 + (−2.1913) = 13.3812
ŷ(T+2) = …                + S_day[1]                     = 15.7672
ŷ(T+3) = …                + S_day[2]                     = 19.1292
ŷ(T+4) = …                + S_day[3]                     = 15.4747

The result [13.3812, 15.7672, 19.1292, 15.4747] is a "waveform on a rise": the high and low order of the four points follows the seasonal shape.

One limit to see: the "truth" of the constructed data (the base keeps rising 0.5 per step) would be [14, 16.5, 20, 16.5], and the forecast is a little lower (by about 0.6 to 1.0), because Theta takes half of the trend. That is a property of Theta as the base forecast: on a steadily rising load it is on the low side.

These numbers are computed by the real code in pkg/forecast/docs_examples_test.go and checked on every test run.

Tuning and tradeoffs

Configure daily_season_steps first. weekly_season_steps=0 disables weekly seasonality. A weekly season must exceed the daily season; insufficient history is not padded.

Sources and references

  • Bandara, K., Hyndman, R.J., Bergmeir, C. "MSTL: A Seasonal-Trend Decomposition Algorithm for Time Series with Multiple Seasonal Patterns", 2021, arXiv:2107.13462: the multiple-season decomposition and forecasting with it.
  • Cleveland, R.B., Cleveland, W.S., McRae, J.E., Terpenning, I. "STL: A seasonal-trend decomposition procedure based on Loess", Journal of Official Statistics 6(1), 1990, 3–73: the single-season STL MSTL builds on.
  • Theta as the base forecast: see the Theta page of this site.
  • The difference from the paper is stated above ("Difference from the paper"): the seasonal shapes here are fixed (the mean of all cycles), no LOESS.

Shared parameters: shifts and quantiles

Parameter / typeDefault / range / unitMeaning and use
reset_on_change
bool		false
No additional range		Use history after a detected level shift, preserving enough points for the underlying method.
change_threshold
float		8
≥ 3; ≤ 50		Minimum shift relative to robust noise; used only with reset_on_change.
change_min_shift
float		0.2
≥ 0; ≤ 5		Minimum relative level shift; 0.2 means 20%. Used only with reset_on_change.
quantile_level
float		0
≥ 0; ≤ 0.99		Zero disables conformal calibration; otherwise must be above 0.5 and at most 0.99. Calibrates an upper forecast using earlier forecast errors.
calibration_windows
int		8
≥ 3; ≤ 50		Historical windows for conformal calibration; more windows add forecast calls and history requirements.

quantile_level uses a 0–1 scale; percentile uses 1–100. Calibration runs extra historical forecasts. Check history and runtime budgets before increasing windows; coverage is an evaluation target, not a guarantee.

Use in a module

  1. Save parameters and check history, sample interval, and horizon.
  2. Enable module prediction. Fixed mode runs the selected method; dynamic mode uses centrally enabled methods.
  3. Run rolling backtests and earn version promotion before adoption. Re-run backtests after changes affecting model identity.
  4. Review error, peak underestimation, runtime, and adoption reasons in Observe or Recommend before separately authorizing admission and replica actions.

For insufficient history, invalid settings, timeouts, or invalid output, inspect run reasons. Without eligible forecasts, the module follows its schedules, fallback, and protection rules.
