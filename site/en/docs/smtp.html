USER GUIDE

Email (SMTP) setup

Set the mail server, the encryption and the sender, fill it in for common mail services, send a test mail first and read the errors.

What the email channel is and who uses it

The email channel lets the platform send mail to given addresses through an SMTP server. What uses it today is the AI scheduled tasks: a task has a model answer on a schedule and mails the answer to its recipients. The channel only hands a message to an SMTP server and knows nothing about the content; when it is not set up, a task run fails and the task center says why, so no mail is lost silently.

All of it is set in the Notify category of "System → System parameters"; there is no configuration file. Each item is saved on its own, and a parameter just saved takes effect within 10 seconds. Once it is set, the "Send test mail" button on the same page is the quickest check.

Parameters

ParameterDefaultMeaning
notify.email.hostemptyThe host name or IP of the SMTP server. Empty means the channel is not set up and sending fails at once.
notify.email.port587The port, 1 to 65535. Usual pairs: 587 + starttls, 465 + tls, 25 + none.
notify.email.securitystarttlsHow the connection is encrypted: starttls (connect in clear, then upgrade to encryption), tls (the whole connection is TLS from the start, also called implicit TLS / SMTPS) or none (no encryption).
notify.email.usernameemptyThe account that signs in to the SMTP server. Leave empty when the server needs no sign-in.
notify.email.passwordemptyThe password or app password of the account. Stored encrypted and shown as a mask; sending the mask back keeps the stored value.
notify.email.fromemptyThe sender address, required. It may be reports@example.com or with a display name, "kube-res-foresight <reports@example.com>". A mail service usually requires it to be the sign-in account or an address that account may send as.
notify.email.skip_verifyfalseWhether to skip checking the server certificate. Turn it on, for a while, only for a server with a self-signed certificate; with it on the connection can be impersonated, so do not use it when a trusted certificate is available.
notify.email.timeout_seconds30The time one mail may take from connecting and signing in to being handed to the server, 5 to 300 seconds.

There is no separate "enable" switch: when host, port and from are valid the channel is usable.

Encryption and the password: when the sign-in password is sent

The platform uses the standard SMTP PLAIN sign-in. For safety, the account password is sent only over an encrypted connection, or to a server on this machine; on an unencrypted connection to another host the sign-in is refused instead of sending the password in clear.

securityUsual portProcessAccount and password?
starttls587Connect in clear and greet; the server must announce STARTTLS; then upgrade to TLS, sign in and send. When the server does not support it, it is an error, not a fall back to clear text.Yes (after the upgrade)
tls465TLS from the first byte, then sign in and send.Yes
none25No encryption at all.Only when the server is on this machine; for an internal relay without authentication.

How to fill it in for common mail services

The host names, addresses and passwords below are examples; replace them with your own. Follow the instructions of your mail provider for the details (some need an "app password" or SMTP sign-in allowed in an admin console).

A company mailbox / Microsoft 365 style 587 + STARTTLS

ParameterValue
notify.email.hostsmtp.example.com
notify.email.port587
notify.email.securitystarttls
notify.email.usernamereports@example.com
notify.email.passwordthe password or app password of that account
notify.email.fromkube-res-foresight <reports@example.com>

465 + implicit TLS

The same as the table above, only port becomes 465 and security becomes tls.

An internal relay, no sign-in

ParameterValue
notify.email.hostmail-relay.internal
notify.email.port25
notify.email.securitynone
notify.email.username / passwordempty
notify.email.fromreports@example.com (a sender the relay allows)

With this setup the content of the mail travels in clear text inside the network; use it only on a trusted network.

An internal server with a self-signed certificate

Fill in the port and the encryption the server really uses, then set notify.email.skip_verify to true. This is a stopgap: the certificate is not checked and the connection can be impersonated; for long-term use give the server a trusted certificate.

What the mail looks like

The content is UTF-8 in base64, so a Chinese subject displays properly. When the answer of a task is HTML, the mail carries a plain-text and an HTML version (multipart/alternative): a client that supports HTML shows the version with headings, tables and colours, any other shows the plain text. The platform removes scripts, frames and objects from the HTML, which mail clients do not show anyway. Line breaks in the content are never used to build a mail header.

One mail goes to one recipient; a task with several recipients sends to each on its own, and one failing does not make a recipient that was served get it again.

Send a test mail first

In "System → System parameters" the Notify category has "Send test mail": enter an address and the platform sends a test message with the parameters as saved now. On success it says sent; on failure it shows the words of the mail server, the most useful thing for troubleshooting. A parameter just changed takes effect within 10 seconds, so wait a moment before testing.

Troubleshooting

Message (excerpt)Cause and what to check
the e-mail channel is not set up: the SMTP host (notify.email.host) is emptyThe host is not set.
the SMTP port (notify.email.port) is not validThe port is not between 1 and 65535.
the sender address (notify.email.from) is not set / is not validThe sender is empty or malformed; with a display name write Name <address>.
the security (notify.email.security) is starttls, tls or nonesecurity must be one of these three values.
could not reach the SMTP server host:portCannot connect: the host name, the port, a firewall or an egress network policy. In a container check that the Pod of the platform can reach the address.
the SMTP server did not greetConnected but the server did not greet in SMTP; usually the port and the encryption do not match, for example starttls on 465, which should be tls.
the SMTP server does not offer STARTTLSThe server cannot upgrade to encryption: use the way it supports (tls), or none only when it is an unencrypted internal relay.
STARTTLS failed / certificate errorsThe certificate is not trusted or the name does not match. Check the certificate of the server; a self-signed one may be allowed for a while with skip_verify.
the SMTP server refused the sign-inThe account or the password is wrong, or the server requires an app password or has not allowed SMTP sign-in for that account.
the SMTP server refused the senderThe sender is not allowed: usually it has to be the sign-in account or an address that account may send as.
the SMTP server refused the recipient …The recipient was refused: a wrong address, or the server does not allow sending to external domains (a relay restriction).

When a task run fails the error also appears in the run record of the task center, and a recipient that was already served does not get the mail again on a retry.
