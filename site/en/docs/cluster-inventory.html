USER GUIDE

Cluster dashboard and the Operator report

Declare cluster metrics, tell module metrics from cluster metrics, and see what the Operator reports about the cluster and workloads.

The cluster dashboard: every item is declared first

"Results > Cluster dashboard" shows the nodes, Pods, CPU and memory of a cluster. It has no built-in query: every item it shows must be declared in a "metric template"; an item that is not declared is not queried and no other query stands in for it, and the page lists the metrics still to declare.

  1. Create a metric template with the metric type "cluster metric" and the Prometheus of the cluster as its data source. A preset creates one in a click.
  2. Every Prometheus data source with declared cluster metrics is a cluster; the one the system parameter cluster.datasource_id points to is the default.
  3. Choose the cluster on the cluster dashboard to see its nodes, Pods, CPU and memory.

Module metrics and cluster metrics

TypeUsed byNotes
Module metricThe metric sources of a module, the resource dashboardA module picks its metrics from these: metrics that take part in algorithms, and display-only metrics (Requests, Limits, OOM, JVM, throttling and others).
Cluster metricThe cluster dashboardA module cannot pick it.

A module metric says whether its query answers "one Pod" or "the sum of all replicas". When a query returns a series for each Pod, the platform says how to join them: sum(...) for the total, avg(...) or max(...) for one Pod. A template whose name and query clearly disagree (named Limits, querying requests) is pointed out.

The Operator report: the real settings in the cluster

The Operator reads the cluster read-only and reports to the platform:

  • Nodes: ready or not, schedulable, capacity and allocatable, and the sum of the Requests and Limits of the module Pods that run on them (only the Pods of the modules; no other Pod is read).
  • The workload of each module: desired, ready, available and updated replicas; the Requests and Limits of every container; the Pods (name, node, phase, ready, restarts); and whether an HPA or KEDA object scales it.

The Operator reads about every 5 minutes; the platform keeps the newest report and records changes of the settings (kept longer than the snapshots). The resource dashboard takes the Requests and Limits of a Pod, the replicas now, the cluster name and the Pod names from it; a report older than 15 minutes is no longer "now". With no report the dashboard falls back to a Prometheus estimate and says "estimated".

The cluster name is the system parameter cluster.name (default by default); it is in the node and workload data, on the resource pages, in the mail and in the cluster variable of the Grafana dashboard. The platform manages one cluster: change it to a meaningful name such as prod-east.

The Grafana dashboard

deploy/grafana in the repository has the resource dashboard; the system settings take the address of Grafana, and the "Open in Grafana" links of the resource dashboard carry the module and the window as variables.

Limits of use

  • The Operator has been tested only with a fake client, not on a real cluster.
  • Reading is read-only and a report changes nothing in the cluster; replicas are changed separately by the Operator in Auto mode; see Admission and scaling.
