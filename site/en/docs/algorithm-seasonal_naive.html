USER GUIDE

Seasonal Naive

Repeats the corresponding observations from the preceding cycle. A seasonal baseline for repeating demand; anomalies in that cycle are repeated too.

← Models and prediction modes

Purpose and workload fit

Repeats the corresponding observations from the preceding cycle. A seasonal baseline for repeating demand; anomalies in that cycle are repeated too.

History and runtime requirements

At least season_length_steps observations: one full cycle.

Inputs must be regularly sampled, gap-free, and finite. Outputs retain the metric unit, such as CPU cores, memory bytes, or requests per second. The sample interval determines the duration of a step. Minimum history permits execution; it does not establish forecast quality.

This method does not use covariates; target metrics are forecast separately.

How it works and the formula

The seasonal naive forecast takes the value at the same position one cycle earlier as the forecast. The cycle length m is in steps, given by season_length_steps; the algorithm never guesses the cycle.

Formula
ŷ(T+h) = y(T + h − m·(k+1)),  where k = ⌊(h−1)/m⌋

In plain words: forecast step 1 is step 1 of the latest cycle, step 2 is step 2, and so on. When the forecast range is longer than a cycle, the latest cycle is repeated as a whole. In the code this is out[h] = values[n − m + (h mod m)] (h from 0).

You convert season_length_steps yourself: the length of the cycle ÷ the sampling step. A daily cycle at 5-minute samples = 24×60÷5 = 288 steps; a weekly cycle = 7×288 = 2016 steps. The history needs at least m points.

Why it is done this way: many business loads have a strong daily or weekly cycle (a morning peak, a Monday batch). For such a load "what was it at this time yesterday" is often more accurate than "what is it now", and it takes almost no computation. It is the baseline of the seasonal algorithms.

Its weakness: it looks at one cycle only. If that cycle happened to hold an incident or an odd peak, it copies the oddity into the future as if it were normal; it sees no trend either. That is why the platform lets it decide only when the history holds several full cycles (system parameter forecast.min_seasons, default 3), and why it should be compared with other algorithms.

Parameter reference

On narrow screens, swipe the parameter table horizontally to read all columns.

Parameter / typeDefault / range / unitMeaning and use
season_length_steps
int		Required; no default
≥ 2; steps		Season length in sample steps; zero disables seasonality where allowed. Seasonal Naive requires an explicit cycle.

Configuration example

Edit parameters in Algorithm management. This is a parameter object, not a complete config.yaml. Seasonal examples assume five-minute sampling; adjust for your actual interval. Omitted optional values use the defaults above.

JSON
{
  "season_length_steps": 288
}

Worked example: data, parameters and substitution

To keep it readable we use a "mini cycle" of 4 steps (in real use it is 288 or 2016). Samples are every 5 minutes and the history holds two full cycles:

JSON
{
  "season_length_steps": 4
}
Data
y = [1.0, 2.0, 3.0, 2.0,   1.2, 2.2, 3.2, 2.1]
     └─ 1st cycle ─┘         └─ 2nd cycle (latest) ─┘     n = 8, m = 4

We forecast the next 6 steps. Take the latest cycle [1.2, 2.2, 3.2, 2.1] and apply values[n − m + (h mod m)]:

The result is [1.2, 2.2, 3.2, 2.1, 1.2, 2.2]: the latest cycle copied as it is. The values of the first cycle (1.0, 2.0, 3.0, 2.0) play no part, which is what "looks at one cycle only" means.

These numbers are computed by the real code in pkg/forecast/docs_examples_test.go and checked on every test run.

Tuning and tradeoffs

Convert the business cycle into sample steps. A day is 288 steps at five-minute sampling or 1440 at one-minute sampling; 24 is not automatically a day.

Sources and references

  • Hyndman, R.J. & Athanasopoulos, G. Forecasting: Principles and Practice (3rd ed., OTexts, 2021), section 5.2, the Seasonal naïve method: https://otexts.com/fpp3/simple-methods.html.
  • The platform rule that a seasonal algorithm may decide only with several cycles of history exists so that one odd cycle is not taken for a pattern; see the system parameter forecast.min_seasons.

Use in a module

  1. Save parameters and check history, sample interval, and horizon.
  2. Enable module prediction. Fixed mode runs the selected method; dynamic mode uses centrally enabled methods.
  3. This baseline does not need backtest promotion, but actual performance still needs review.
  4. Review error, peak underestimation, runtime, and adoption reasons in Observe or Recommend before separately authorizing admission and replica actions.

For insufficient history, invalid settings, timeouts, or invalid output, inspect run reasons. Without eligible forecasts, the module follows its schedules, fallback, and protection rules.
