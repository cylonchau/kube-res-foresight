USER GUIDE

Model service · forecasting and tuning

Calls an external time-series model over HTTP. Configure it in Model management, then choose the module prediction mode. A failed request fails that candidate while other eligible methods continue.

← Models and prediction modes

Purpose and workload fit

Calls an external time-series model over HTTP. Configure it in Model management, then choose the module prediction mode. A failed request fails that candidate while other eligible methods continue.

History and runtime requirements

The platform needs at least 30 points; the service may impose additional context limits. finetune_min_points controls tuning submission, not the forecasting minimum.

Inputs must be regularly sampled, gap-free, and finite. Outputs retain the metric unit, such as CPU cores, memory bytes, or requests per second. The sample interval determines the duration of a step. Minimum history permits execution; it does not establish forecast quality.

This method does not use covariates; target metrics are forecast separately.

How it works and the formula

The model service algorithm has no formula of its own: it does not compute inside the platform. It sends the history to a separately running time-series foundation model (Chronos or TimesFM, for example), which returns the forecast; the platform only sends the request, reads the result and runs the safety checks. Every request carries the whole history, and the service keeps nothing about it between calls except the fine-tuned copy you ask it to make.

Flow
1) the platform takes the latest history y(1…T) (at least 30 points), builds the request for the protocol and POSTs it to endpoint
2) the service returns the mean forecast of H steps and the quantiles it reports
3) service_quantile = 0: use the mean; above 0 (0.9, say): take that quantile of the answer (an error if it is not there)
4) checks: exactly H steps; every step a finite number; a value below 0 is cut to 0 (a resource amount is never negative)

The three protocols:

  • finetune: the service in scripts/tsfm-eval/finetune of this project, which can be fine-tuned. Forecast: POST /v1/predict, request {"values": […], "horizon": H, "quantiles": [q]}, plus "model_key" when there is a fine-tuned copy; answer {"mean": […], "quantiles": {"0.9": […]}}.
  • unitshub_chronos: the ready-made Chronos container of kingfs/unitshub, forecast only, zero-shot. POST /models/current/invoke, request {"task": "forecast_quantile", "input": {"series": […], "horizon": H, "quantiles": [q]}}.
  • unitshub_timesfm: the TimesFM container of the same project, request {"task": "forecast_point", "input": {"history": […], "horizon": H}}. The answer of both unitshub protocols is in output.forecasts[0], holding mean and quantiles.

What the parameters do:

  • endpoint: the address of the service (no trailing slash). protocol: one of the three above.
  • api_key_env: the name of an environment variable, not the key itself; the value of that variable in the platform process is sent as Authorization: Bearer …, and the key is never stored in the algorithm parameters.
  • timeout_seconds: the timeout of one forecast request. service_quantile: 0 uses the mean, 0.5 to 0.99 uses that quantile (0.9 = the actual stays below it about 90% of the time).
  • finetune_*: the fine-tuning settings. Only the finetune protocol supports them; when finetune_interval_hours is above 0 the platform submits the series and these settings to the service (POST /v1/fit) once the fine-tuned copy is older than that, and forecasts then carry model_key, so the service answers from the fine-tuned copy.

Why it is done this way: a time-series foundation model is pretrained on a great many different series and gives a decent forecast without training for each load; it sits in a separate service because it needs a GPU or a heavy runtime that does not belong in the platform process. The platform treats it like any other candidate: it is backtested, scored and promoted, and when the service is down, times out or returns an invalid result that candidate fails, the algorithm run record says why, and the other algorithms are not affected.

Mind: its inside is opaque and has no readable formula; how good it is has to be judged by the backtest and the measured scores.

Configuration example

Edit parameters in Model management. This is a parameter object, not a complete config.yaml. Seasonal examples assume five-minute sampling; adjust for your actual interval. Omitted optional values use the defaults above.

JSON
{
  "endpoint": "http://chronos:8000",
  "protocol": "finetune",
  "timeout_seconds": 30,
  "service_quantile": 0,
  "finetune_interval_hours": 0
}

Worked example: the request, the answer and how the platform reads it

This algorithm has no formula to substitute into, so here is "what the platform sent, what the service answered and what the platform did with it". The answer below comes from a stand-in service made for the demonstration, not from a real model; its numbers were written to show the rules. Parameters:

JSON
{
  "endpoint": "http://chronos:8000",
  "protocol": "finetune",
  "api_key_env": "CHRONOS_API_KEY",
  "timeout_seconds": 30,
  "service_quantile": 0.9
}

Step 1, the request the platform sends (the history has 30 points, only indicated here; 5-minute steps, forecast 3 steps). Because api_key_env is set and that variable exists in the platform process, the header carries Authorization: Bearer …:

Request
POST http://chronos:8000/v1/predict
{"horizon": 3, "quantiles": [0.9], "values": [1.00, 1.01, 1.02, … (30 values) …, 1.29]}

Step 2, the answer of the service (for the demonstration):

Answer
{"mean": [1.2, 1.3, 1.4], "quantiles": {"0.9": [1.8, -0.2, 2.4]}}

Step 3, what the platform does. service_quantile = 0.9, so it takes quantiles["0.9"] = [1.8, −0.2, 2.4] (not the mean); the 3 steps match the request; every step is a finite number; step 2 is −0.2, below 0, and is cut to 0:

Result
ŷ = [1.8, 0, 2.4]

With service_quantile 0 the quantile list of the request is [0.5] (a median is asked for) and the platform uses the mean of the answer = [1.2, 1.3, 1.4] as it is.

If the answer has no 0.9 entry, the number of steps is not 3, or it contains a NaN, the platform neither guesses nor fills in: the forecast fails and the reason is written to the algorithm run record.

These behaviours are checked by pkg/forecast/docs_examples_test.go with the real request and reading code against a stand-in service; no real model is involved.

Tuning and tradeoffs

Use the following as a starting point for background tuning. Deploy a compatible service first and replace the example endpoint. The 24-hour tuning interval is an example, not the platform default.

JSON
{
  "endpoint": "http://chronos:8000",
  "protocol": "finetune",
  "timeout_seconds": 30,
  "finetune_interval_hours": 24,
  "finetune_mode": "full",
  "finetune_steps": 30,
  "finetune_learning_rate": 0.00001,
  "finetune_batch_size": 16,
  "finetune_context_length": 256,
  "finetune_min_points": 200
}

The finetune protocol supports background tuning. unitshub_chronos and unitshub_timesfm are prediction-only and require a zero tuning interval. Store credentials in the platform environment and set only the variable name in api_key_env. Backtests and replay use pretrained models; assess tuned models through arriving actuals.

Sources and references

  • Ansari, A.F. et al. "Chronos: Learning the Language of Time Series", 2024, arXiv:2403.07815: a foundation model that quantises a series into tokens and forecasts probabilistically with a language-model architecture.
  • Das, A., Kong, W., Sen, R., Zhou, Y. "A decoder-only foundation model for time-series forecasting" (TimesFM), ICML 2024, arXiv:2310.10688.
  • Hu, E.J. et al. "LoRA: Low-Rank Adaptation of Large Language Models", 2021, arXiv:2106.09685: the low-rank adaptation used by finetune_mode: lora.
  • The service interface of the unitshub containers and of scripts/tsfm-eval/finetune of this project is the request and answer format listed under "How it works and the formula" on this page, implemented in pkg/forecast/modelservice.go.

Parameter / typeDefault / range / unitMeaning and use
reset_on_change
bool		false
No additional range		Use history after a detected level shift, preserving enough points for the underlying method.

float		8
≥ 3; ≤ 50		Minimum shift relative to robust noise; used only with reset_on_change.

float		0.2
≥ 0; ≤ 5		Minimum relative level shift; 0.2 means 20%. Used only with reset_on_change.
quantile_level
float		0
≥ 0; ≤ 0.99		Zero disables conformal calibration; otherwise must be above 0.5 and at most 0.99. Calibrates an upper forecast using earlier forecast errors.
calibration_windows
int		8
≥ 3; ≤ 50		Historical windows for conformal calibration; more windows add forecast calls and history requirements.

quantile_level uses a 0–1 scale; percentile uses 1–100. Calibration runs extra historical forecasts. Check history and runtime budgets before increasing windows; coverage is an evaluation target, not a guarantee.

Use in a module

  1. Save parameters and check history, sample interval, and horizon.
  2. Enable module prediction. Fixed mode runs the selected method; dynamic mode uses centrally enabled methods.
  3. Run rolling backtests and earn version promotion before adoption. Re-run backtests after changes affecting model identity.
  4. Review error, peak underestimation, runtime, and adoption reasons in Observe or Recommend before separately authorizing admission and replica actions.

For insufficient history, invalid settings, timeouts, or invalid output, inspect run reasons. Without eligible forecasts, the module follows its schedules, fallback, and protection rules.
