Histogram Percentile · 历史分位数

← 算法与模型总览

用途与适用负载

对带时间衰减的历史取百分位，并将该值作为未来各步的水平。适合关注资源高水位的规格比较，不刻画峰值发生的具体时刻。

历史数据与运行条件

至少 4 个点；要覆盖典型高峰，应准备完整业务周期。

输入应是等间隔、无缺口且数值有限的序列。输出保留输入指标单位，例如 CPU 核、内存字节或每秒请求数；采样步长决定步数对应的真实时间。最低样本数仅表示可运行，不代表预测可靠。

此方法不使用协变量；分别预测各目标指标。

原理与公式

历史分位数不预测未来，它回答的是“历史里有 p% 的时间，负载不超过多少”，再把这个值延伸为一条水平线。越新的样本权重越大：一个样本比最新的样本老 half_life_hours 小时，它的权重就减半。

公式
半衰期（步数）：H = half_life_hours × 3600 ÷ 采样步长（秒）
样本权重：      w(i) = 0.5 ^ (age(i) / H)，age(i) = 距最新样本的步数（最新的 age = 0，权重 = 1）
分位值 Q：      把样本按数值从小到大排，累加权重，取累计权重第一次 ≥ (percentile/100) × 总权重 的那个值
预测：          ŷ(T+h) = Q × (1 + safety_margin)          h = 1 … H（一条水平线）

参数怎样进入公式：

  • percentile（1 到 100）：取第几百分位。95 表示“95% 的（加权）时间不超过这个值”，越大越保守。
  • half_life_hours：半衰期。越短越只看近期，越长越接近不加权的整体分位数；0 表示不衰减。
  • safety_margin：再乘 1+margin，作为额外余量。例如 0.1 表示多留 10%。

为什么这样做：Kubernetes 的 VPA 和 Google 的 Autopilot 都是这样给资源请求定值的：用带衰减的分位数，而不是平均值。平均值会让一半的时间不够用；高分位数能盖住大多数峰值，衰减让它在负载上升时较快跟上、在高峰过去后缓慢遗忘。对“宁可多给也不能 OOM”的内存推荐，它是常用的对照。

它做不到的：它是一条平线，不模拟未来，不认识周期，也不知道高峰什么时候到来。它是“偏保守”的预测，不是“预期负载”，所以平台在需求拆解里会标出 P90 或 P95 的提示。

配置示例

在“算法管理”编辑参数。以下仅为参数对象，不是 config.yaml 全文；周期示例按 5 分钟采样，需按实际步长调整。未列出的可选参数使用上表默认值。

JSON
{
  "percentile": 95,
  "half_life_hours": 24,
  "safety_margin": 0.1
}

计算示例：数据、参数与代入过程

最近 8 个采样点（每 5 分钟一个）的内存使用量（MiB），其中有一次短暂高峰 60。参数：90 分位，半衰期 0.5 小时（= 30 分钟 = 6 步），再留 10% 余量。

JSON
{
  "percentile": 90,
  "half_life_hours": 0.5,
  "safety_margin": 0.1
}
数据
y = [40, 42, 45, 41, 60, 44, 43, 46]        （最新的是最后一个 46）

第 1 步，算权重。H = 0.5×3600÷300 = 6 步。w = 0.5^(age/6)：

总权重 = 5.5283，90 分位的目标累计权重 = 0.9 × 5.5283 = 4.9755。

第 2 步，按数值排序并累加权重：

排序后的值4041424344454660
该值的权重0.44540.63000.50000.89090.79370.56121.00000.7071
累计权重0.44541.07541.57542.46633.26003.82124.82125.5283

累计权重第一次 ≥ 4.9755 的是最后一格（46 处只到 4.8212，还差一点），所以 Q = 60。这就是高分位数的意思：一次高峰只占 12.8% 的权重，但因为 90 分位要求盖住 90% 的权重，高峰仍被纳入。

第 3 步，加余量：ŷ = 60 × (1 + 0.1) = 66。预测 [66, 66]（2 步）。

对比：如果把 percentile 改成 50（中位），累计权重 ≥ 2.7642 的第一个值是 44，不计 10% 余量时预测为 44；高分位数和中位数之间差了 16 MiB，这就是“保守”的代价。把 half_life_hours 改成 0（不衰减），同样的数据 90 分位仍是 60，因为这个高峰在 8 个点里本来就占了 1/8，而 90% 的目标要求盖到它。

这些数字由 pkg/forecast/docs_examples_test.go 用真实代码算出并持续校验。

调参与取舍

percentile 用 1～100 的百分数，如 95；half_life_hours 越短越重视近期，0 表示不衰减。安全余量再乘 (1+safety_margin)，不要与其他保护余量重复叠加而不评估。

来源与引用

  • Kubernetes Vertical Pod Autoscaler（VPA）的推荐器：用带指数衰减（半衰期）的直方图取目标分位数，并加安全余量。源码与设计文档在 kubernetes/autoscaler 的 vertical-pod-autoscaler 目录。
  • Rzadca, K. 等 “Autopilot: Workload Autoscaling at Google”，EuroSys 2020：Google 的 Autopilot 同样使用带衰减的直方图和分位数，并比较了多种推荐器。
  • 本平台与 VPA 的差别：这里直接对采样序列做加权分位（不分桶），并默认 95 分位、24 小时半衰期；参数与 VPA 的默认值不同，不要照搬。

通用参数：变化重置与分位校准

参数 / 类型默认值 / 范围 / 单位含义与使用
reset_on_change
bool		false
无额外范围限制		水平突变后重置：检测历史里最后一次水平突变（发布、扩缩容、流量切换），只用突变之后的历史预测。关闭时用全部历史（现状）。突变之后至少要有 6 步才会被确认；突变后的历史不够算法所需时，取算法所需的最新一段。
change_threshold
float		8
≥ 3; ≤ 50		突变阈值：突变幅度（扣除前一段趋势后）超过噪声的多少倍才算，越大越不容易误报，噪声由相邻步变化的稳健标准差估计。仅 reset_on_change=true 时使用。
change_min_shift
float		0.2
≥ 0; ≤ 5		最小突变幅度：突变至少是水平的这个比例（0.2 = 20%），很干净的序列上的微小跳变不算。仅 reset_on_change=true 时使用。
quantile_level
float		0
≥ 0; ≤ 0.99		推荐分位数：0 = 点预测（现状）；0.9 等 = 预测「实际值有约 90% 的把握不超过」的线（保形预测：用本算法在这个负载最近几个窗口里的真实误差校准，需要更多历史和时间）。必须大于 0.5。
calibration_windows
int		8
≥ 3; ≤ 50		校准窗口数：用最近多少个历史窗口测本算法的误差；越多越稳，也越慢（每个窗口多跑一次预测）。仅推荐分位数大于 0 时使用。

quantile_level 是 0～1 的分位点，percentile 是 1～100 的百分数，二者不是同一参数。分位校准会额外运行历史预测；增加校准窗口前检查历史与运行预算，覆盖率是评估目标而非保证。

在模块中使用

  1. 保存参数，检查历史窗口、采样步长和预测范围。
  2. 打开模块的“启用预测”；固定算法只运行指定方法，动态算法使用平台已启用的方法。
  3. 先运行滚动回测，通过版本晋升后才会采用；修改影响模型版本的参数后重新回测。
  4. 在仅观察或仅推荐下检查误差、峰值低估、耗时与采用原因，再分别授权准入和副本执行。

历史不足、参数不合法、运行超时或输出无效时，检查算法运行原因；没有合格预测时按模块的固定周期、兜底与保护规则处理。
