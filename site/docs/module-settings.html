文档/资源大盘与模块配置

使用指南

模块配置说明

逐组说明模块的每项配置怎么填、默认值和效果，并给出一次完整配置的示例。

配置在哪里，怎么看生效值

在“模块管理 > 模块列表”里新建或编辑模块。编辑页分四组：基础配置、计算参数、安全边界、模块策略；运行模式在基础信息里选。模块列表的操作栏有“参数”按钮，不进入编辑页就能按分组看到每项参数当前的生效值、单位、来源（本模块、系统设置或未设置）和含义。

大多数计算系数填 0 表示“跟随系统设置”（系统管理 > 系统设置 > 资源分析与推荐）。需要整体调整时改系统设置，某个模块要特殊对待时才在模块里单独填。

一次配置的顺序

  1. 工作负载与指标。填命名空间、Kind、名称；在“算法计算指标”里选 CPU、内存等指标模板，在“监控展示指标”里选 Requests、Limits 等只展示的指标，模板由指标接入里的数据源与指标模板提供。
  2. 运行模式。先选 Observe 或 Recommend，看资源大盘的结果是否可信，再考虑 Admission 或 Auto。
  3. 计算参数。多数模块保持默认即可；有明确的余量要求时再改系数。
  4. 安全边界。至少填最小、最大副本数；要限制动作快慢时填调整节奏。
  5. 模块策略。需要时再加时间周期、指标触发或固定副本数。
  6. 回到资源大盘，在“计算依据”里确认每个数字用的是你设的系数。

基础配置

配置项含义怎么配
名称、命名空间、Kind、工作负载这个模块管哪个工作负载。命名空间、Kind、名称合起来不能重复。Kind 支持 Deployment、StatefulSet、DaemonSet。
Service、Container指标 PromQL 里的 {{service}}、{{container}} 变量，不属于工作负载的身份。只有指标模板用到这些变量时才填。
运行模式Observe 只观察；Recommend 给建议；Admission 允许为新 Pod 应用资源建议；Auto 允许 Operator 调副本。准入与自动还要全局开关打开，默认关闭。
历史范围（默认 720 小时）、预测提前量（15 分钟）、采样步长、训练窗口步数、最少数据点、最大补点步数（3）预测用的数据与周期。资源大盘不用它们。历史范围至少覆盖算法需要的周期数；步长留空沿用指标查询的步长。
最大缺失比例（30%）、最少历史占比（80%）数据质量底线：缺得太多或历史太短，这一轮降级。数据源经常抖动时适当放宽，而不是关掉检查。
时区时间周期、指标触发的生效时间和大盘按小时的分析都按它算，默认 Asia/Shanghai。写 IANA 时区名。

指标绑定：大盘读什么数据

资源大盘读模块的每个指标来源，向 Prometheus 当场查询。绑定时注意：

  • 使用量指标要么返回一个 Pod、要么返回全部副本的总和，在来源里说明“查询结果为单 Pod / 全副本”。查询对每个 Pod 返回一条序列时，平台会提示：求总和用 sum(...)，求单 Pod 用 avg(...) 或 max(...)。
  • Requests、Limits 属于展示指标，不参与算法。有 Operator 上报时大盘用 Pod 模板，指标只作旁证。
  • 要显示 OOM、限流、JVM，需要分别绑定 OOM 次数、OOM 前工作集、CPU 限流、JVM 堆等指标；没绑定的规则不生效，页面写明缺什么。

计算参数：容量与副本

配置项含义默认与怎么配
副本模式、容量方式副本上限是固定还是可动态抬高；单 Pod 容量是手填还是从历史估算。默认固定、手动。
单 Pod 容量（请求/秒）动态副本按它算副本数。要先验证过再填。
单 Pod CPU、内存 Requests（模块填写）容量计算用。资源大盘用的是 Kubernetes 的 Pod 模板，不是这两项。与工作负载实际的 Requests 保持一致。
容量保留系数一个 Pod 的容量最多用到多少，推荐值 = 需要量 ÷ 系数。0 表示不保留；0.8 即留 20% 余量。
推荐值系数预测峰值乘以它。默认 1。

计算参数：资源大盘的推荐系数

下面是大盘推荐 Requests、Limits 和副本数的全部系数。模块填 0 跟随系统设置，括号里是系统默认。

配置项含义怎么配
P90、P95、P99 目标占比（80%、85%、110%）推荐后这个百分位的使用量占 Requests 的比例，推荐 Requests = 使用量 ÷ 它。占比越小推荐越大。P99 可以大于 100%：短时超出 Requests 由 Limits 承担。
持续时间窗口（30 分钟）推荐用的百分位取“持续使用量”，窗口越长，越短的峰值越不影响长期配置。0 按原始点；对每天有规律短峰的负载可加大。
CPU、内存 Requests 余量（不加）在三个百分位的最大需求上再加的比例，0.1 即多 10%。CPU、内存分别设。
CPU、内存 Limits 系数（120%）推荐 Limits = max(推荐 Requests, P99 × 系数)。填 1.2 就是 P99 × 1.2，不得小于 1。内存的系数不要压得太低：Limits 低于峰值会被 OOM 杀掉。
Limits 峰值占比上限（90%）推荐副本下，全副本 P99 使用量不超过 Limits 总和的这个比例。防止副本被减得太少，峰值顶到 Limits。
保底系数大于 0 时，推荐不低于模块填写的 Pod Requests × 它。0 关闭。

三个百分位的合理区间、超配分级、CPU 限流界限、分析周期只在系统设置里改；模块列表的“参数”窗口里能看到它们，标“系统设置”。

两个“Limits 系数”不是一回事

“CPU、内存 Limits 系数”只影响资源大盘推荐的 Limits。基础信息里的“CPU limit 系数、内存 limit 系数”是准入给新 Pod 设置的 Limits = 推荐 Requests × 系数，见Request、Limit 比例与 OOM 地板。

计算参数：OOM 与 JVM

配置项含义默认与怎么配
OOM 追溯天数预测流水线看 OOM 的周期。14 天。
OOM 保护系数窗口内有 OOM 时，内存推荐不低于被杀时的工作集 × 它，并且不低于现在的 Requests。1.2；发生过 OOM 的负载可调高。
OOM 扣算法评分、OOM 权重开启后每次 OOM 扣预测算法的内存评分：评分 = 100 × (1 − 次数 × 权重)。只影响算法选择，不改大盘推荐值。默认关闭，权重 0.2。
OOM 下限：工作集、Limits、历史倍数OOM 下限里三种底数各乘自己的系数，取最大的。默认都是 1。
JVM 堆压力阈值P99 堆使用量占堆上限超过它视为堆压力，不缩容。默认 0.85；0 关闭，需要绑定 JVM 堆指标。

安全边界

配置项含义怎么配
最小、最大副本数所有策略给出的结果最后都要落在这个区间，永远在最后一步。至少填一个；不填就没有这一侧的限制。
硬上限、上限扩展速度最大副本数模式为动态时：预测需要更多，上限每个周期最多抬高当前上限的这个比例，最高到硬上限。只在动态扩展下使用。
CPU、内存的最小、最大值推荐的 Requests 不会越过它。按节点规格和业务底线填。
扩容、缩容单次最多增减，扩容、缩容冷却一次动作最多动几个副本、同方向动作的间隔。限制动作快慢，不限制数量上下限。0 不限制。缩容单次 1 个是常见的稳健起点。
推荐有效期（900 秒）、算法最低评分一份推荐多久内可用；评分低于它的算法不被采用。过短时推荐会在下一轮预测前过期。
降级 CPU、内存、副本数预测不可用时的默认值，经过上面的边界。可选；不填则保持原值。
恢复观察周期数（2）降级恢复后要连续健康这么多个周期才解除。避免在异常边缘频繁切换。
旁路开启后模块不参与自动决策，也不改任何配置。需要人工接管时开，并写原因。

模块策略

预测模式、时间周期、指标触发和固定副本数在模块策略与合并顺序里说明，包括几个策略同时给出不同副本数时怎么合并。

示例：一个 12 副本的 Deployment

单 Pod Requests 4 核、6 GiB，Limits 8 核、16 GiB。目标：先观察，再逐步收紧。

步骤配置在资源大盘上看到什么
1运行模式 Recommend，其余系数跟随系统。方案①、方案②给出建议，依据里的系数都是系统值。
2最小副本数 4、最大副本数 20，缩容单次最多 1 个。推荐 9、现在 12 时，“推荐副本数”是 9，“本次动作到”是 11。
3内存 Limits 系数 1.3。推荐 Limits = max(推荐 Requests, P99 × 1.3)，依据里的 Limits 公式随之变化。
4需要时再加时间周期：工作日 09:00–18:00 至少 8 个副本。常态与高负载时段里的高峰小时可作为设置周期的依据。
5确认效果后再改为 Auto，并打开全局开关。Operator 在边界、步长和冷却内调副本。
