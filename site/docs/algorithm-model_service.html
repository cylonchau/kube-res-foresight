使用指南

模型服务 · 预测与微调

通过 HTTP 调用外部时序模型。模型管理中配置服务，模块中选择预测方式。服务不可用时本次候选失败，其他算法继续按资格参与。

用途与适用负载

通过 HTTP 调用外部时序模型。模型管理中配置服务，模块中选择预测方式。服务不可用时本次候选失败，其他算法继续按资格参与。

历史数据与运行条件

平台至少 30 点，服务可能另有上下文限制；finetune_min_points 仅决定何时提交微调，不是预测的最低点数。

输入应是等间隔、无缺口且数值有限的序列。输出保留输入指标单位，例如 CPU 核、内存字节或每秒请求数；采样步长决定步数对应的真实时间。最低样本数仅表示可运行，不代表预测可靠。

此方法不使用协变量；分别预测各目标指标。

原理与公式

模型服务算法本身没有公式：它不在平台里计算，而是把历史发给一个独立运行的时间序列基础模型（例如 Chronos、TimesFM），由它返回预测，平台只负责发请求、读结果、做安全检查。平台每次请求都带上完整历史，服务端除了你让它做的微调副本之外，不保存任何状态。

流程
1) 平台取最近的历史 y(1…T)（至少 30 点），按协议组成请求，POST 到 endpoint
2) 服务返回 H 步的均值预测，以及它报告的若干分位数
3) service_quantile = 0：用均值；大于 0（如 0.9）：从返回的分位数里取这一个分位（取不到就报错）
4) 检查：步数必须正好是 H；每一步必须是有限数；小于 0 的截为 0（资源量不会是负的）

三种协议：

  • finetune：本项目 scripts/tsfm-eval/finetune 里的服务，支持微调。预测：POST /v1/predict，请求 {"values": […], "horizon": H, "quantiles": [q]}，有微调副本时再带 "model_key"；答复 {"mean": […], "quantiles": {"0.9": […]}}。
  • unitshub_chronos：kingfs/unitshub 的 Chronos 现成容器，只预测、零样本。POST /models/current/invoke，请求 {"task": "forecast_quantile", "input": {"series": […], "horizon": H, "quantiles": [q]}}。
  • unitshub_timesfm：同一个项目里的 TimesFM 容器，请求 {"task": "forecast_point", "input": {"history": […], "horizon": H}}。两个 unitshub 协议的答复都在 output.forecasts[0] 里，含 mean 和 quantiles。

参数怎样发挥作用：

  • endpoint：服务地址（不带末尾斜杠）。protocol：上面三种之一。
  • api_key_env：环境变量的名字，不是密钥本身；平台进程里这个变量的值会作为 Authorization: Bearer … 发出，密钥不会存进算法参数。
  • timeout_seconds：一次预测请求的超时。service_quantile：0 用均值，0.5 到 0.99 用那个分位（0.9 = 实际值约 90% 的时候不超过它）。
  • finetune_*：微调的设置。只有 finetune 协议支持，finetune_interval_hours 大于 0 时，平台在微调副本超过这个时长时把序列和这些设置提交给服务（POST /v1/fit），预测时带上 model_key，服务就用微调后的副本答复。

为什么这样做：时间序列基础模型是在大量不同序列上预训练的，不需要为每个负载单独训练就能给出不错的预测；放在独立服务里，是因为它需要 GPU 或较重的运行环境，不适合塞进平台进程。平台把它当成和其他算法一样的候选：同样要回测、评分、晋升，服务不可用、超时或结果无效时，这个候选失败，算法运行记录里写明原因，不影响其他算法。

要留意：它的内部不透明，没有可解释的公式；预测的好坏要靠回测和实测评分来判断。

参数说明

窄屏可左右滑动参数表，查看完整说明。

参数 / 类型默认值 / 范围 / 单位含义与使用
endpoint
string		必填，无默认值
无额外范围限制		模型服务的地址，如 http://chronos:8000，不带结尾斜杠。
protocol
string		"finetune"
finetune / unitshub_chronos / unitshub_timesfm		服务的接口协议：finetune = scripts/tsfm-eval/finetune 的服务（支持微调）；unitshub_chronos、unitshub_timesfm = kingfs/unitshub 的现成容器（只预测）。
api_key_env
string		""
无额外范围限制		保存访问密钥的环境变量名（平台进程的环境变量），预测时作为 Bearer 密钥发给服务；留空表示服务不需要密钥。密钥本身不存进算法参数。
timeout_seconds
int		30
≥ 1; ≤ 600; s		一次预测请求的超时时间。
service_quantile
float		0
≥ 0; ≤ 0.99		0 = 用服务给的均值预测；0.5～0.99 = 用服务给的这个分位数（如 0.9 = 实际值不超过这条线）。分位数预测按 pinball 损失和覆盖率回测。
finetune_interval_hours
int		0
≥ 0; ≤ 720; h		微调间隔：服务上微调后的模型超过这么久，平台就重新提交数据微调一次；0 = 不微调，一直用预训练模型。只有 finetune 协议的服务支持。微调在后台进行，期间预测仍用旧的微调模型（没有就用预训练模型）。
finetune_mode
string		"full"
full / lora		微调方式：full = 全参数微调；lora = 低秩适配（服务端要装 peft，没装会让微调失败）。
finetune_steps
int		30
≥ 1; ≤ 2000; steps		每次微调的训练步数；增加会提高训练耗时，也可能过拟合。
finetune_learning_rate
float		1e-05
≥ 1e-08; ≤ 0.01		微调的学习率。全参数微调用很小的值（1e-5 量级）。
finetune_batch_size
int		16
≥ 1; ≤ 256		微调每步用的窗口数。
finetune_context_length
int		256
≥ 16; ≤ 8192; steps		微调时每个训练窗口读取的最近步数。
finetune_min_points
int		200
≥ 60; ≤ 100000; points		序列至少有这么多点才提交微调；更短的序列微调只会学到噪声，继续用预训练模型。

配置示例

在“模型管理”编辑参数。以下仅为参数对象，不是 config.yaml 全文；周期示例按 5 分钟采样，需按实际步长调整。未列出的可选参数使用上表默认值。

JSON
{
  "endpoint": "http://chronos:8000",
  "protocol": "finetune",
  "timeout_seconds": 30,
  "service_quantile": 0,
  "finetune_interval_hours": 0
}

计算示例：请求、答复与平台怎么读

这个算法没有可代入的公式，所以这里演示“平台发了什么、服务答了什么、平台怎么处理”。下面的答复由一个用于演示的假服务返回，不是真实模型的输出，数字是为了展示规则而写的。参数：

JSON
{
  "endpoint": "http://chronos:8000",
  "protocol": "finetune",
  "api_key_env": "CHRONOS_API_KEY",
  "timeout_seconds": 30,
  "service_quantile": 0.9
}

第 1 步，平台发出的请求（历史共 30 个点，这里只示意；步长 5 分钟，预测 3 步）。因为设置了 api_key_env，并且平台进程里有这个环境变量，请求头带 Authorization: Bearer …：

请求
POST http://chronos:8000/v1/predict
{"horizon": 3, "quantiles": [0.9], "values": [1.00, 1.01, 1.02, …（共 30 个）…, 1.29]}

第 2 步，服务的答复（演示用）：

答复
{"mean": [1.2, 1.3, 1.4], "quantiles": {"0.9": [1.8, -0.2, 2.4]}}

第 3 步，平台处理。service_quantile = 0.9，所以取 quantiles["0.9"] = [1.8, −0.2, 2.4]（而不是均值）；步数 3 与请求一致；每一步都是有限数；第 2 步是 −0.2，小于 0，被截为 0：

结果
ŷ = [1.8, 0, 2.4]

如果 service_quantile 是 0：请求里的分位列表是 [0.5]（要一个中位数），平台改用答复里的 mean = [1.2, 1.3, 1.4]，原样采用。

如果服务答复里没有 0.9 这一项、步数不是 3、或者含有 NaN，平台不会猜或补，这次预测失败，原因写进算法运行记录。

这些行为由 pkg/forecast/docs_examples_test.go 用真实的请求和读取代码对着一个替身服务验证，不依赖真实模型。

调参与取舍

要启用后台微调，可从以下配置开始。服务端须已部署并支持对应协议；示例地址需要替换为自己的服务。24 小时是此示例的微调间隔，不是平台默认值。

JSON
{
  "endpoint": "http://chronos:8000",
  "protocol": "finetune",
  "timeout_seconds": 30,
  "finetune_interval_hours": 24,
  "finetune_mode": "full",
  "finetune_steps": 30,
  "finetune_learning_rate": 0.00001,
  "finetune_batch_size": 16,
  "finetune_context_length": 256,
  "finetune_min_points": 200
}

finetune 协议支持后台微调；unitshub_chronos 与 unitshub_timesfm 仅预测，微调间隔必须为 0。密钥放平台进程环境变量，api_key_env 只填写变量名。回测与回放使用预训练模型，微调效果查看在线预测的实测回填。

通用参数：变化重置与分位校准

参数 / 类型默认值 / 范围 / 单位含义与使用
reset_on_change
bool		false
无额外范围限制		水平突变后重置：检测历史里最后一次水平突变（发布、扩缩容、流量切换），只用突变之后的历史预测。关闭时用全部历史（现状）。突变之后至少要有 6 步才会被确认；突变后的历史不够算法所需时，取算法所需的最新一段。
change_threshold
float		8
≥ 3; ≤ 50		突变阈值：突变幅度（扣除前一段趋势后）超过噪声的多少倍才算，越大越不容易误报，噪声由相邻步变化的稳健标准差估计。仅 reset_on_change=true 时使用。
change_min_shift
float		0.2
≥ 0; ≤ 5		最小突变幅度：突变至少是水平的这个比例（0.2 = 20%），很干净的序列上的微小跳变不算。仅 reset_on_change=true 时使用。
quantile_level
float		0
≥ 0; ≤ 0.99		推荐分位数：0 = 点预测（现状）；0.9 等 = 预测「实际值有约 90% 的把握不超过」的线（保形预测：用本算法在这个负载最近几个窗口里的真实误差校准，需要更多历史和时间）。必须大于 0.5。
calibration_windows
int		8
≥ 3; ≤ 50		校准窗口数：用最近多少个历史窗口测本算法的误差；越多越稳，也越慢（每个窗口多跑一次预测）。仅推荐分位数大于 0 时使用。

quantile_level 是 0～1 的分位点，percentile 是 1～100 的百分数，二者不是同一参数。分位校准会额外运行历史预测；增加校准窗口前检查历史与运行预算，覆盖率是评估目标而非保证。

在模块中使用

  1. 保存参数，检查历史窗口、采样步长和预测范围。
  2. 打开模块的“启用预测”；固定算法只运行指定方法，动态算法使用平台已启用的方法。
  3. 先运行滚动回测，通过版本晋升后才会采用；修改影响模型版本的参数后重新回测。
  4. 在仅观察或仅推荐下检查误差、峰值低估、耗时与采用原因，再分别授权准入和副本执行。

历史不足、参数不合法、运行超时或输出无效时，检查算法运行原因；没有合格预测时按模块的固定周期、兜底与保护规则处理。
