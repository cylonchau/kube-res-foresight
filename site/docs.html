KUBE_RESOURCE_FCST / DOCUMENTATION

理解预测，掌握调度。

从功能全景到实际操作，了解如何管理工作负载、比较预测结果、审查资源建议，并逐步开放弹性执行。

01项目概览

kube-resource-fcst 是面向单 Kubernetes 集群的资源预测与调度平台。它读取 Prometheus 历史与实时指标，通过多种算法预测未来需求，通过滚动回测和实测评分选择候选模型，生成 CPU、内存与目标副本建议，并将建议交给准入机制和 Operator。

平台适合需要理解周期性负载、比较预测方法、审查资源建议，并逐步开放自动伸缩的团队。管理界面使用中文，保留数据源、算法、模块、预测结果、推荐执行、监控、系统管理、授权管理和任务中心等能力。

一个模块，描述一个工作负载

模块关联 Kubernetes 工作负载，管理指标来源、阈值、历史窗口、预测周期、副本上下界、固定周期与 Fallback。算法管理保存平台级启用状态、参数、权重与采用门槛，统一应用到模块，无需为每个模块重复创建算法实例。

历史与实时指标→预测 / 回测→推荐快照→准入 / 副本执行→实测评估
先区分四种信息

观测值来自指标；容量估计属于推断；未来需求属于算法预测；API 写入、实际副本和 Pod Ready 属于执行结果。阅读推荐时，应结合当前用量、预测需求与实际就绪容量分别判断。

02快速开始

第一次使用，先借助演示了解“数据 → 预测 → 推荐 → 评估”，再接入自己的工作负载。每一步都能看到明确结果，先在 Observe 模式完成验证。

1. 体验一个完整的演示模块

在数据源相关页面创建演示，平台会准备合成指标和演示模块。查看历史趋势、预测、回测和推荐，理解各页面之间的关系。演示适合熟悉操作，数值不代表实际业务效果。

2. 接入自己的指标

添加 Prometheus 数据源并测试连接，为 CPU、内存、请求量等指标建立映射。检查查询范围、单位、历史窗口与缺样情况，确认数据确实属于目标工作负载。

3. 创建工作负载模块

选择目标命名空间和工作负载，关联指标来源与阈值，配置预测周期、资源及副本边界、固定周期和兜底值。算法配置在算法管理中统一维护，模块自动使用已启用算法。

4. 比较预测，审查推荐

运行采集、预测与滚动回测，查看误差、峰值低估、评分及排名。进入 Recommend 后，检查资源与副本建议、决定性约束、采用来源及降级原因。目标时间到达后，再用实测结果评估。

5. 验证后逐步开放执行

在测试环境分别验证新 Pod 资源准入与副本伸缩，完成权限、安全边界和故障回退检查后，再授权对应模式。执行后继续观察实际副本、Ready 状态和资源表现。

第一次接入的检查清单

数据连接正常、指标语义一致、历史样本足够、回测可比较、推荐可解释、兜底值已确认。Admission 与 Auto 的系统开关默认关闭。

尚未安装平台？展开部署准备与启动命令

1. 准备源码与工具

准备 Git、与 go.mod 匹配的 Go 工具链（当前声明为 1.27.0），以及管理前端 web/package.json 指定的 Node.js 与 pnpm。web/ 是独立 Git 仓库，根仓库忽略该目录，克隆后需另外准备前端源码，才能构建嵌入式管理界面。

2. 构建管理界面与后端

在仓库根目录执行。示例按 Bash 环境书写；Windows 可使用 Git Bash，并将后续可执行文件命名为 kube-resource-fcst.exe。

BASH / REPOSITORY ROOT
# 安装管理前端依赖（web/ 源码需已准备好）
cd web
pnpm install --frozen-lockfile
cd ..

# 构建前端并嵌入 Go 静态资源目录
make package-web
mkdir -p target/bin
go build -o target/bin/kube-resource-fcst ./cmd

3. 配置与显式迁移

参考根目录 config.yaml 配置数据库、监听地址与日志。默认示例使用 SQLite，服务端口为 20001。部署时设置稳定的 JWT 密钥与凭据加密密钥；保留原有数据库路径和 KUBE_RESOURCE_FCST_SECRET_KEY，避免加密凭据失去可读性。

BASH / FIRST INSTALLATION
# 首次安装：执行迁移并启动 server
target/bin/kube-resource-fcst server --config config.yaml --migration

# 停止上一步的 server 后，启动 API 与任务引擎
target/bin/kube-resource-fcst all --config config.yaml

访问 http://localhost:20001。也可以分别运行 server 与 job。已有安装先备份数据库，再审阅 --upgrade 的清理范围；该选项会删除已退役模块的数据表，普通启动不会执行该清理。

模块、指标、算法如何关联？

模块定义“为谁预测”：一个 Kubernetes 工作负载及其调度边界。指标定义“依据什么预测”：CPU、内存、请求量等来源及其统计口径。算法定义“怎样预测”：平台统一维护参数和采用门槛，自动应用到模块。三者共同决定预测输入与候选结果。

从一个模块，串起一轮业务操作

  1. 配置：选择工作负载，接入多指标，设定边界、固定周期、兜底值与运行模式。
  2. 观察：查看历史趋势、缺口和新鲜度，确认输入可信。
  3. 验证：比较各算法的预测、回测与实测评分，判断是否满足采用条件。
  4. 推荐：审查 CPU、内存与目标副本，了解建议由哪个约束、规则或兜底值决定。
  5. 执行与复盘：授权后检查准入或伸缩结果，把实际表现反馈到下一轮评估。

三类常见使用场景

  • 先做容量观察：接入有周期变化的负载，比较未来需求与当前资源，保持 Observe / Recommend，积累决策依据。
  • 为明确时段提供保障：为业务保障窗口设置固定周期值，注明时区、覆盖字段和边界，再检查命中记录。
  • 逐步开放自动伸缩：在非关键工作负载中验证建议、冷却和限幅，关注 Ready 副本与实际用量，确认稳定后扩大范围。

04数据接入与质量

Prometheus 数据源由统一客户端访问。指标映射描述查询与标签范围；数据集定义粒度、聚合、精度、换算与缺失处理。模块可以同时配置 CPU、内存、吞吐、OOM、JVM 等来源，并为各来源设置阈值。

真实接入前核对五件事

  • 范围：Namespace、工作负载、容器标签是否真实存在，查询结果是否属于目标模块。
  • 语义：工作负载总 RPS 与单 Pod 吞吐分开，requests / limits 与实际用量分开。
  • 单位：CPU、内存、速率的换算保持一致，避免将核数、毫核、字节和 MiB 混用。
  • 时间：采样周期、历史窗口、预测视野与数据新鲜度满足算法输入要求。
  • 质量：确认缺样、覆盖率、异常值和降级阈值；样本不足应跳过或回退。

内置 PromQL 预设可作为接入起点。不同集群的指标标签可能不同；若查询无数据，检查标签与过滤条件是否匹配实际序列。

时间统一按 UTC 存储；固定调度周期按明确的 IANA 时区解释。前端按配置显示，不能用浏览器本地时区静默改变调度含义。

05算法管理与预测

当前支持下列 14 种算法，可在算法管理中统一启停、调整参数与权重，并设置采用门槛。模块自动使用已启用的候选；列入目录不代表在真实业务中优于基线。

算法方法与用途关键边界

EWMA指数平滑，强调近期观测平滑系数与 span 按 schema 约束配置
Holt-Winters建模水平、趋势与季节性周期长度、趋势与阻尼需结合回测

统一配置与自定义算法

在算法管理中设置启用状态、参数、权重与采用门槛。模块自动使用已启用算法。管理员也可以基于内置算法创建派生算法，或定义带数值 / 布尔参数的公式算法；公式保存前会进行试算，修改实现或参数会影响版本与晋升资格。

使用时关注哪些结果？

  • 历史是否足够：样本不足或输入质量较差时，查看跳过与降级原因。
  • 是否满足业务窗口：历史窗口、预测周期与未来视野应与实际资源准备时间匹配。
  • 是否值得采用：结合回测、实测误差、峰值低估和采用门槛判断，不能只看模型名称或复杂度。
  • 改参数后是否仍然有效：配置变化会影响版本与晋升资格，应重新检查验证结果。

支持多指标输入的算法可以利用其他指标的历史信息。不支持的算法按自身能力预测；所有方法都需要通过相同业务窗口的回测比较，不能使用真实未来值提前验证自己。

06回测与模型选优

模型先在历史上按时间滚动验证，再用到达的真实观测进行评估。训练区间始终在预测原点之前，回测窗口与预测视野应与实际决策场景一致。

维度解释阅读方式
WAPE绝对误差总和相对于实际值绝对总和的比例比较同一数据与窗口下的预测误差；零分母按实现处理
峰值低估关注模型低估峰值需求的风险平均误差下降也可能伴随峰值风险增加
综合评分与排名结合资源维度准确度、OOM 扣分和完整度等信息结合评分明细、配置权重和模型资格阅读
实测回填预测目标时间到达后，与采集的真实观测关联未来时点尚未到达时，不能将空白评估当作零误差

模型采用还受晋升资格、最低分、新鲜度和切换滞后等条件约束。挑战者需经过基线对照；排名领先不等于立刻切换。平台保留当前排名、历史排名、评分明细与训练记录，帮助追溯建议的来源。

预测表现随负载规律、数据质量与预测窗口变化。结合自己的业务数据比较误差、峰值低估和执行后的资源表现，再调整采用门槛与策略。

07决策与执行

资源建议与副本建议分别计算

固定副本模式按峰值、余量与单 Pod 容量换算；动态模式综合吞吐、CPU、内存及 JVM 堆压力等约束。各算法的峰值低估可用于修正需求，副本建议受上下界、平滑与防抖限制。历史估计的单 Pod 容量属于推断值，需通过压测核验。

把目标副本建议用于弹性伸缩

在模块中设置最小与最大副本、扩缩容步长和冷却时间。开启经过授权的 Auto 模式后，由 Operator 根据有效建议调整目标工作负载；执行记录用于核对目标、实际与 Ready 副本，以及暂停或失败原因。

日常使用可直接以平台模块作为配置入口；需要声明式管理的环境也可使用 PredictiveScaler。两种方式都必须保证一个工作负载只有一个副本控制者，不能与 HPA、KEDA 或重复的 scaler 同时调整同一目标。

新 Pod 的资源准入

资源准入在创建 Pod 时读取最新有效建议，调整 CPU / 内存 requests，以及配置允许的 limits 比例。查看准入记录可核对采用结果与原因。缺少模块、推荐不可用或平台不可达时，应保留原资源配置，避免阻塞发布。

资源准入作用于新建 Pod；运行中的 Pod 需要通过新建或滚动更新应用资源配置。自动调低内存 limits 仍需独立回测、安全检查与授权；不能由点预测直接触发。

08安全与回退

资源建议不仅要有效、未过期，还必须符合你设定的范围与授权。遇到数据或模型异常时，平台记录原因并按规则降级；需要人工接管时，可对模块启用旁路，保留原值。

机制作用与限制
渐进模式Observe → Recommend → Admission → Auto；模块模式与系统授权共同约束写入
全局开关资源准入与自动伸缩默认关闭，管理员授权后才可应用；关闭后停止后续应用，设置生效存在短时缓存
模块旁路Bypass 保留原值，操作需要原因并留审计记录
字段级降级旁路 → 固定周期 → 合格算法 → 模块 Fallback → 保持原值；各字段独立判断，全部值仍受安全校验
OOM 保护OOM 地板对除 bypass 外的来源生效，受模块上限约束，推荐详情记录原因
恢复滞后连续健康周期达到恢复要求后退出降级，避免故障恢复时频繁切换
执行边界副本硬上限、步长与冷却约束；缺失或过期决策冻结危险动作

需要停止自动行为时

  1. 立即对目标模块启用 Bypass，并记录原因。
  2. 关闭对应系统开关，将模块恢复为 Recommend 或 Observe。
  3. 检查推荐快照、准入记录、扩缩容报告与实际资源状态。
  4. 修复数据或配置后重新回测，再按受控流程恢复授权。

系统开关和旁路阻止后续动作，不会自动撤销已经发生的副本或资源变更。已有资源的恢复应结合业务状态和审计记录执行。

09监控与管理支撑

日常运维既要判断“平台是否在正常运行”，也要回答“建议为什么变化、操作由谁发起”。监控指标、任务中心、权限管理与审计共同支持这些工作。

运行监控：发现链路停在哪一步

在监控指标中查询历史用量、预测与实测趋势，检查数据源状态、推荐年龄、算法表现和降级情况。结合目标、当前与 Ready 副本判断伸缩状态，避免将“已提交调整”当作“服务容量已就绪”。曲线与数据点可以帮助复盘，也可按页面支持的方式导出。

任务中心：检查周期任务与异常

查看任务定义、调度与执行记录，定位采集、预测、回测或评估是否正常完成。发生失败时先核对错误与输入，再按任务机制处理重试；不要因某次任务完成就跳过对数据新鲜度和结果质量的检查。

权限与系统参数：管理谁能改变策略

通过用户、角色、菜单和 API 权限分配访问范围。系统参数维护全局配置与安全开关，算法与模块页面管理各自策略。外部目录认证可在系统管理 → 系统参数 → LDAP 配置连接、用户/组查询与角色映射；本地账号可作为目录故障时的应急入口。

保留与导出

按业务复盘周期确认历史指标、预测、评估、推荐、执行与日志的保留要求。审计导出用于离线核对，相关操作留痕。数据和日志中的凭据应受保护，API 凭据按用途配置最小权限。

部署参考与外部监控接入

平台需独立部署，官网不运行管理服务或连接集群。部署前核对数据库、地址、证书、密钥与集群权限，备份数据库和稳定的凭据加密密钥。

配置指标监听后可接入 Prometheus，使用 /metrics、/healthz、/readyz 观察运行状态。指标用于监控，不能替代实际执行结果。

10适用范围与使用边界

选择接入方式和运行模式时，先明确管理对象、数据口径以及资源变更的作用范围。

范围如何使用
单集群管理围绕一个 Kubernetes 集群中的工作负载管理预测与资源策略，不承担跨集群迁移或多云调度。
容量估计历史推断的单 Pod 容量用于辅助计算，不能视为真实最大承载能力；应结合业务压测与 SLO 设定边界。
资源变更准入建议作用于新建 Pod；副本调整由 Operator 执行。两者按授权分别启用。
副本控制权一个工作负载只保留一个副本控制者。切换 HPA、KEDA 或本平台前，先停止原有控制。
内存保护结合 OOM、内存峰值与资源上限审查建议。调低内存 limits 前，需要独立评估风险并授权。
预测与就绪未来需求、目标副本与实际 Ready 容量分别阅读；决策提前量应考虑采集周期和 Pod 就绪时间。

11常见问题

官网能直接作为管理控制台使用吗？

官网提供功能介绍与使用指南。管理控制台需要单独部署，用于连接数据源、管理算法与模块、查看结果和授权执行。

可以与 HPA / KEDA 同时控制一个工作负载吗？

不能。目标 replicas 必须只有一个控制者。切换执行后端前先停止原控制器并释放字段所有权，再验证新控制器的边界。

如何选择合适的预测算法？

从基线算法开始，在相同历史窗口和预测视野下比较误差、峰值低估与运行耗时。结合实际负载和资源预算设置采用门槛，再通过后续实测持续评估。

为什么接入后没有预测或排名？

先检查数据源连接、PromQL 标签与单位、模块启用状态、历史窗口和算法最小样本，再检查任务记录、预测新鲜度、实测目标时间及资格门槛。缺少可比较实测时，不应伪造评分。
