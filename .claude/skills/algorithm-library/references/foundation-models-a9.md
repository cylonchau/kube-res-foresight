# A9 小型时序基础模型离线评估（2026-10-29）

结论先说：**Chronos-2 在这份数据上和平台自带的最好统计算法大致打平，没有拉开差距；现成镜像里的 TimesFM 2.5 输出异常，不可用。现在不值得为它引入外部服务。** 数据只有约 5 小时（322 点）、4 个合成负载 × CPU/内存，不是生产结论。

## 做法

- **不自己封装**：用 Docker Hub 上现成的第三方镜像 [`kingfs/unitshub`](https://hub.docker.com/r/kingfs/unitshub)（每个镜像一个模型，REST：`POST /models/current/invoke`，Bearer 密钥）。镜像：`chronos-0.4.0`（Chronos-2，2.85 GB 解压后）、`timesfm-0.4.0`（TimesFM 2.5，3.71 GB）。模型权重已打在镜像里，启动约 25 秒就绪，仅用 CPU（本机 12 核）。
- **只有预测，没有训练接口**：两个模型都是零样本，“周期提交数据训练”在这里等于每次预测都带上截止点之前的全部历史。需要训练/微调（如 Granite TTM 的少样本微调、AutoGluon 微调 Chronos-Bolt）得自己封装服务，本轮没有做。
- **评估工具**：`scripts/tsfm-eval`（Go）。读平台库的**副本**（只读打开），用平台自己的 `backtest.Run` 在**同一批起点**上给所有模型打分，与 `scripts/baseline` 同口径；基础模型每个起点只看到起点之前的数据。
  ```
  docker run -d --name ut-chronos -p 18000:8000 -e MODEL_TYPE=chronos -e API_KEY=local kingfs/unitshub:chronos-0.4.0
  docker run -d --name ut-timesfm -p 18001:8000 -e MODEL_TYPE=timesfm -e API_KEY=local kingfs/unitshub:timesfm-0.4.0
  go run ./scripts/tsfm-eval -db <平台库副本> -horizon 10 -cutoffs 10
  ```
- 对照算法用默认参数：naive、ewma、holt_winters、theta、hist_percentile、peak_envelope、combination。**ridge_ar、gbdt 因必填参数 `lags` 没有跑；knn 在 `load-web` 上历史不足被跳过**，所以它们不在对比里。
- 数据：平台库副本里 `load-web/api/batch/cache` 的 CPU 与内存各一条，步长 60 秒；缺口处只取最近一段连续数据，共 322 点，每条序列 7 个起点、70 个评分点。

|---|---|---|---|---|---|

| combination | 0.164 | 0.308 | 0.192 | 0.600 | <1 ms |

## 读数

1. **Chronos-2 的 WAPE 最低**（10 步 0.145，其余最好 0.163），但按“低估更贵”的低估加权误差排只排第 4，与 theta/combination/ewma 的差距在这 70 点样本下不足以排先后。它没有在这份平滑的合成负载上显示出统计算法做不到的东西。
2. **Chronos-2 的 P90 线覆盖率 0.90，达到名义水平**，峰值低估 0.059，比平台默认的 P90 保形包装（A3，覆盖率约 0.83–0.89）略好，但 WAPE 约翻倍（故意偏高），与 hist_percentile 同类取舍。这是它最有用的一点：不用自己标定就给出校准较好的上界。
3. **TimesFM 2.5（该镜像）不可用**：在一条光滑正弦上单独调用时第 2 步就跳到 72（真值约 58），回测里覆盖率仅 0.33、低估加权误差 1.0。这是**该镜像服务的输出**有问题（可能是它的封装或输入处理），**不能当作 TimesFM 模型本身的结论**；没有查原因。
4. **成本**：CPU 上每次预测 0.1 秒（Chronos）和约 1 秒（TimesFM）；平台统计算法不到 1 毫秒。每个模块每次运行的预测次数不多，延迟不是障碍；真正的成本是 2.85 GB 镜像、单独部署、多一个故障点，以及 Operator 的“预测不依赖外部服务”要变成“外部服务不可用时降级”。
5. 数据太短：5 小时、合成负载，没有日周期，基础模型擅长的“识别周期形状”在这里用不上。

## 建议

- **现在不接入**：收益在这份数据上看不出来，代价是新的外部依赖。
- 想继续评估的话，先用**更长的真实历史**（至少几天，含日周期）重跑同一个命令；这一步不需要改代码。
- 如果之后要接入，只考虑 Chronos 的 P90 作为“上界”算法候选，接入方式是一个新的远程算法（走 forecast 注册表，超时/失败时回退到统计算法），而不是替换现有算法；要先决定能否接受外部服务和 2.85 GB 镜像。
- “周期提交数据训练”需要支持微调的模型（Granite TTM、AutoGluon 微调 Chronos-Bolt），不在现成镜像里，得自己封装；上一次尝试的自建镜像因 CUDA 依赖下载过慢（1.2 MB/s）中止，没有评估结果。

## 限制

第三方镜像 `kingfs/unitshub` 未做安全审查，评估只往里发数字，不含凭据；镜像版本 0.4.0（2026-10-22 发布）。结果为 5 小时合成负载上的 7 个起点，不能推广。
