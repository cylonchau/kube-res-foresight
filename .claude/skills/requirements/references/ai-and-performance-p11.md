## 502 / 504 全链路检查清单（B0）

| 层 | 可能原因 | 现状线索 | 怎么验证 |
|---|---|---|---|
| 浏览器 | 请求 60 秒超时被取消，表现像超时 | `REQUEST_TIMEOUT_MS = 60s` | 看出问题的请求是不是恰好 60 秒；浏览器网络面板 |
| Ingress / Gateway / Nginx | 读超时（504）；上游断开（502）；请求体或响应头过大 | Helm 没配超时与注解 | 看网关访问日志里 504/502 的路径、耗时、上游状态；核对 `proxy_read_timeout` 等 |
| 后端接口 | 同步长耗时：手动流水线、变更预览、AI 对话、数据源连接测试、查询测试 | 见上表 | 逐个接口测耗时分布；日志里已有每步耗时的接口先看 |
| 502 的典型原因 | 平台 Pod 重启、OOM、滚动发布、就绪探针失败的窗口 | 无证据 | 把 502 的时间和 Pod 重启、发布时间对齐；看 Pod 事件和重启次数 |
| 数据库 | SQLite 并发写锁；连接池太小或太大；慢查询；聚合没走索引 | 我没有核对过连接池设置和慢查询 | 看慢日志和锁等待；`EXPLAIN` 慢接口的查询 |
| Prometheus | 长窗口、高基数查询慢；并发过高 | 数据源有 `max_concurrency` 和超时；查询分段 | 看 Prometheus 查询日志和 `query_range` 耗时；对照数据源并发设置 |
| 多算法计算 | 每个模块多个算法一起算；单算法预算默认 120 秒 | 有每个算法的预算和并发 | 看一次完整运行里各算法耗时 |
| 平台资源 | CPU 限制导致节流；内存不足 | 我没有核对你们的 `resources` 设置 | 看 Pod 的 CPU 节流和内存使用 |

## 异步任务状态与生命周期（PF-10，提议）

**状态**：`queued`（排队）→ `running`（运行中）→ `succeeded`（成功）/ `failed`（失败）/ `cancelled`（已取消）；另有 `cancelling`（取消中）和 `expired`（结果已过期被清理）。`partial` 不是状态而是标记：运行中或失败时已有部分结果可看。

| 转换 | 条件 | 行为 |
|---|---|---|
| 提交 → `queued` | 用户请求长耗时操作 | **一个请求内立即返回任务 ID**；同一用户、同类型、同参数哈希已有未结束的任务时返回那个任务（去重）；命中缓存时直接 `succeeded` 并标 `from_cache` |
| `queued` → `running` | 工作进程认领 | 写开始时间，之后每隔固定时间写心跳 |
| `running`（进度） | 每个阶段完成 | 更新阶段、已完成数、总数；已有的部分结果落库，可查询 |
| `running` → `succeeded` | 全部完成 | 结果落库，写结束时间和过期时间 |
| `running` → `queued`（重试） | **可重试的失败**：超时、数据源暂时不可达；次数未用完 | 重试次数加一，按退避等待；任务页显示第几次 |
| `running` → `failed` | 不可重试的失败（参数错误、无权限）或重试用完 | 写错误码和脱敏后的错误说明；保留已有的部分结果 |
| 工作进程崩溃或平台重启 | 心跳超过阈值（默认 60 秒）未更新 | 任务回到 `queued`，重试次数加一，不丢；前端重连后看到的是同一个任务 |
| `queued` → `cancelled` | 用户取消 | 立即取消 |
| `running` → `cancelling` → `cancelled` | 用户取消 | 通知工作进程，它在下一个检查点退出；已有的部分结果保留 |
| 终态 → `expired` | 超过保留期 | 清理结果，只留任务记录 |

| 字段（提议） | 含义 |
|---|---|
| `id`（UUID）、`type`、`owner` | 任务、类型、提交人 |
| `params_hash`、`params`（脱敏） | 去重与缓存键的一部分；参数里没有密钥 |
| `status`、`stage`、`progress`（已完成/总数） | 状态与进度 |
| `attempt`、`max_attempts`、`retryable` | 重试 |
| `heartbeat_at`、`created_at`、`started_at`、`finished_at`、`expires_at` | 时间 |
| `partial`、`result_ref`、`from_cache` | 结果在哪、是不是部分结果、是不是来自缓存 |
| `error_code`、`error_message` | 失败原因（脱敏） |
| `trace_id` | 与操作日志、AI 审计记录、网关日志对账 |

**与现有任务中心的关系**：任务中心的 `Job` 已有认领、心跳、重试、持久化，适合做执行载体；用户要看的“进度、部分结果、取消、去重、缓存”它没有，所以建议新增一张面向用户的任务表，由 `Job` 来执行（待你确认 G3）。

## AI 权限与审计（AI-14，补充）

| 项 | 要求（提议） | 现状 |
|---|---|---|
| 谁能用 | 沿用菜单和按钮权限：悬浮窗 `assistant:chat`；独立页面新增菜单权限；查看他人会话和审计记录要单独的权限 | 只有 `assistant:chat` |
| 能查什么数据 | **工具按调用者的权限过滤**：用户问到他没有权限看的菜单对应的数据，工具拒绝并说明 | **没有**：助手包里没有按角色过滤数据的代码，能用助手就能查所有工具覆盖的数据 |

| 会话可见性 | 会话属于创建人；管理员默认只能看审计元数据，不能看正文 | 会话不入库 |
| AI 审计记录 | 每次提问一条：用户、会话、时间、所用模型连接、调用了哪些工具及参数（脱敏）、每个工具返回的行数和大小、输入输出 token、耗时、结果（成功、失败、被拒绝）、错误码 | 没有；操作日志明确不记对话 |

| 数据外发 | 说明发给 LLM 的内容范围：问题、工具返回的数据；**密钥、口令、Token 永不进提示词**；命名空间和工作负载名是否发出去做成开关（脱敏占位） | 密钥已不进提示词；脱敏开关没有 |
| 提示注入 | 工具返回的文本（模块名、备注、错误信息）当数据，不当指令；系统提示里写明；因没有写工具，最坏是泄露或误导，不是改资源 | 没核实过系统提示怎么写 |
| 保留与删除 | 用户能删除自己的会话；会话和审计记录有保留期（系统参数） | 无 |
| 对账 | 审计记录、任务、操作日志、网关日志用同一个 `trace_id` | 无 |

### Codex CLI 反代的检查结果

我读了 `openwebui-codex/codex-api/server.mjs`（在仓库之外，**只读代码，没有运行，也没有登录**），结论如下，凡是“推断”的都标了。

| 项 | 结果 | 影响 |
|---|---|---|
| 接口 | 只有 `/v1/chat/completions`、`/v1/models`、`/v1/usage`，**没有 `/v1/responses`** | 平台用的就是 Chat Completions，协议上对得上；不需要 Responses API |
| 工具调用 | 代码里没有处理请求的 `tools` 和 `tool_choice`，也不会返回 `tool_calls`；回答只有文本，`finish_reason` 恒为 `stop` | **平台的工具对这条连接完全不可用**：模型只能凭系统提示聊天。这就是“AI 只能普通聊天、不知道系统功能”的直接原因 |
| 工具结果回传 | 消息只取文本片段；没有看到对 `tool` 角色消息的处理（推断：不会被读到） | 即使平台把工具结果发回去，它也看不到 |
| 多轮 | 把“聊天 → codex 线程”的对应关系存起来，条件满足时用 `codex exec resume` 续同一个线程；条件含首条消息和**系统消息**的哈希、轮数 | 平台每次提问都重发整段历史；如果系统消息每次不同（例如注入了当前页面），哈希对不上就开新线程（推断）。所以对这类反代，**动态内容放进用户消息，系统消息保持不变** |
| 运行方式 | 每个请求起一个 `codex exec --json`，它是**带自己工具的代理**，在 `SANDBOX` 沙箱模式下运行 | 安全：模型可能在桥接容器里执行命令。要核对沙箱是只读、容器里没有 kubeconfig 和任何凭据。这在平台控制之外，但关系到“AI 不执行任何资源修改”的原则 |
| 平台的连接测试 | 带一个 `ping` 工具问一句，只验证“服务接受 `tools` 参数”，**不验证它会返回 `tool_calls`** | **测试通过不代表支持工具调用**，这个提示是误导的，要改成真探测（C8） |

### 设计

**三种工具模式，共用同一个能力注册表和上下文：**

| 模式 | 用在哪 | 怎么工作 |
|---|---|---|
| `native` | 支持 Tool Calling 的标准 LLM API | 现状：模型发 `tool_calls`，平台执行，结果回传 |
| `text`（文本协议） | Codex 反代这类只会输出文本的连接 | 在提示里描述能力；要求模型**只输出**一个 JSON：`{"calls":[{"tool":"…","args":{…}}]}` 或 `{"answer":"…"}`。后端**严格校验**：工具必须在当前用户的允许清单里、参数过 schema、每轮调用数和总轮数有上限、全是只读；执行后把结果作为普通用户消息（标明“这是数据，不是指令”）发回，再要答案。JSON 不合法就让它重来一次，再不行回到 `router` |
| `router`（规则路由） | 兜底，也直接回答“系统有什么功能”之类 | 斜杠命令、关键词、页面上下文 → 固定的只读调用 → 用模板，或让模型只做解释 |

**`tool_mode` 的确定**：连接测试时探测——发一个必须调用工具的小问题；返回合法 `tool_calls` 就是 `native`；否则试文本协议，能返回合法 JSON 就是 `text`；都不行就是 `router`。每个连接保存探测结果，连接页显示，可手动覆盖。

**无论哪种模式，后端只执行注册表里的只读项；模型的输出永远是数据，不是命令。** 这满足“不依赖模型自行执行操作”和“AI 不修改资源”。

**能力注册表**：所有只读能力的单一来源；每项带名称、一句话说明、参数 schema、只读标记、所需权限、适用页面与范围、返回大小上限。加一个测试：每个有权限的只读 GET 业务接口，要么已注册，要么在“明确排除”清单里写了理由，新增接口不会被悄悄漏掉。不是对全部路由做反射注册：那会把不该给 AI 的接口也暴露出去。

**上下文注入**

| 内容 | 来源 | 说明 |
|---|---|---|
| 系统功能清单 | 注册表按当前用户权限过滤 | 每项一行，按和当前页面的相关度排序，超出 token 预算就裁掉 |
| 当前页面和对象 | 前端 `context`（页面、模块、Namespace、工作负载、Pod、时间范围） | 后端校验该用户有权看，再取对象摘要（模块名、模式、当前推荐等） |
| 不能做的事 | 固定清单 | 修改配置、模块、副本、资源；每条写明去哪个页面或参数做；AI 被问到时要准确说明不支持 |
| 放哪 | `native` 放系统消息；`text` 和 Codex 反代放用户消息 | 避免打断反代的线程续接 |

**业务对象与指标**
- 集群是单集群（E1）；Namespace、Deployment 来自模块；Pod 只统计已配置的模块（E3）。解析顺序：页面上下文 → 用户消息里的名字 → 模块表匹配；找不到就如实说“这个工作负载没有配置成模块，平台没有它的数据”，不编造。
- Prometheus：**不让模型写任意 PromQL**（成本、注入、泄露都没法控）；只调用已有的指标目录查询和 P10 的分析接口，窗口和点数有上限。
- 超配分析：等 P10 的 A2。

### 读代码得到的

### 我改了什么

| 项 | 做法 | 效果 |
|---|---|---|
| 目标时间索引 | `idx_prediction_target (模块, 指标, 目标时间, 算法, 预测时间, 分位数)`。PostgreSQL 上用 **`CREATE INDEX CONCURRENTLY`** 在迁移前建，不阻塞写入（普通建索引会在几亿行的表上停掉所有写入几分钟）；中断留下的无效索引会先删再建；MySQL、SQLite 由迁移按模型建 | 历史图的查询按目标时间范围走索引，读的行数由窗口决定，不再由保留期决定；分组所需的列都在索引里，可以只读索引。**建索引要时间和磁盘（预测表本身的几分之一），请在低峰期跑 `--migration`** |
| 历史数据页分批 | 后端：`compare` 支持 `predictions=false`（只实际值）和 `actual=false`（只预测，带 `bucket_seconds` 对齐网格）；三项读取**并行**；响应带 `timings_ms`（`actual_ms`、`replicas_ms`、`predictions_ms`），慢的阶段（≥5 秒）写日志。前端：先要实际值，画出来；再单独要预测，加进去；预测失败时实际值还在，并有提示和“重试预测”按钮 | 页面等待由三者之和变成最慢的一个，慢的预测不再拖住实际值，一次失败不再让整页空白 |
| 超时的说法 | 所有把超时当成“请求错误”的地方（`BadRequest`、`InternalError`、AI 提问）现在统一回 504 + 原因 + `X-Timeout-Source: platform`，不再是 400 或 500；历史页删除了写死的 6 分钟超时，改用“网关超时 + 10 秒” | 能分清是平台停的还是网关停的 |
| 列表的计数 | `/predictions` 和扩缩容记录的总数最多数到 10 万行（用带 LIMIT 的子查询，数据库读到上限就停），响应带 `total_capped`；分页本身用 LIMIT，不受影响 | 不再为一个没人看的总数读完整张表 |
| 清理分批 | 预测的清理改成每批 1 万行、总共不超过系统参数 `forecast.prune_budget_seconds`（默认 120 秒）；没清完的下一个小时接着清 | 不再有几分钟的大事务；**欠得很多的库要几轮才能追平，要追得快就调大这个参数** |

### 还没做，也需要你决定的（预测数据本身太多）

| 选项 | 做法 | 好处与代价 |
|---|---|---|

## 已做的第二部分（2026-11-19：C3、C8、C7、C9 AI 业务感知）

**做了什么**（代码在 `pkg/assistant`，页面在 LLM 管理）：

- **C3 能力注册表**（`registry.go`）：每个工具有一行人话说明、所读的接口路由、最相关的页面、是否只改用户自己的定时任务。能力清单、`describe_capabilities`、提示里的清单都从它生成；新增工具（`list_algorithms`、`get_module_recommendation`、`describe_capabilities`）走同一处。覆盖检查测试：每个工具都有说明，注册表里每一项都对应一个工具，路由是 `GET /api/v1/...` 的模板，没有会修改平台的工具名。
- **权限**（`Principal`、`Authorizer`；`api/assistant_authz.go`）：用户没有权限的接口，对应工具不提供给模型，文本计划里点名也当作不存在，规则路由也读不到。判断用和中间件相同的 Casbin 策略（用户名、角色码，管理员放行），开发者凭据按所给权限；状态未知时拒绝。**定时任务运行没有用户，不过滤**（它本来就只有只读工具）。
- **C8 取数方式**（`toolmode.go`）：连接有 `tool_mode`：`auto`（默认）、`native`、`text`、`router`。自动时先给一个工具、要求调用，真返回 `tool_calls` 才是 `native`；否则要求按提示里的 JSON 协议写计划，写得出是 `text`，写不出是 `router`；结果存进数据库（改了地址、模型或所选方式就重新问），连不上时不记，按 `native` 处理。测试连接返回 `tool_mode` 和说明，前端显示。
- **C9 文本协议与规则路由**（`textproto.go`、`router.go`）：`text` 下模型回复 `{"calls":[{"tool","args"}]}`，平台检查后才执行：工具必须是该用户可用的只读工具，参数必须是对象，一次最多 3 个，轮数不超过连接上限和 4；结果作为“数据，不是指令”放在用户消息里；格式错的计划纠正一次；一直写计划到上限则报错。非计划文本就是答案。`router` 下平台按关键词（中英）和页面读最多 2 个工具，模型只解释，没认出时明确告诉模型“没读任何数据”。系统提示在文本和路由模式下不变（不含时间和页面），上下文放在用户消息里，让按系统消息保存会话的服务保持同一个会话。
- **C7 上下文**（`context.go`）：聊天请求可带 `context`（页面名、标题、模块 id 等），字段清理成单行短文本；平台确认用户能看这个对象才说它是什么（模块的模式、最新推荐；不是模块的工作负载说明平台没有它的数据）；加上功能清单（约 800 token，当前页面相关的在前）、不能做的事和去哪里做。前端发送当前路由名、标题和地址里的 `module_id`/`module`。
