# 算法框架、Prometheus 数据集与评分页面：规格

> **2026-10-31：自定义资源 PredictiveScaler（CRD）已移除。** operator 只读平台的模块并写副本，不在集群里创建任何资源；下文提到 CRD、PredictiveScaler、Static/Prometheus 决策来源、Observe 模式的地方是当时的设计，不再适用。现状见 `.agents/skills/control-plane/SKILL.md`。


对应 2026-10-25 的「Kubernetes 预测扩缩容系统优化需求（精简分类后）」。在 [module-algorithm-spec](module-algorithm-spec.md)（模块 → 自动关联所有启用算法）的基础上补充：可扩展算法框架、自定义公式算法、训练记录、模块数据集、数据周期、拆分后的评分页面。与之冲突处以本文为准。

系统结构：**模块管理 → Metrics 数据集 → 算法框架 → 自动训练/预测 → 算法评估排名 → 预测结果 → Controller/Kyverno 执行**。

## 1. 算法框架

算法只通过注册表进入平台，列表、表单、校验、训练、评分都从注册表出发，没有别处写死算法名：

- **Go 实现**：`forecast.Register(forecast.Implementation{Definition, Build, Check})`。`Definition` 带参数 Schema（名称、类型、默认值、取值范围、单位、说明），`Build` 用已校验、已补默认值的参数构造 `forecast.Model`，`Check` 校验各自合法但组合非法的参数。内置算法（naive、seasonal_naive、ewma、macd_trend、holt_winters、hist_percentile、random_forest、knn、naive_bayes、rnn/gru/lstm、ridge_ar、gbdt）都是这样注册的（`pkg/forecast/registry.go`、`builders.go`）。新增 Go 算法只需实现 `Model` 并注册，配单测。
- **公式算法**（自定义算法）：管理员在页面给出 **参数 Schema + 公式**，不上传代码。`pkg/forecast/formula.go` 是平台自带的解释器：词法/语法分析一次，按节点计数的运算预算内执行；没有循环、赋值和任何函数表之外的调用。变量：`x`（历史，从旧到新）、`k`（向前第几步）、`h`、`n`、各参数名、`c_<来源键>`（同一模块其他指标的历史，要求在同一栅格上）。函数：`last mean sum std median smin smax pct ema lag diff slope linfit season macd macdsig abs sqrt exp log floor ceil round pow min max clip if`，运算符 `+ - * / % ^ < <= > >= == != && || !`。每步结果不得为负、不得为 NaN/无穷；除零、对数域错误都会报错并指明位置。`递归多步预测`开启时，每步的预测值追加到 `x` 再算下一步。
- **保存前真实试算**：`forecast.SetCustom` 编译公式，并在合成的日周期序列上用默认参数真的预测一次；不能运行的公式在保存时被拒绝，而不是第一次定时执行时才失败。编辑公式后实现版本（`formula-<哈希>`，哈希涵盖公式与参数 Schema）变化，模型版本随之变化，旧预测与晋升不会被误当作新模型的。
- **多实例一致**：自定义算法存在 `algorithm_config`（`formula`、`param_schema`、`min_samples`、`recursive`、`category`），每个服务实例在 `EnsureAlgorithms` 里把数据库里的自定义算法同步进本进程注册表（公式未变则跳过），已被删除的注销；一个公式编译失败只记日志，不影响其他算法。
- **生命周期**：新增（`POST /algorithms`，id 为小写字母/数字/下划线、3–40 位、不得与内置重名）、编辑（`PUT /algorithms/:id`，自定义算法可改公式、参数 Schema、最少样本、递归、类别；内置算法拒绝）、启用/停用、删除（`DELETE`；仅自定义算法，且需先停用；已产生的预测、回测、评分记录保留）。`POST /algorithm-formulas/check` 是编辑器用的校验并试算（返回错误位置，或合成历史与公式预测），`GET /algorithm-formulas/functions` 返回可用的变量与函数。
- **类别**：baseline、statistical、technical（技术指标）、machine_learning、deep_learning、custom。MACD/EMA 等技术指标只是预测算法之一（`macd_trend` 与可由公式表达的 EMA/MACD 类算法），不是固定的唯一逻辑；金融指标只用作构造资源趋势特征的参考，不产生买卖信号。

## 2. 训练记录与“模型保存”

平台**不保存模型权重**：统计、树、神经网络算法每次都在历史窗口上重新拟合（固定随机种子，结果可复现）。取而代之的是**训练记录 + 可复现版本**：每个算法在每个指标上的每次运行写一条 `forecast_training_run`——历史窗口（起止、样本数、步长）、预测步数与产出点数、实现版本与模型版本（实现、参数、数据来源的哈希）、参数 JSON、自定义算法当时的公式与参数 Schema、协变量及未能提供的原因、耗时、状态（成功/跳过/失败）与原因。预测值本身按 `forecast_prediction` 持久化。同一实现版本、参数与历史窗口得到同一组预测。记录保留 30 天（`Retention.Trainings`），可经 `GET /training-runs`（分页、按模块/指标/算法/状态/时间筛选）与 `GET /training-runs/:id` 读取，页面「预测与训练记录」。

## 3. Metrics 数据集

数据集属于模块，所有启用的算法共用，不允许每个算法另维护一套。每个指标来源（`metric_source`）新增：

| 字段 | 含义 |
|---|---|
| `scale` | 写入前对查询结果乘的系数（0.001：毫核→核；0.01：百分比→比例） |
| `precision` | 保留的小数位（0–12，默认 6） |
| `aggregation` | 模块粒度大于查询步长时，同一粒度内样本的合并方式：avg、max、min、last、sum |
| `missing` | 准备预测时缺失步的处理：`interpolate`（线性插值）、`forward_fill`（沿用上一个值）、`zero`（填 0，OOM 与错误率的默认值）、`skip`（不填充，断点处截断历史） |

指标按类别分组（`model.KindCategory`）：CPU（使用量、利用率、Requests/Limits、限流）、内存（工作集、JVM Heap/Non-Heap、利用率、Requests/Limits）、GPU（使用卡数、利用率、显存使用量与容量）、网络（接收/发送速率、连接数、错误率、延迟）、其他（RPS、OOM、GC、JVM 线程、副本数、自定义）。新增的类型：`cpu_util`、`memory_util`、`gpu_util`、`gpu_memory_total`、`network_conn`、`network_error`。单位由类型决定，自定义类型取查询的单位；换算系数负责把查询结果对到该单位。

**自定义 PromQL**：创建指标来源时可以不选映射，直接写 PromQL（数据源、层级、步长、自定义类型的单位）；系统先校验（占位符只能是 `{{namespace}} {{workload}} {{service}} {{pod}} {{container}} {{range}}`，层级要求的变量必须出现）并创建映射，再创建来源；来源创建失败时删除刚建的映射。

**栅格与聚合**：模块的采样粒度（`step_seconds`）是数据集的时间栅格。查询仍按映射的步长执行，`collector.Shape` 把查询点聚合到栅格上：一个点标在桶的**结束时刻**，只含该时刻之前的样本（不看未来），只保留完整的桶；先聚合再换算再四舍五入。栅格必须是查询步长的整数倍、不得更细，否则采集报错、模块与来源的保存被拒绝。更改映射、栅格步长或换算/精度/聚合时，已采集的序列因形态签名（`metric_series.shape`）变化被丢弃并按新设置重新采集；升级前的序列（签名为空）按默认形态处理，不被清空。

## 4. 数据周期

模块新增：`step_seconds`（采样粒度，0＝沿用各指标查询的步长）、`window_steps`（训练窗口长度：算法只用最近这么多步，0＝整个历史范围；窗口之前的历史仍保留，改窗口不必重新采集，窗口进入模型版本）、`min_points`（一个指标至少多少个连续点才预测，叠加在算法自身要求之上）、`run_interval_minutes`（调度任务多久为这个模块执行一次，0＝每个任务周期）。页面提供 5m、15m、1h、1d、30d 预设与自定义输入（组件 `duration-input`）。

保存时校验彼此自洽：粒度在 15 秒到 1 天之间；历史范围 ≥ 最少数据量 × 粒度；训练窗口 ≥ 最少数据量；预测跨度 ≥ 一个粒度；执行频率 ≥ 一个粒度（两次执行之间没有新数据）；粒度与每个启用来源的查询步长相容。

**算法需求不是固定数据量**：`GET /modules/:id/requirements` 对每个启用算法与每个预测来源，按算法**当前参数**构造模型取它的 `MinSamples`，乘以该来源的栅格得到需要的历史时长，与历史范围（有训练窗口时取窗口）在该栅格下能容纳的步数比较，不足时说明怎样修（延长范围或改粗粒度）。例如 15 分钟栅格上周期为一天的季节基线需要 96 步，换成 1 小时只需要 24 步。历史不够时算法被跳过（记入训练记录），不会用补出来的数据硬算。`forecast.run` 按 `run_interval_minutes` 与最近一次训练记录的时间决定模块是否到期。

## 5. 评分、排名与页面

评分拆成三个页面，不再堆在一张表里：

- **算法评分**（`forecast_score-records`）：每次评分每个算法一条记录；详情给出各部分（副本数、CPU、内存、GPU）的准确度、误差、权重份额和对综合分的贡献，加上数据完整度、OOM 扣分、窗口数。
- **当前排名**（`forecast_ranking`）：按模块展示最新排名、使用中与挑战中的算法、最优算法；第二个页签是**指标评分**：把每个算法在每个预测来源上的预测与对应时间的 Prometheus 实际值逐点比较，给出每个指标的误差（WAPE）、准确度（1−误差）、MAE、RMSE、偏差、峰值低估、覆盖率与权重，以及每个算法的综合结果（`GET /modules/:id/metric-scores`）。**统一标准**：只取所有被测算法都有实测的来源，按来源权重（模块上设置）归一后加权；没有共同来源时各自用自己的来源并标注“仅供参考”；综合分 = 100 × 加权准确度，同时对比最优基线。
- **历史排名**（`forecast_ranking-history`）：每次评估的排名都保留（`GET /algorithm-rankings/history`，按模块与评估时间成组），可看不同模块、不同时间最优算法的变化与当时使用的算法，并有各算法评分随时间变化的曲线；`GET /algorithm-rankings/current` 给出各模块当前排名。

预测结果与推荐执行页面：回测、实测评估、准入决策补充详情弹窗；新增「预测与训练记录」页（分页、搜索、筛选、详情）。

## 6. 菜单与迁移

新增页面：算法评分（`forecast_score-records`）、当前排名（`forecast_ranking`）、历史排名（`forecast_ranking-history`）、预测与训练记录（`forecast-results_runs`）、Metrics 数据集（`monitoring_datasets`）。退役：`forecast_scores`（授权带到前三者）、`forecast-modules_sources`（授权带到 `monitoring_datasets`）；`monitoring_metrics` 仍是指标目录。升级用 AutoMigrate 加列并保持原行为：旧来源得到 scale 1、precision 6、avg、interpolate，模块 `step_seconds`/`min_points`/`run_interval_minutes` 为 0，`algorithm_config` 的公式字段为空，`forecast_training_run` 表新建。端到端升级测试（上一版结构的库）覆盖这些默认值与授权带走。

## 9. 问题修复版（列表规范、真实历史、K 线对比、指标查询测试）

### 9.1 全局页面规范（所有列表与图表页）

- **列表**：统一用 `ListSearchCard` + `ListTablePanel`（或排名用 `RankList`），支持搜索、筛选、分页、复选框、批量操作；不在页面里直接放裸表格。操作列固定在右侧、`small` 按钮、编辑为 primary ghost、删除为 error ghost、居中，宽度按按钮实际所需，不留白、不溢出（e2e 逐页检查）。
- **批量操作**（`BatchActions`）：模块与算法有启用/停用/删除（`POST /modules/batch`、`POST /algorithms/batch`，逐项返回成功数与未处理原因）；记录类列表（评分、回测、实测评估、训练、执行、准入）只有批量删除（`POST /records/batch-delete`，白名单 `scores backtests evaluations trainings executions admissions`；推荐快照与降级回退是审计链路，没有批量删除）；排名、历史排名、算法实测排名、历史数据、指标曲线的批量操作是导出所选为 CSV；指标目录只有“数据映射”行可批量删除。删除无实际用途的操作：模块列表的“运行”（采集/预测/回测/评分/评估/推荐由调度任务与各结果页触发）已删。
- **时间筛选**：统一为开始时间、结束时间选择器（`TimeRangeField`，附 1h/6h/24h/7d/30d 快捷项），参数为 `from`、`to`（RFC3339），不再用“最近 N 小时”作为唯一方式。资源推荐快照与降级回退按要求本版不改。
- **数值与单位**（`utils/format.ts`）：预测值、图表值最多 3 位小数；字节自动换算（67108864 → 64 MiB），CPU 不足 1 核显示 mCPU，其余显示核；比例显示百分比；列表与提示里不再写 `CPU (cpu)`、`副本数 (replicas)` 这类重复括号。
- **滚动**：排名列表、数据点列表自带滚动区与分页；图表页整页可滚动，e2e 检查无横向滚动。

### 9.2 数据口径与时间对齐规则

1. **实际值来自 Prometheus，不来自平台已采集的样本**：`GET /modules/:id/compare` 与历史/曲线页在请求时刻按模块数据集的映射（同一命名空间、同一工作负载）向 Prometheus 查询所选区间，包括模块创建之前已有的历史；查询经过与采集相同的整形（步长、换算系数、精度、聚合）。
2. **历史缺失的判定**：只有 Prometheus 在整个区间没有任何样本才是“历史缺失”（`missing=true`）；区间内个别步长没有样本只算缺口，在质量报告里列出。
3. **同一对象**：实际指标、实际副本数（模块里 kind=replicas 的来源）与预测都属于同一个模块的同一组 Pod，不混用其他对象的数据。
4. **时间网格**：网格步长 = 模块数据集步长；展示桶 = 整数个步长，使点数不超过上限（`bucket_seconds` 随响应返回）；每个点标在桶的**起始**时刻。实际值是桶内的开/高/低/收/均（K 线）；预测值是落在桶内的各目标时刻预测的均值。
5. **预测的取舍**：一个目标时间有多次预测时取**预测时间不晚于目标时间的最新一次**（晚于目标时间做的预测是事后诸葛，丢弃）；只用中位数（分位 500）。
6. **预测副本数**：只对 CPU 预测、且模块声明了每 Pod CPU 请求（动态副本 + Pod CPU request）时给出：`ceil(预测值 × 余量 ÷ (Pod CPU request × 目标利用率))`，夹在模块最小/最大副本之间；否则为空，并在 `replica_basis` 说明原因。预测副本数是推导值，不是执行结果；实际副本数是 Prometheus 里的观测值。
7. **评分与实测排名**使用同一份历史：只取所有被测算法都有实测值的指标按权重归一，各算法因此可比；覆盖所有已启用且有有效实测的算法（动态读取，不写死个数）。
8. **指标查询测试**（`POST /metric-queries/test`）：先校验模板变量与层级，再由 Prometheus 解析和执行；`stage` 为 template / datasource / syntax / query / empty / ok，原样给出 Prometheus 的错误；结果按换算系数与精度整形，与数据集存储的值一致，窗口最长 7 天，不写库。新增自定义 PromQL 必须先通过测试才能保存。

## 10. 问题修复 R3（真实数据链路、合并排名、算法覆盖、记录链路）

起因：真实库里的页面空、算法缺、分页异常，根因主要在数据，不在样式。逐条核对后的结论与规则：

### 10.1 数据与时间
1. SQLite 里旧版本写入的时间带 `+08:00`，新版本写 UTC，起止时间筛选按文本比较，跨偏移的行全部被筛掉：回测记录（537 行）、扩缩容记录（122 行）、实测评估（5662 行）在页面上是空的，数据其实都在。**修复**：迁移 `normalizeSQLiteTimes` 在每次 `--migration` 把所有 datetime 列重写为 UTC（幂等，只对 SQLite，有单测）；写入与筛选边界已是 UTC。
2. 评分回放没有可用窗口时（`windows = 0`），以前仍保存一行分数 0 并按名称排出名次，等于凭空排名。**规则**：一次评分没有任何回放窗口的算法不产生评分行（`ErrNothingToScore`）；排名查询（当前排名、历史排名）只读 `windows > 0` 的行。算法评分记录页仍列出全部已保存的行，不改。
3. 启用的算法缺必填参数（如 random_forest 的 `lags`）每次训练都失败：**规则**：启用（单个与批量）前按参数 schema 校验，不通过拒绝并写明原因；库里已经启用的会在状态里显示为「运行失败：参数 lags 是必填」。

### 10.2 每个已启用算法都要出现
- 历史数据、预测趋势对比（`GET /modules/{id}/compare`，字段 `statuses`）、算法实测排行榜（`GET /modules/{id}/leaderboard`，字段 `status`、`reason`）、排名页的指标排名（`metric-scores` 的 `unranked`）、当前排名（`ranking` 的 `status`、`reason`）都列出**全部**已启用算法。没有结果的给状态与原因，状态取自该算法最近一次训练记录：`ready` 有结果；`skipped` 最近一次跳过（样本/质量不足，原因原文）；`failed` 最近一次失败；`not_run` 启用了但还没有训练记录；`no_result` 跑过但所选范围内没有预测，或有预测但还没有对应的实际值可评估。
- 状态不是写死的列表：来自训练记录（`forecast_training_run`）与预测、评估行；算法个数动态读取。

### 10.3 页面职责
- **排名**（`forecast/ranking`，原当前排名 + 历史排名 + 两个独立列表合一）：模块 + 起止时间。上半是排名列表（每个算法一行：回放评分、各部分准确度、实测准确度、状态/原因），下面是标准指标排名（每个指标内按准确度排名）；再往下是评分随时间的变化和所选范围内每次评估的列表（服务端分页，勾选导出所选），点「查看此次排名」把那次评估放进上面的列表，「回到当前排名」还原。不再有 `forecast_ranking-history` 页面和菜单。
- **历史数据**：真实历史指标（Prometheus K 线、实际副本数、缺样与缺口）与保存下来的预测记录（预测时间、预测值、当时实际值）；不做误差统计。
- **预测趋势对比**：各算法预测值对实际值（线图，窗口向后延伸一个预测时长）、各算法误差汇总（MAE、WAPE、偏差，没有结果的排最后并写原因）、逐时间点的误差与误差率。
- **训练记录**：只有「运行概览」四个数（运行次数、命中率、平均耗时、最近一次）；成功/跳过/失败及原因在每条记录的详情里（状态说明 + 原因）。不再有单独的失败/跳过统计和「常见原因」面板。
- **算法运行情况**（新页，`forecast-results/algorithm-runs`）：每个已启用算法的运行次数、成功/跳过/失败、命中率、平均耗时、最近一次与常见原因（每个算法最多 3 条）；数字全部来自训练记录；没有运行过的算法也列出（尚未运行）。「训练记录」按钮带算法与模块跳到训练记录。

### 10.4 记录链路（真实数据，不造假）
- **扩缩容记录**：operator 每次调和后 `POST /operator/reports` 落 `scaling_execution`（模块、命名空间、目标、原副本 `current`、就绪 `ready`、目标 `desired`、动作、结果、原因、对应推荐版本）。真实库里有 122 条，之前被时间偏移筛掉；页面默认列补上原副本、动作与原因。
- **准入记录**：Kyverno 策略每次询问都落一条 `admission_decision`。真实库为 0 条，原因有二：集群里没有请求到达平台，且系统设置 `forecast.allow_admission_mode` 为 false 时旧代码在查模块之前就拒绝，**不写记录**。修复：先查模块、再判断开关，拒绝也记录（有单测）。没有任何模块匹配的请求不记录（否则集群里每个 Pod 都会写一行）。空列表的提示说明了这些条件。未用真实 Kyverno 验证。
- **回溯记录**：定时任务 `forecast.backtest` 一直在跑并落 `backtest_run`；页面空是 10.1 的时间偏移。

### 10.5 页面与图表
- 图表工具栏（缩放、还原、重置、保存图片）与图例分行，不重叠；图例只占工具栏左侧；底部范围滑块高 44px、与绘图区之间留 118px；图高 480–500px；纵轴名称在绘图区之上。

### 14.3 固定周期（最高优先级）规则

字段：名称、启用/禁用、起止时间（绝对时间段）、固定副本数、CPU（核）、内存（GiB）、优先级。0 表示该项不固定，仍由算法决定。每周重复的周期保留在后端与接口，界面只列出、不改动。

生效与冲突规则（决策函数 `decision.Decide`，逐字段判断）：
1. 顺序：**旁路 > 固定周期 > 算法推荐 > 模块兜底值 > 保持原值**。旁路时固定周期也不生效。
2. 启用且处于起止时间内才生效；到期或禁用后自动恢复算法推荐，不需要人工清理。
3. 多个周期同时生效且都固定了同一字段：优先级数值大的生效；相同则按名称字典序；决策原因里写明「覆盖了谁」。
4. 固定值**仍受模块上下限与内存下限（OOM）约束**：超出时被调整，并在原因里写「raised to the minimum / capped at the maximum」；这是安全边界，不是算法覆盖。
5. 算法、压力副本（metric pressure）、动态副本求解都不能改写固定周期的字段。
6. 删除模块时一并删除它的固定周期；克隆模块时复制固定周期。

### 16.5 资源与副本的职责（准入 vs 扩缩容）
- **副本数**随预测每个周期变化，由 operator 扩缩（operator 决策接口只回副本和边界，不回 CPU/内存）。**Pod 的 CPU/内存规格（requests）**在准入时设置，生效后保持不变：新 Pod（扩容或重启产生的）拿到的是生效中的规格，不是当次预测值，同一个工作负载的 Pod 一致，扩缩容决策不会改写资源。
- 规格何时变化（`forecastsvc/resourcespec.go`）：预测值（已取整）与生效规格相差不超过「变化百分比」（系统参数 `forecast.resource_change_ratio`，默认 20）不改动；增加超过它立即采用；**降低**超过它要等规格已生效满「保持小时数」（`forecast.resource_hold_hours`，默认 24）；旁路、固定周期、模块兜底、OOM 保护立即生效；生效中的规格本身来自固定周期等覆盖时，预测接管不被挡；生效规格超出模块上下限时不保留。
- 规格有版本（`recommendation.resource_version`，只在规格变化时 +1，`resource_changed_at`、`resource_held`），说明写在 `detail.resource_spec`（预测算出/快照采用/保持或采用的原因）。
- **取整**：CPU 低于 1 核按 10m 向上取整，1 核起按 50m；内存取整到整 MiB，1 GiB 以下 10Mi 一档（320Mi、420Mi），1 GiB 起 64Mi 一档；向上取整，再裁到模块上下限。展示用 `formatCpuMilli`（420m、1.5 核）与 `formatMemoryBytes`（320Mi、2Gi），不再显示无单位数字或 MiB 字样。
- 与 Kyverno/operator 不冲突：Kyverno 只改新 Pod 的 requests/limits，operator 只改副本数，两者读取的是同一个快照里互不重叠的字段；限制（limits）仍由准入按模块比例从 request 推出。

### 16.6 资源推荐与推荐快照
- 「资源推荐」页（`forecast-actions_recommendations`）：每个模块**当前**的推荐，CPU/内存（Pod 规格）、副本数、规格版本/保持标记、算法、决策说明，操作里有「快照历史」跳到该模块的快照。
- 「推荐快照」页（`forecast-actions_snapshots`，新菜单，拥有旧页面权限的角色自动获得）：推荐的**历史**。快照 = 模块的第一个推荐、每个结果变化的推荐（模式、副本数、规格版本、CPU/内存、GPU、算法、任一值的来源、降级、OOM 保护、副本上限）、至少每小时一个（`recommendation.snapshot`、`snapshot_reason`）。同样的结果每个周期重复的版本只用来保持当前推荐有效，不是快照。快照保存完整的推荐（参数、算法、指标来源、计算依据）和执行情况，可随时打开。
- 保留：每个模块最近 20 条推荐（不论是否快照）保留；更早的只留快照，快照每个模块最多保留 `forecast.snapshot_max_per_module`（默认 200）条，最新的一条永远保留；超过 180 天的清理（最新的保留）。升级时已有推荐按「第一条、变化的、当前」补记快照（`BackfillSnapshots`，只对还没有快照的模块做一次）。
- **状态**（`forecastsvc.SnapshotState`，由 operator 的执行报告和准入记录得出，快照覆盖的范围是它的版本到下一个快照之前）：待执行 pending（当前、有效、还没人用）｜已执行 applied（operator 按它扩缩过，或副本数本来就对，或准入把它的资源给了新 Pod）｜执行失败 failed（operator 报错或冲突且没有一次成功）｜已过期 expired（被新快照替换或过了有效期而从未被使用）｜仅建议 advisory（模块只推荐，没有执行方；是第五种，只用于 recommend 模式）。扩缩容记录页的结果名也统一：已执行、无需变更、暂缓、冲突未执行、执行失败。接口 `GET /snapshots`（module_id、state、from、to、排序、分页）与 `GET /snapshots/:id`（完整决策与该范围内的执行）。

### 16.7 降级与回退
- **降级（degrade）**：预测算法、指标数据或决策服务异常时，改用预设的安全配置继续运行（模块兜底值、保持原值、OOM 地板；operator 没有可用决策时保持副本数）。一次降级是一个**事件**：从第一个降级快照开始，到下一个正常快照结束，持续时间与恢复时间都算出来；原配置 = 降级之前生效的配置，目标配置 = 现在改用的安全配置。
- **回退（rollback）**：已经决定的变更没有成功落地（operator 报错，或另一个自动扩缩器占着目标）时，工作负载保持在此前有效的配置上；原配置 = 本来想改成的副本数，目标配置 = 实际保持的副本数；恢复 = 之后第一次成功的执行。冷却、步长限制属于节奏控制，不是记录。平台没有「撤销一个已经应用的变更」的机制，不把它说成有。
- 接口 `GET /fallbacks`（kind=degrade｜rollback、reason、module_id、时间）；每条记录有 kind、触发原因、changes（字段、原配置、目标配置、来源）、实际执行结果（状态与句子）、发生时间、是否进行中。页面默认可见的五列：发生时间、模块、触发原因（含类型）、原配置 → 目标配置、实际执行结果。

### 17.1 预测资源准确度（统一公式）
- 准确度针对**资源**（CPU、内存、GPU），不是副本数。副本数由资源需求推出（整个负载需要的资源 ÷ 一个 Pod 的规格，向上取整），本身不是一项准确度。例：一个 Pod 1C/2GiB，负载实际需要 3C/6GiB（3 个 Pod），预测需要 4C/8GiB（4 个 Pod）：CPU 准确度 = 1 − |4−3|/3 = 66.7%，内存准确度 = 1 − |8−6|/6 = 66.7%；副本数 4 对 3 只是这两个数的结果。
- 一个窗口的资源准确度 = 1 − Σ误差 ÷ Σ实际值，误差 = |预测 − 实际|，预测低于实际（低估）时乘 `Under`（默认 2）；下限 0。
- 每个资源有自己的分：`score = 100 × 准确度 × (0.7 + 0.3 × 数据完整度)`；内存再乘 `(1 − OOM 扣分)`，OOM 是内存事件，只扣内存分，CPU 与 GPU 不扣。综合分 = 各资源按权重（CPU 0.35、内存 0.45、GPU 0.2，没有数据的部分剔除后归一）加权，再乘 `(1 − OOM 扣分) × (0.7 + 0.3 × 完整度)`。
- 只有当模块没有任何 CPU/内存/GPU 来源时，才用副本数的准确度当综合分（此时它是唯一能评的量）。副本匹配次数 `replica_exact` 作为派生数字保留，不进分数。
- 实现：`pkg/scoring`（`Result.Metrics`、`MetricResult`），接口的 `breakdown` 每项有 `accuracy`、`score`；副本数只在上述唯一情形下出现。

### 18.5 乱码
- 根因：客户端（GBK 控制台里的 PowerShell 或 curl）发来的中文不是 UTF-8，JSON 解码把非法字节换成 U+FFFD 后入库，原文无法恢复。库里 `secret_key` 的 `operator` 凭证备注和对应的操作日志就是这样。
- 修复：`UTF8BodyMiddleware` 拒绝非 UTF-8 的 JSON / 表单请求体（400，说明原因）；日志与备注的截断改为在字符边界截断（`truncate`、`trimTo`）；升级时把含 U+FFFD 的备注换成「(备注因提交时编码错误损坏，请重新填写)」，日志请求体换成说明（`repairBrokenRemarks`）。原备注要由管理员重新填写。

### 19.3 没有做或没有完全做的
- **算法清理**：移除了 macd_trend（金融技术分析类）以及意义不大的 naive_bayes、rnn、gru、lstm。理由：naive_bayes 把序列分桶后预测一个桶，分辨率受桶宽限制；rnn、gru、lstm 每次运行都在单个工作负载的几千个点上现训练一个网络，受训练时间预算限制，没有任何一份测量显示它们在这类数据上胜过统计算法（A0 的基线表里没有它们）。保留的 random_forest、knn、gbdt、ridge_ar 都在 A0 里有测量。深度学习类别因此没有算法，前端的分类选项里也去掉了「技术指标」「深度学习」。升级迁移删除这些算法的设置、预测、评估、回测、训练、评分数据，以及以它们为基础的自定义算法；推荐记录里的算法名保留。
- **多维度准确度**：评分按 CPU、内存、GPU、综合分行，副本数只在模块没有资源来源时出现。系统里**没有 Node 数量这个指标**，所以没有 Node 维度；历史数据页的副本数仍在右侧副轴，没有另拆页面。
- **个人中心**：没有做成「原有」的标签页布局——原来的标签页还带 Telegram 绑定，Telegram 随旧工作流页面在前面的提交里整体移除，且本项目约定页面和弹窗不用标签页；所以只保留三张卡并增加账户信息卡。没有找到别的被删掉的账户功能。
- **全局中文化**：抽查了列名和枚举值的渲染，没有发现外露的原始英文；没有逐页逐列做完整审计，浏览器里也没看过。
- **浏览器验证**：本节所有页面改动只经过类型检查、lint、locale 测试和后端测试，没有在浏览器里看过（QA 环境仍然没有重建）。
