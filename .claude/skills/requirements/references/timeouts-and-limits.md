# 超时、并发与资源限制总表（B6，2026-11-19）

一个请求从浏览器走到数据库再回来，每一层都有自己的时间和数量限制。**规则：越靠外的限制越大，越靠里的越小**，这样先停下的总是平台自己（它会说明原因，回 504 和 `X-Timeout-Source: platform`），而不是网关用一个没有原因的 502 或 504 切断。

| 层 | 限制 | 默认 | 在哪里改 | 谁先停 |
|---|---|---|---|---|
| 浏览器 | 一般请求的超时 | 60 秒（`ui.request_timeout_seconds`） | 系统参数 | 必须不小于网关超时 |
| 浏览器 | 读请求失败后的重试次数（502、503、断网） | 1 次（`ui.request_retries`） | 系统参数 | |
| 浏览器 | 带 `X-Long-Request` 的请求 | 网关超时 + 10 秒 | 随网关超时 | |
| 网关（Nginx、Ingress、云负载均衡） | 等后端回答的时间 | **你的网关自己的设置** | 网关 | 平台需要知道它：见下一行 |
| 平台参数 | 告诉平台网关等多久（`http.gateway_timeout_seconds`） | 60 秒 | 系统参数 | **必须和网关的真实设置一致**，平台据此把自己的时限压在它之下 |
| 平台 | 读请求（列表、报告、图表）的时限 | 30 秒（`http.list_query_seconds`），并小于网关超时 | 系统参数 | 到点取消数据库语句，回 504 并说明原因 |
| 平台 | 模块页的 Prometheus 分位数（`/modules/:id/overprovision/prometheus`） | 读请求时限（`http.list_query_seconds`）减 2 秒；没有时限的请求用网关时间减 5 秒；最多 8 个指标一起问 | 系统参数 | 到点停止，答完的指标照常给，没答的标 `skipped`，整份标 `partial`，不回 504；部分答案不进缓存 |
| 平台 | 没给时间范围的文本搜索只读最近几天 | 7 天（`http.list_search_days`） | 系统参数 | 页面提示读了几天 |
| 平台 | 没给起点的汇总只读最近几小时 | 24 小时（`http.summary_window_hours`） | 系统参数 | 页面提示 |
| 平台 | 操作日志、登录日志（按用户名、地址搜）、任务审计的文本搜索没给范围时只读最近几天 | 同上一行（`http.list_search_days`） | 系统参数 | 页面提示读了几天 |
| 平台 | 列表的总数 | 最多数到 100000，到了就说“超过” | 代码常量 | 缩小筛选条件 |
| 平台 | 结果缓存 | 30 分钟（`cache.result_minutes`，0 关闭），64 MiB；答案只在依据的数据没变时才给；Prometheus 分位数最多 5 分钟、变更预览最多 10 分钟 | 系统参数 | 响应头 `X-Cache`；命中率在系统诊断页 |
| 平台 | 预测复用 | 30 分钟（`forecast.reuse_minutes`，0 关闭） | 系统参数 | 同样的输入不重算、不重复写预测行 |
| 平台 | 翻页深度 | 跳过超过 20000 行回 400 | 代码常量 | 请缩小筛选条件 |
| 平台 | 慢请求日志阈值 | 3 秒（`http.slow_request_seconds`） | 系统参数 | 只写日志，带请求号 |
| 平台 | 手动步骤（采集、预测、回测等）同步运行的预算 | 300 秒（`forecast.pipeline_timeout_seconds`），同步时压在网关超时之内 | 系统参数 | 后台运行（`POST /modules/:id/steps/:step`）不受网关限制，只受这个预算 |
| 平台 | 变更预览 | 60 秒（`forecast.preview_budget_seconds`） | 系统参数 | 说明原因，不回一半结果 |
| 后台任务 | 工作进程心跳／判失联 | 每 10 秒／60 秒没有心跳放回队列（至少给 3 次） | 代码常量 | 巡检每 15 秒一次，次数用完以 `worker_lost` 失败 |
| 后台任务 | 可再试的失败 | 等 10 秒、20 秒……最长 2 分钟；采集 3 次、预测／运行／评估／变更预览 2 次、回测和评分 1 次、AI 提问 2 次 | 代码常量 | 步骤超过流水线时限不再试 |
| 后台任务 | 进度和部分结果的写入 | 进度最多每 250 毫秒一次，部分结果每 500 毫秒一次、最多 256 KB | 代码常量 | 最后一个值不丢 |
| 后台任务 | 结果保留与记录保留 | 72 小时（`assistant.async_retention_hours`）后清结果、再留 30 天记录 | 系统参数／常量 | 过期后只留记录 |
| 平台 | 请求耗时基线与进程运行记录 | 保留 14 天，每分钟存一次，每 30 秒写心跳 | 代码常量 | 系统诊断页 |
| 平台 | 一个算法一次预测 | 120 秒（`forecast.train_budget_seconds`） | 系统参数 | |
| 平台 | 预测清理每轮删多久 | 120 秒（`forecast.prune_budget_seconds`），一批 1 万行；疏化被新运行盖掉的旧预测也用这个预算（`forecast.prediction_thin_after_hours`，默认 24 小时） | 系统参数 | 下一轮接着删 |
| HTTP 服务器 | 读请求头 | 10 秒 | 代码 | 防止慢连接占着不放 |
| HTTP 服务器 | 空闲连接 | 3 分钟 | 代码 | 要比网关的空闲保持时间长，否则网关会拿到已被平台关掉的连接，得到 502 |
| HTTP 服务器 | 停机时等运行中的请求 | 40 秒 | 代码 | 滚动更新不切断正在回答的页面 |
| Pod | `terminationGracePeriodSeconds` | 60 秒 | Helm | 要大于上一行 |
| Pod | 内存限制和 `GOMEMLIMIT` | 1Gi 和 900MiB | Helm（`resources`、`goMemLimit`） | 被 OOM 杀掉的 Pod，在途的请求全是 502；`goMemLimit` 取内存限制的九成，改内存限制时要一起改 |
| Pod | CPU 限制 | 2 核 | Helm | Go 1.27 按 cgroup 的限制设 `GOMAXPROCS`，不用另设 |
| Pod | 探针 | 启动（查数据库）5 秒一次最多 60 次；存活 20 秒一次、3 次，**不查数据库**；就绪 10 秒一次、3 次，查数据库、3 秒内要答；每个探针的超时 5 秒 | Helm | 存活探针只问进程还在不在：数据库慢或连接用完时 Pod 不会被重启（重启会让在途的请求全部 502）；就绪探针查数据库，连不上的 Pod 暂时从 Service 里摘掉 |
| 数据库 | 连接池（`max_open_connection`、`max_idle_connection`） | 代码默认 25／10；Helm：MySQL 100／50，PostgreSQL 25／10 | 配置文件、Helm | 所有 Pod 的连接之和要小于数据库的 `max_connections`；池不够时在“数据库诊断”页看到“等连接次数”增长 |
| 数据库 | 单条语句 | 随请求的时限取消 | 请求的上下文 | 到点取消，不会在网关切断后继续跑 |
| Prometheus | 一次抓取同时发出的查询数 | 每个数据源的“最大并发” | 数据源页面 | |
| Prometheus | **整个平台对一个数据源同时在途的查询数** | 8（`forecast.prometheus_total_concurrency`） | 系统参数 | 多人同时开历史页、采集同时进行时，不会把 Prometheus 压慢到所有人都超时；排队的查询随请求的时限放弃 |
| Prometheus | 数据源超时 | 每个数据源的“超时” | 数据源页面 | |
| 语言模型 | 一次请求超时 | 每个连接的“超时”，默认 90 秒 | LLM 管理 | |
| 语言模型 | 一次工具读取 | 20 秒；`analyze_resources`（资源大盘的分析，每个模块读一次 Prometheus）100 秒 | 代码 | 该工具最多读 40 个启用模块、每次回答最多 20 个，一次 4 个、每个模块 45 秒；读不到的写进回答的 `skipped`，不拖垮整个回答 |
| 语言模型 | 每日 AI 建议（资源大盘） | 每天 8 点（任务 `Resource advice`，调度可改），一个任务、一份报告 | AI 配置 > 定时任务 | 最近一次失败显示在大盘上，同时留着之前的报告 |
| 语言模型 | 一个问题的总时间 | 超时 × 读取次数，最多 10 分钟 | 代码 | 提问在后台运行，不占网关 |
| 语言模型 | 并发中的提问 | 有上限，满了回 429 | 代码 | |
| Operator | 请求平台的超时和降级时间 | 见 `operator.*` 系统参数 | 系统参数 | |

**检查顺序（出现 502 或 504 时）**
1. 看响应头 `X-Timeout-Source`：是 `platform` 就是平台自己按上面的时限停的，页面上的提示写了原因和该改的参数；没有这个头，就是网关或更外面切断的，先核对 `http.gateway_timeout_seconds` 和网关的真实设置是否一致。
2. 打开“系统管理 > 数据库诊断”：连接池“等连接次数”在涨说明池太小，“正在执行”里有长语句说明查询慢。
3. 看平台日志里带请求号的慢请求和“被放弃的请求”。
4. Pod 有没有被 OOM 杀掉（`kubectl describe pod` 的 `Last State`），有就调内存限制和 `goMemLimit`。
