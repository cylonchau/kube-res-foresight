# 04 验收标准与实施顺序

> **2026-10-31：自定义资源 PredictiveScaler（CRD）已移除。** operator 只读平台的模块并写副本，不在集群里创建任何资源；下文提到 CRD、PredictiveScaler、Static/Prometheus 决策来源、Observe 模式的地方是当时的设计，不再适用。现状见 `.agents/skills/control-plane/SKILL.md`。


> 来源：根目录 `docs/04-验收标准与实施阶段.md`。以下是未来阶段验收，不是完成报告；当前能力见 [代码地图](repository-map.md)。日期与数值仅为测试样例。

## 阶段 1：基础与管理
完成中文菜单、系统参数、用户/角色/菜单/授权/操作日志保留、LDAP/LDAPS 对接、权限与审计、Prometheus 数据源接入与指标质量看板。必须可查询 30 天 CPU/内存/RPS 及 P50/P95/P99，并明确聚合粒度和缺失情况。

## 阶段 2：算法框架和回测
完成动态算法注册、统一参数 Schema、宽屏参数编辑及 Naive/SeasonalNaive、EWMA/Holt-Winters、岭回归/GBDT（纯 Go）的可运行对照；按工作负载和 horizon 做无未来泄漏的滚动回测，比较峰值低估、分位数覆盖、SLO 与训练/推理成本。金融技术指标不纳入交付。新增算法须以 Go 实现，未优于基线不得仅因模型复杂而晋升；内存规格推荐另验收峰值/OOM 保护。

## 阶段 3：模块与安全策略
模块绑定算法、默认副本与资源值、有效期、故障回退、特殊日期窗固定配置；确保时间窗内完全绕过相关模型值；各模式 observe/recommend/admission/auto 可切换。所有切换写入审计。

## 阶段 4：准入与 Operator
Webhook 只读有 TTL 快照；Webhook 断连/超时、Kafka/Prometheus/算法故障时仍成功发布且使用明确 fallback；上线 kube-res-foresight-operator 按 CRD 自动扩缩容，并阻止与 HPA 同时写同一对象；提供独立 `/metrics`。

## 阶段 5：闭环评估
每次计算：保留原特征窗口、所有算法候选、选中的算法及权重、推荐的 requests/limits、目标副本、决策解释、执行结果、实际 Ready 时间、预测与真实误差；历史查询和导出；可按 MAE/WAPE、P90 覆盖率、burst 召回率、错报率、SLO 违规、容量成本评估模型。

## 阶段 8（整理，未开始）：AI 分析与对话、异步计算与 502/504 治理

见 [ai-and-performance-p11.md](ai-and-performance-p11.md)。验收口径：AI 没有任何写 Kubernetes 或平台资源配置的能力；回答里的数字都来自工具，不是模型自己算的；工具按调用者权限过滤，无权限的数据被拒绝且有审计记录；审计记录只含元数据（用户、会话、工具、参数脱敏、行数、token、耗时、结果），不含密钥和正文；会话入库、只有本人可见、关浏览器后能恢复，悬浮窗与独立页面共享；长耗时操作提交后一个请求内返回任务 ID，任务状态持久化、可查进度和部分结果、可取消、可重试、平台重启后不丢；相同输入 30 分钟内不重复计算；每个同步接口的最坏耗时小于网关超时的一半；502/504 先定位再治理，验收指标先测基线再定数值；AI 业务感知（2026-11-19 补充）：反代与标准 API 共用能力注册表和上下文；反代不支持工具调用时由后端走受控的文本协议或规则路由，只执行注册表里的只读项，模型输出永远是数据；无权限的能力不出现、不可调用；被问到不支持的操作要准确说明并指出去哪里做；不让模型写任意 PromQL；两种接入方式用同一组自动用例验证（假的 OpenAI 兼容服务器，一个返回 tool_calls、一个像反代那样忽略 tools），真实 Codex 反代只能在你的环境里手动走一遍。只用合成数据和故障注入验证，没有对着你的真实网关验证。

## 阶段 7（当前，未开始）：资源超配分析与可观测大盘

见 [overprovision-p10.md](overprovision-p10.md)。验收口径：配置与元数据由 Controller 只读上报（Controller 不连数据库，重启后数据不丢）；超配判断只用真实历史，不用预测；每个结论能回答“为什么超配、依据哪些指标、分析了多久、真实用了多少、建议值怎么算”，并给出公式与代入的数；CPU 与内存独立判断，节流和 OOM 保护有单测；JVM 的 Used、Committed、Max 与 Container 的 Working Set、RSS 并排显示，不互相替代；数据缺失时写可信度，不给确定性结论；移动平均写成 `MA(n, 步长)`；系统大盘与 Grafana 用同一套口径，互相能带参数跳转；只用合成数据和假 Prometheus 验证，Grafana 无法在真实实例里加载。

## 阶段 6（暂缓）：成本闭环（C1～C4 在暂缓前已实现并在合成数据上验证，C5～C8 未开始）

见 [cost-closure-p9.md](cost-closure-p9.md)。验收口径：成本守恒（Σ工作负载成本 + 闲置 = 节点总成本，没有价格的节点标“未定价”不当 0）；成本最优值不低于安全值；“已实现节省”只在节点数确实下降且有节点小时或账单依据时出现，否则最多是“预计”；机会列表不直接相加；装箱模拟的结果标为乐观上界并列出未模拟的约束；回滚幂等且也进台账；全部只用合成数据验证，真实 OpenCost、账单和集群上的节点释放没有验证。

## 关键验收用例
1. 新业务历史不足：不会盲目缩小用户 limits，使用模块 fallback；没有合法 fallback 则原样保留用户配置。
2. 历史 2Gi、瞬时 8Gi：不能仅因 P95 低而建议 3Gi Limit；展示峰值证据与保留策略。
3. 2026-10-01 至 2026-10-20 固定时间窗：命中 10 副本、CPU Limit=6、Memory Limit=24Gi；时间结束恢复正常，审计固定覆盖命中。
4. Kafka、Prometheus、算法服务分别断开：新 Pod 发布不失败；控制器停止危险缩容；状态清晰报警。
5. 有 HPA 的 Deployment 启动自定义 Auto：必须阻止双控制器写入并告警，不能发生副本反复振荡。
6. 对于预测值 1800、真实值 1950，记录 APE=7.69%，并将区间准确率与点预测准确率分开。
7. 计算 CPU、内存和 RPS 时分别展示聚合层级；不能将平均单 Pod RPS 误称每个 Pod 实测值。
8. 无突发历史无法保证毫秒级 Burst：系统须返回“不可充分预测”并保有最低 Ready 容量。
9. LDAP 账号注销或禁用后权限按同步策略收敛，break-glass 本地管理员可恢复权限系统。
10. `kubectl` 观测预测 CRD 与 Deployment 期望/Ready 一致，Metrics 与日志能对账。
